# Architecture

This repository ships one Claude Code plugin and two outer loops around it. The plugin (`hooks/`) runs inside a `claude` session and keeps a persona's goal tree and heartbeat, and writes and reads the persona's distilled memories as records in the kit's shared memory store. The supervisor (`bin/supervise.sh` with `bin/supervise-decide.mjs`) runs one such session at a time for days and relaunches or stops it on the signals the session writes. The process keeper (`bin/Start-Persona.ps1`, `bin/keeper-functions.ps1`, `bin/Register-PersonaTasks.ps1`, `bin/keeper-probe.ps1`) runs one supervisor per persona under a Windows scheduled task that starts at boot with no logon. One persona in the fleet, the one the `coordinatorPersona` setting names, reads back up the stack: its plugin reads the roster and every roster persona's keeper state files, and can write two files into another persona's run directory, the restart request and the interrupt request, both read by that persona's supervisor. `README.md` at the repository root carries the plugin's design and the operator-facing reference for the supervisor and the keeper. This document states how the three layers fit together, what each owns, and how each fails.

## Layers

| Layer | Process | Owns | Reads | Writes |
|---|---|---|---|---|
| Plugin | `claude` (the child) | goal tree, task list, self-review lessons, the list of memory records shown per goal, decision log, heartbeat, commons inbox, the decision journal, the fleet reading on the coordinator persona | its own store, the commons store, the question override directory `<home>/.claude/agentic-questions/`, the plan document a queue entry names, under the session's live directory or the nearest ancestor of it inside the same checkout, at `docs/plans/` or one of three archive places, `<rundir>/mailbox.jsonl` and `<rundir>/mailbox.ack.jsonl` on a supervised launch, and on the coordinator persona the roster, every roster persona's `keeper.json`, `keeper.hold` and `keeper.park`, and the standing `restart.request` in the run directory a `fleet_restart` call targets, and at a supervised launch's priming turn, through `bin/restart-recap.mjs`, the harness transcripts of the sessions that held the persona before this one, under `<home>/.claude/projects/`, and through the kit's `memq judged` at each prompt of an owner-armed session, this persona's records in the kit's shared memory store | `<workdir>/.agentic-personas.json`, `.agentic-heartbeat.json`, `.agentic-yields.log` when it yields, `.agentic-goal-history.jsonl` when `goal_create` replaces a tree, the channel log segments `.agentic-channel.<n>.jsonl`, the machine-global commons store, `<home>/.claude/agentic-decisions/<persona>/<YYYY-MM-DD>-<session>.jsonl`, on a supervised launch `<rundir>/mailbox.ack.jsonl` and `<rundir>/heartbeat.json` (its own `supervisorHeartbeatPath`), and on the coordinator persona another roster persona's `<rundir>/restart.request` and `<rundir>/interrupt.request`, and through the kit's `memq put` and `memq touch --applied`, records and applied stamps in the kit's shared memory store, in the project tier of the launch directory |
| Supervisor | `bash bin/supervise.sh` | launch, poll, stop, relaunch or adoption of one child | the persona store, the workdir's shared heartbeat sidecar, the child's own `heartbeat.json`, the child's `stdout.jsonl`, the newest turn-record timestamp in the child's harness transcript and its subagent transcripts, `mailbox.jsonl` and its ack file, `<rundir>/restart.request`, `interrupt.request`, `shutdown.request`, a prior `handle.json` under the run directory, and `child-N/interrupt.served`; the holder it launches reads Claude Code's `installed_plugins.json` once per child launch for the kit's skill prefix | `<rundir>/supervisor.log`, `supervisor.err`, `settings.json`, `<rundir>/child-<n>.prompt`, `child-N/` (`handle.json`, `child.pid`, `.exit`, `ask.request`, `interrupt.request`, `interrupt.served`), `mailbox.jsonl`; the holder it launches, `bin/supervise-holder.sh`, writes `child-N/holder.pid`, and takes `child-N/interrupt.request` by renaming it to `interrupt.request.taken`, which it removes once read; in the work directory it removes `.agentic-channel.jsonl` and every numbered `.agentic-channel.<n>.jsonl` segment but the highest once older than `channelLogRetentionDays` |
| Keeper | `powershell.exe -File bin/Start-Persona.ps1` | relaunch, hold, park or exit on the supervisor's exit code | the roster, the env file, the supervisor's exit code and stderr, the machine's process list | `<rundir>/keeper.log`, `keeper.json`, `keeper.hold`, `keeper.park`, `supervisor.out` |
| Task Scheduler | `AgentPersona-<name>` | starting the keeper at boot, restarting it when the keeper itself fails | the task definition | the task's last-run result |

Each layer's whole input from the layer below is one channel. The supervisor reads the child through files the child writes, and reads five files the child does not. `<rundir>/restart.request` is written by the coordinator persona's plugin through `fleet_restart`, and `<rundir>/interrupt.request` through `fleet_interrupt`. `<rundir>/shutdown.request` is written by the operator to stop the persona on purpose. A `handle.json` under the run directory is written by an earlier supervisor for the child it launched. A child directory's `interrupt.served` is written by the supervisor that last relayed an interrupt there, and read by any supervisor that adopts the child. The keeper reads the supervisor through its exit code, plus the last stderr line for the hold marker's text, and finds one already running through the process list before each launch. The scheduler reads the keeper through the keeper's exit code alone. The supervisor never writes the persona store, and the keeper never reads it.

No layer reads how full the child's context window is. The plugin keeps no estimate of it and the supervisor restarts no child on context grounds, so the signals in the table above are the whole set. Compaction is the harness's own, landed at the boundary the plugin banks through the kit's checkpoint CLI. In every session that owns its persona, it banks one after the persona's own turn ends with an answer, no `BLOCKED:` or `WAITING:` lead, no question left open to the operator, no background agent the main loop started still running, and no plan section left half-done. A background subagent's completion neither owes nor drops one. The bank runs at the first main-loop tool call the model makes in a later turn, and a later turn that ends without that shape first drops it. `README.md` under "No context reading" states the predicate, the command and the decisions it logs.

A queue entry that carries a plan document is judged from that document rather than from a count of turns. `hooks/plan-record.ts` parses it for a `Status: Complete` header, its Chapter count, its section total and its latest Chapter's `Next:` line, and the session that owns the store reads it at the end of each turn on the entry, at `planPath` or one of three archive places. A readable document's section total and `Next:` line are stored on the plan holder as `sectionCount` and `nextSection` for the Discord board card, without moving `updatedAt` or logging a decision. The directory is the session's live one from `$.session.cwd()`, or the nearest ancestor of it that holds the document. That walk stops at the first folder holding a `.git` entry, so a worktree never reads the launch checkout's stale copy, and a read under an ancestor logs `plan_record_dir_resolved` once per plan holder. The entry's other record is the worker's own closing text. The owning session reads its first line at turn end for a `BLOCKED:` or `WAITING:` lead, and the controller holds its idle nudges for that entry while the lead stands. A blocked lead stands until a working turn clears it, `goal_resume` lifts it, or an ask on the entry closes after it was set. A waiting lead holds for 60 minutes, or until a `WORKING:` line or a working turn clears it. Completion by the document clears the lead on every entry it completes. `README.md` states the rules under "Plan entries: judged from the record". The supervisor reads none of this: its own checks read the `restart_requested`, `shutdown_requested`, `park_requested` and `root_complete` decisions, plus the run directory's `restart.request`, `interrupt.request` and `shutdown.request`, and never the round counter or the document. After a child exits 0 on its own, it also reads the `untracked_work` decision, the one line a session keeps for turns that did work with no open goal.

Whether the controller nudges is its own record, and the goal tree carries only the states the worker and the operator mean. One read, `holdOf` in `hooks/agent-state.ts`, returns the reason not to nudge: an open ask, a blocked lead, or a waiting lead inside its 60-minute window. It is computed on each idle tick and stored nowhere. The nudge cap, the hourly cost cap, the error streak and the worker's own `ASK:` line each hold by opening an ask, and none of them writes a status on the entry. The controller writes `paused` only when it assigns the active slot, at a plan switch and at `goal_resume`'s demotion of the entry it displaces. Each nudge asks the worker to open its closing text with `WORKING:`, `WAITING:` or `BLOCKED:`. Three nudged answers in a row that carry none of them and do no work open one fixed question to the operator, which pauses nothing. A turn counts as open from its `turn.start` to the `turn.complete` carrying its id, and both write that id to the plugin's log. `README.md` states each rule under "Nudge discipline" and "Ask wait".

A channel turn the persona ends without replying still reaches the operator, and only the persona's own answer does. Where a Discord message opened the turn, whatever its sender class, the persona's own turn end carries an answer, and nothing in the turn called the reply tool, the `turn.complete` handler in `hooks/index.ts` sends that answer to the thread through the relay's reply tool. It logs `channel_reply_backfilled`. Where that direct call throws, it submits one `[REPLY BACKSTOP]` turn asking the model to send the exact text, and logs `channel_reply_backfill_reprompted` once the submit is accepted. Only the session that owns the persona backfills. A priming turn and a nudged turn are never backfilled, and neither is a turn that ended aborted, errored, refused or with no answer. The persona's own turn end is the completion carrying the id its `turn.start` recorded and no subagent `agentId`, which the handler reads as `completesGateTurn`. A background subagent's completion inside the open channel turn carries the subagent's report as its answer. It posts nothing and leaves the channel-origin flag set, so the persona's own completion afterwards is still backfilled. Three bounds follow from these rules. A reply-tool call from any loop in the turn counts as the persona's reply, a subagent's included. A channel turn whose `turn.start` this session never saw, such as one open across a plugin reload, is not backfilled. The handler's other readers of the answer, the `ASK:` match, the plan entry's lead and the inbox reply filer, still read a subagent's completion. `docs/backlog.md` files the first and the third under their own headings.

The session that owns a persona receives its inbox one record per turn. The inbox drain, `drainInbox` in `hooks/index.ts`, delivers the oldest deliverable record as a labelled prompt and returns. It runs at a quiet controller tick. It runs again from the `turn.complete` handler when a turn this session saw start has closed and no other turn is open. So a burst of records drains back to back, each further record following as the previous delivery turn ends. Two kinds of completion drain nothing even then: one carrying a subagent `agentId`, whatever turn id it carries, and one whose handler attempted the `[REPLY BACKSTOP]` submit, whether or not the harness accepted it. After those, the record waits for the next qualifying turn end or quiet tick. The handler schedules its drain rather than awaiting it, so it returns `next(e)` first, and a throw out of that drain is recorded as one `operator_delivery_error` decision. A shared in-flight promise, `drainInFlight`, keeps a tick and a completion from delivering the same record twice. `turn.start` is the only event that marks a turn open, so a session whose harness never reports a turn's start drains at tick pace alone. `README.md` under Delivery states the labels and the record lifecycle.

Two channels run the other way. A supervised child's plugin reads `<rundir>/mailbox.jsonl`, which its own supervisor writes, and acknowledges each record in `mailbox.ack.jsonl` beside it. The fleet reading is the other, and the one that reaches the keeper's layer. The coordinator persona's plugin reads the keeper's own state files for every persona in the roster, so one child sees the layer above it, and it sees that layer for the whole fleet rather than for its own supervisor. It writes none of the keeper's files: no plugin path writes a roster, a `keeper.json`, a `keeper.hold` or a `keeper.park`. The two files it writes into another persona's run directory are `restart.request` and `interrupt.request`, and that persona's supervisor reads them rather than its keeper.

The plugin also ships skills, under `skills/<name>/SKILL.md` at the plugin root, which Claude Code discovers from that layout and `claude plugin validate` reads. Each skill is a short procedure over one script in `bin/`, so a session invoking it and any other caller share one set of mechanics. `upgrade-check` validates a new Claude Code build before the fleet restarts onto it, over `bin/upgrade-check.mjs`. Its `pre` verb runs its Claude Code sessions in a scratch folder where the plugin stays passive, and its `post` verb runs in the canary session after that session restarts onto the new build. Both append rows to `upgrade-checks.jsonl` in the roster's directory and regenerate `upgrade-checks.md` beside it. So the record is a property of the machine and its installed build, not of this tree. Every session `pre` starts inherits the check's own environment unchanged, except step 2's probe run. From Claude Code 2.1.287 the engine loads the plugin's module with no environment variable set for it. `restart-recap` tells a restarted persona session what the session before it was doing, over `bin/restart-recap.mjs`. The script reads the transcripts of the sessions the store's `previousSessionIds` names, or the newest other transcript in the working directory's transcript folder where that list is empty. It prints one JSON header line, whose `lineage` field says which of the two it read, and a bounded digest of the operator's messages, the persona's replies and each session's last words. The plugin runs the same script at the supervisor's priming turn, so the skill and the automatic block share one set of mechanics.

The upgrade check reads the new build's plugin interface off a probe plugin, because the engine writes its declarations only beside a plugin it loads from a folder. An installed copy gets none, and no slash command writes them. Step 2 writes a one-hook probe into the scratch folder, at `<scratch>/types-probe/`, and makes an empty config folder at `<scratch>/config`. It then runs `claude -p "/version" --plugin-dir <probe>` with `CLAUDE_CONFIG_DIR` set to that folder. The probe's environment drops `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` (`PROBE_LOGIN_KEYS` in `bin/upgrade-check.mjs`), so no Anthropic login reaches the run and it sends nothing to the model. A cloud-provider login is not dropped, and `docs/backlog.md` carries that gap. The run prints "Not logged in" and exits 1, having already written `claude-code/index.d.ts` and `claude-code-tools/index.d.ts` under `<probe>/.claude-plugin/types/`. Step 2 joins the two, the tools' tables after the interface, into `<scratch>/claude-code.d.ts`, which steps 3 and 4 read. The step passes once the run spawned, did not time out, and both files are present. Its pass row opens with the declarations' first line, which names the build that wrote them, then carries the exit code and the run's first output line as evidence. A missing or empty interface file, or a missing tables file, reads fail and names the file. The exit code decides nothing. The scratch folder, emptied at the start of each run, is what keeps an earlier run's files from reading as this build's. The engine also writes a tool-list mirror beside the probe, and step 4 ignores it in favour of the checkout's own `.claude/types/claude-code-mcp.d.ts`, since the probe connects no tools. A `--dev` session writes the same `.claude-plugin/types/` folder into the checkout, and `.gitignore` keeps it out of the index. `README.md` under "Cost and cadence options", beside its AL7 note, states the hand recipe that regenerates the committed `.claude/types/claude-code.d.ts`.

## Data flow at boot

1. Windows starts the `AgentPersona-<name>` task under the Password logon type for the registered user, at RunLevel Limited. That logon unlocks the account's user-scope DPAPI key, so the credential stores a persona's git reads are readable. The user-scoped `PATH` and the profile variables come from the environment file in step 4 rather than from the task's own environment.
2. The task's action runs `powershell.exe -NoProfile -WindowStyle Hidden -ExecutionPolicy Bypass -File <repo>/bin/Start-Persona.ps1 -Name <name> -Roster <roster> -EnvFile <envfile>`, every path absolute (`bin/Register-PersonaTasks.ps1:311-313`).
3. The wrapper reads the roster entry (`Read-KeeperRoster`), resolves the run directory, and stops if a hold marker exists there. Otherwise it removes a park marker if one exists and goes on.
4. It applies the env file's allowlisted keys to its own process (`Set-KeeperEnvironment` in `bin/Start-Persona.ps1:158-196`), which pins `HOME`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `TEMP`, `TMP`, prepends `KEEPER_PATH_PREPEND` to `PATH`, and takes `KEEPER_BASH_EXE` as the bash to run.
5. It builds the supervisor's argument list and environment from the entry (`Build-SupervisorInvocation`), sets `MODEL`, `EFFORT`, `controllerTickMs`, `memoryGateDiscardPercent`, `channelLogRetentionDays`, `COORDINATOR_PERSONA`, `ARCHITECT_PERSONA`, `LIAISON_PERSONA`, `FLEET_ROSTER`, `JEV_MODE` and `JEV_LIVE` where the entry carries them, `JEV_LIVE` taking the entry's array of question-set ids joined with commas, and launches `bash <repo>/bin/supervise.sh <workdir> <name> <permissionMode> [--rundir ...] [--channel-name ...] [args...]` with the repository root as the working directory. Before that launch, and before every relaunch, it reads the process list for a supervisor already running for this persona (`Open-KeeperLiveSupervisor`, which hands the records to `Find-KeeperLiveSupervisor`), and where one is running it logs `ADOPT pid=<pid>` and waits on that process instead.
6. The supervisor checks its settings, then reads any handle a prior supervisor left behind and adopts a live child under it where it can, or else gates on the persona being free in the commons store and the heartbeat file, removes the work directory's channel log files older than `channelLogRetentionDays` days, the highest-numbered segment excepted (README, Channel Log Retention), launches `bin/supervise-holder.sh | claude ... &` with no `disown` so the holder holds the child's stdin pipe open (the main loop's launch step, whose pipeline's last stage is `child_wrapper`), and polls it. The poll loop repeats the sweep once a day, and an adopted child's first poll sweeps. The child claims the persona, attaches to the Discord relay thread, and idles until a goal arrives.
7. When the supervisor exits, the wrapper appends a launched supervisor's stdout and stderr to `<rundir>/supervisor.out`, writes `keeper.json`, logs a `DECIDE` line, and either sleeps and relaunches, writes `keeper.hold` and exits 0, writes `keeper.park` and exits 0, or exits 0 with no marker.

## The keeper

### Files

- `bin/keeper-functions.ps1`: pure functions, dot-sourced by the wrapper and the probe. Nothing in it writes a file, sets an environment variable or launches a process. It holds the env allowlist (`$script:KeeperEnvAllowlist`, eight keys), the policy constants (base delay 300 s, cap 14400 s, reset uptime 3600 s, exit-1 hold count 3, exit-1 short uptime 60 s), `Get-KeeperDecision`, `Read-KeeperRoster`, `ConvertTo-BashPath`, `Build-SupervisorInvocation`, `Split-KeeperCommandLine`, `Find-KeeperLiveSupervisor` and `Read-KeeperEnvFile`.
- `bin/Start-Persona.ps1`: the wrapper the task runs. Parameters: `-Name` (required, checked in the body so a missing value fails rather than prompting under a task with no console), `-Roster` (default `D:/personas/fleet.json`), `-EnvFile` (default `D:/personas/keeper.env`), `-Release`, and `-DelayScale`, a multiplier on every relaunch sleep that exists for the unit test and that no task passes.
- `bin/Register-PersonaTasks.ps1`: builds one task definition per enabled roster entry and registers, updates, enables, disables, reports on or (under `-Prune`) unregisters tasks named `AgentPersona-*`.
- `bin/keeper-probe.ps1`: a recorder, never a gate. Run by hand or as a scratch task's action, it writes one `key=value` file naming the running user, the session id, the elevation state, the delivered `USERPROFILE`, `HOME`, `APPDATA`, `LOCALAPPDATA`, `TEMP`, `TMP` and `PATH`, then applies the env file through the shared allowlist and records the exit code and first output line of `bash --version`, `node --version` and `claude --version` through that bash. It exits 1 only when the out file could not be written.
- `bin/fleet.example.json`: a four-entry worked roster (`steward`, `architect`, `aios`, `dev`). It is an example rather than a copy of any machine's roster.
- `.kit/keeper-unit-test.mjs` and `.kit/keeper-register-test.mjs`: the two suites, both driving the real `powershell.exe` from node. The register suite shadows every Task Scheduler cmdlet inside the spawned PowerShell so nothing real is registered.

### Roster contract

The roster is a top-level JSON array. `Read-KeeperRoster` (`bin/keeper-functions.ps1:135-172`) returns the entry whose `name` matches, and throws, naming the roster path and the name, when the file cannot be read or parsed, no entry matches, the entry has no `enabled` field, `enabled` is not a JSON boolean, or `enabled` is false. `Build-SupervisorInvocation` (`:226-291`) throws when `name`, `workdir` or `permissionMode` is missing or blank, or when `args` carries `--prompt` or `--prompt=...`. `workdir` and `rundir` are converted to the bash spelling (`D:/x` becomes `/d/x`) because `bin/supervise.sh` treats a `--rundir` that does not start with `/` as relative. The wrapper's own files keep the Windows spelling.

`bin/Register-PersonaTasks.ps1` has a second roster reader, `Read-PersonaRoster` (`:127-187`), with its own rules: the top level must be an array, every entry needs `name` and a boolean `enabled`, names match `\A[A-Za-z0-9_][A-Za-z0-9_-]*\z`, and a name repeated once case is ignored is refused. It does not check `workdir` or `permissionMode`, so a roster the registration accepts can still fail at the wrapper on every launch. `docs/backlog.md` files that gap under "The registration script accepts a roster entry the wrapper cannot launch".

### Env file contract

`Read-KeeperEnvFile` (`bin/keeper-functions.ps1:452-472`) reads every `KEY=value` line as UTF-8, skips blank lines, `#` comments and lines with no `=` or an empty key, splits on the first `=`, trims both sides, strips one matching pair of outer double or single quotes from the value, and takes the last value for a repeated key. It returns every key, not only allowlisted ones, plus `Duplicates` and `Unquoted` lists. The allowlist is applied by the two callers. In the wrapper, a key outside the list is named on one `ENV ignored:` line; an allowlisted key whose value is empty or whitespace is named on an `ENV empty:` line and not applied, because `Set-Item env:` with an empty value removes the variable under Windows PowerShell 5.1 and keeps it under PowerShell 7; a repeated key is named on `ENV duplicate:`, a quote-stripped one on `ENV unquoted:`. `KEEPER_BASH_EXE` is returned to the caller and never exported. `KEEPER_PATH_PREPEND` is prepended to the process `PATH` with a semicolon.

When the env file is absent the wrapper logs `ENV missing:` and takes `KEEPER_BASH_EXE` from its own process environment if present (`bin/Start-Persona.ps1:664-678`). With neither source it exits 1 with `no bash executable`.

### The decision function

`Get-KeeperDecision` (`bin/keeper-functions.ps1:57-122`) takes the exit code, the uptime in seconds, the previous delay and the consecutive short exit-1 count, and returns `Action` (`hold`, `park`, `relaunch` or `exit`), `DelaySeconds`, `NextDelaySeconds`, `NextExit1Count` and one-line `Reason`. Before the row is applied, a previous delay below 300 is raised to 300 and an uptime of 3600 or more resets the ladder to 300.

| Exit | Action | Delay now | Ladder after |
|---|---|---|---|
| 0 | hold | 0 | unchanged |
| 6 | park | 0 | unchanged; exit-1 count resets to 0 |
| 1, uptime under 60 s, count reaches 3 | hold | 0 | unchanged |
| 1 otherwise | relaunch | 300 | unchanged; count increments only when uptime is under 60 s, else resets to 0 |
| 2 | relaunch | 300 | unchanged |
| 130, 143 | exit | 0 | unchanged |
| 3, 4, 5, any other | relaunch | current ladder | doubled, capped at 14400 |

A hold on exit 1 of a launched supervisor writes three lines to `keeper.hold`: the reason, the supervisor's last non-blank stderr line, and the path of `supervisor.out`. A hold on exit 0, and any hold an adopted supervisor ends in, writes the reason alone. A park writes `keeper.park` with the reason as its only line.

### The wrapper's run loop

Each launch (`Invoke-Supervisor`, `bin/Start-Persona.ps1:312-362`) starts bash with `Start-Process -PassThru -NoNewWindow`, redirecting stdout and stderr to two files named `supervisor.out.<pid>-<start time>.<launch>.stdout` and `.stderr` in the run directory. The wait is on the launched process alone, renewed every second, never on its descendants, so a supervisor that exits 5 and leaves a survivor is still read the moment it exits. After exit, both files are appended to `supervisor.out` (stdout first) with a share mode that tolerates a descendant still holding the write end, the stderr file's last non-blank line is read from its final 64 KB, and both files are removed. A file a survivor still holds is logged `CAPTURE held:` and swept by a later launch of the same wrapper incarnation (`Remove-KeeperCaptureLeftovers`); a pair another wrapper or an earlier incarnation left is never touched.

The loop then writes `keeper.json` (`persona`, `launchCount`, `lastStart`, `lastEnd`, `lastExitCode`, `currentDelay`, `holdReason`), logs `DECIDE exit=<n> uptime=<s> action=<a> delay=<d> reason=<r>`, and acts. A `hold` writes the marker and exits 0. A `park` writes `keeper.park` and exits 0, and `keeper.json`'s `holdReason` carries its reason as it does a hold's. An `exit` exits 0 with no marker. A `relaunch` sleeps `DelaySeconds * DelayScale` and loops.

### Logs and state under the run directory

- `keeper.log`: one UTF-8 line per event, each prefixed with a UTC ISO timestamp. Line families: `LAUNCH <n> <bash> <args>`, `ADOPT pid=<pid>`, `ADOPT skipped|failed|watching|ended ...`, `SCAN failed:`, `EXIT <n> code=<c> uptime=<s>`, `EXIT adopted pid=<pid> code=<c> uptime=<s>`, `DECIDE ...`, `HOLD <reason>`, `UNPARK <path>`, `RELEASE <path>` (one per marker removed) or `RELEASE none`, `ENV ignored:|empty:|duplicate:|unquoted:|failed:|missing:`, `CAPTURE failed:|held:`, `STATE failed:`, `ROTATE failed:`, `ERROR ...`. Rotation renames the log to `keeper.log.1` when it exceeds 5 MB, immediately before the append that would cross it.
- `keeper.json`: the last run's facts, rewritten whole after every supervisor exit.
- `keeper.hold`: present while the persona is held. Its first line is the reason the next start logs as `HOLD <reason>`.
- `keeper.park`: present while the persona is parked, its only line the reason. The next start removes it, logs `UNPARK <path>`, and launches. A start that finds `keeper.hold` beside it logs `HOLD` and leaves both.
- `supervisor.out`: the supervisor's own stdout and stderr, appended per launch, with no size cap.
- `keeper-refused.log`, beside the roster file rather than in the run directory: every refusal raised before the roster has named a run directory (a missing `-Name`, an unreadable roster, a run directory that could not be created), because a scheduled task gives stderr no console. The path is the roster's directory plus `keeper-refused.log`.

### Exit codes of the wrapper

0 when the policy said hold, park or exit, when `-Release` ran, or when a hold marker was already present at start. 1 on a fault of the wrapper's own: an unknown switch, a missing `-Name`, a roster or env file that cannot be read, a run directory that cannot be created, no bash executable, a `--prompt` in `args`, a launch that fails to start, a supervisor that reported no exit code, or a hold or park marker that could not be removed under `-Release`. A hold marker that could not be written still exits 0, logged as `ERROR`, because exiting 1 would have the scheduler relaunch within the minute a persona the policy just said to stop. A park marker that could not be written also exits 0, and one the start cannot remove is logged as `ERROR` and the start launches.

### Registration

`bin/Register-PersonaTasks.ps1` resolves `-RepoRoot` (default: the parent of its own directory), `-Roster` and `-EnvFile` to absolute canonical paths, reads and validates the roster, then calls `Register-PersonaTasks`. Without `-WhatIf` that function throws before any ScheduledTasks cmdlet when the session is not elevated. It reads the existing `AgentPersona-*` tasks at the scheduler root (`-TaskPath '\'`), treating a not-found query as an empty list and any other read failure as a refusal of the whole run. For each enabled entry it builds a definition (`Get-PersonaTaskDefinitions`, `:218-347`): action as above with `powershell.exe` pinned under `$env:SystemRoot\System32\WindowsPowerShell\v1.0`; trigger AtStartup with `-StartupDelay` on it (default `PT2M`); principal with the Password logon type at RunLevel Limited for `-User` (default: the current identity), the password read from `-Credential` at the write and refused there, naming the parameter, when it is missing or names another account; settings RestartCount 999, RestartInterval one minute, ExecutionTimeLimit zero, MultipleInstances IgnoreNew, StartWhenAvailable, AllowStartIfOnBatteries, DontStopIfGoingOnBatteries. The builder refuses a `-RepoRoot`, `-Roster`, `-EnvFile` or target script path carrying a double quote or ending in a path separator, a missing `bin/Start-Persona.ps1` under `-RepoRoot`, a missing env file, and an unusable `$env:SystemRoot`. Those checks run under `-WhatIf` too.

An existing task is updated with `Set-ScheduledTask`, a new one registered with `Register-ScheduledTask`, and either is then passed to `Enable-ScheduledTask`. `-Start` runs `Start-ScheduledTask` after each. A disabled entry's existing task is passed to `Disable-ScheduledTask`; one with no task is reported. A task with no roster entry is reported as an orphan and removed only under `-Prune` without `-WhatIf`. `-WhatIf` prints each definition's fields read back off the built CIM objects, says `would register`, `would update`, `would disable` or `would start`, and touches nothing.

The keeper reads no file permissions. No script reads an access control list, an owner or a writer set, and none refuses, warns or skips on such a reading. The roster, the env file and the repository tree are the operator's machine state and are trusted as such.

### Machine state outside the tree

- `D:/personas/fleet.json`: the real roster, and the one the keeper reads by default. It is the machine's own, so its entries need not match `bin/fleet.example.json`.
- `D:/personas/keeper.env`: the real env file, carrying all eight allowlisted keys at this machine's values.
- `D:/personas/<name>/`: one directory per roster persona, holding that persona's run directory. None of them holds a hand launcher, so each persona starts from its keeper task.
- The `AgentPersona-*` tasks, one per roster persona. `README.md` holds the cutover steps, under the heading on cutting over to a roster that renames or retires a persona.
- `docs/security-model.md` states why the keeper trusts these files as the operator's own, and which files let a local process take over a persona.

## The fleet reading

One persona reports the fleet's health, and the plugin rather than the persona does the reading. The persona is whichever one the `coordinatorPersona` setting names, `steward` in `bin/fleet.example.json`, and the reading runs only where the `fleetRoster` setting also names a roster. On every controller tick that persona's plugin parses the roster, reads each entry's `keeper.json`, `keeper.hold` and `keeper.park` from that entry's run directory, and reads each persona's commons entry for the claim and the heartbeat age. It reduces each row to one of five health classes: held, backing off, stale, no live claim while the roster enables it, and healthy.

The comparison state is what keeps the report quiet. The tick holds the last reported class per key in session memory (`sess.fleetHealth`), writes it to no file, and submits a turn labelled `[FLEET]` carrying only the keys that moved, at most one line per key per ten minutes. A persona the steward watches can write that persona's own store, so a reading read back from a file would let a watched persona decide the steward's silence about itself. The same tick submits a `[RECONCILE]` turn every `reconcileEveryMs`, four hours by default, which is the kit Coordinator seat's reconciliation cadence and the only trigger for that pass. `README.md` under The fleet wake states the watcher whole, and `fleet_status` is the on-demand read of the same rows.

Both settings reach the child through `<rundir>/settings.json`. The supervisor emits that file from `COORDINATOR_PERSONA` and `FLEET_ROSTER`, and the keeper sets both from the roster entry's `coordinatorPersona` and `fleetRoster` fields. The supervisor writes the file only where none exists, so a roster edit repointing either one reaches nothing until the stale file is deleted. `README.md` holds the cutover steps that cover it.

The seats themselves are instruction text the supervisor writes at priming. A launch whose persona equals `coordinatorPersona` gets the coordinator role instruction, which carries the fleet duty, the kit Coordinator seat and the design-escalation clause. A launch whose persona equals `architectPersona` gets the architect's charter instead: design work only, worktrees cut under its own directory, and a plan handed back through the coordinator persona. Each plan branch it pushes gets a draft pull request that it never marks ready or merges, and a plan it drops is abandoned with the coordinator persona told first. It holds no standing goal of its own but one goal-tree entry per plan it is writing, which the controller tick nudges while it is active. That entry carries a `planPath`, since the plugin judges a plan entry by its plan path (`isPlanEntry` in `hooks/index.ts`), and it closes with `goal_done` when the draft's number is reported or the plan is abandoned. Completing its last open entry finishes its tree's root, and the supervisor answers that `root_complete` with a passive relaunch that keeps the tree (the `root_complete` row in `bin/supervise-decide.mjs`). A worker's own design record is answered to that worker directly, before the architect resolves it, while a plan still reaches the worker's queue only through the coordinator persona. Where the plugin refuses that direct answer, the architect sends it to the coordinator persona instead, naming the worker's persona and quoting that worker's record id, and the coordinator relays it to that worker as a coordinator record that says it relays the architect's answer and carries no coordinator steer, so the worker uses it as that answer within its own plan. A worker cannot read fleet state, so where two `agentic_inbox` reads at the architect at least five minutes apart both show its record `pending` with no `deferred` flag, it sends the question to the coordinator as an escalation quoting that record id, since a live architect takes a waiting record at its next quiet controller tick or as its running turn ends, and the record most likely has no live architect behind it or sits behind a long queue. That launch is also one of the two that take neither the skill-load sentence nor the coordinator steer sentence: both are cleared to the empty string for it (the architect-launch branch that clears `SKILL_LOAD_INSTRUCTION` and `COORDINATOR_STEER_INSTRUCTION` in `bin/supervise-holder.sh`), because the charter already states which skills a design ask takes and what it does with a coordinator record. `architectPersona` has no default, so a fleet that names no architect builds that charter for nobody and the escalation clause for nobody. The plugin reads `architectPersona` as well, for its inbox gates: any named persona owner may address the architect, and the architect may answer a persona whose owner's record to it is delivered or answered. The answer carries the id of that record, and delivery honours it while the writer still owns the architect persona, so an answer sent while the record is open is delivered even if the architect resolves the record afterwards. A value of `default`, or one equal to the coordinator's name, reads there as no architect. Each session reads the key from its own `<rundir>/settings.json`, so both ends of a line need it. A worker's send is judged against the worker's own setting, and a delivery is judged against the receiving session's setting. So a worker whose own settings file names no architect is refused at send, gets none of the steer instruction's architect sentences, and has any answer addressed to it skipped at delivery. In `bin/fleet.example.json` only the steward and architect entries carry `architectPersona`, so a fleet copied from it gives its two workers no line to the architect. A launch whose persona equals `liaisonPersona` gets the liaison's charter instead, `LIAISON_ROLE_INSTRUCTION`, spliced after the architect's. It splices the names `ARCHITECT_PERSONA` and `COORDINATOR_PERSONA` carry into its two `agentic_say` sentences, and `README.md` under "Launch the liaison" states its clauses. That launch is the other one that takes neither the skill-load sentence nor the steer sentence, both cleared in the liaison-launch branch of `bin/supervise-holder.sh`, since the seat executes no plan and holds no goal node a steer could tie to. `liaisonPersona` has no default, and a settings file naming a liaison and no architect refuses the launch on both settings branches, so the charter always has an architect to brief. Where the coordinator's own settings name a liaison, its role instruction gains one clause: a `[WORKER:<liaison> id=<record id>]` record asking for status is answered in a record with the fleet's state, and its `fleet_status` read is a case the fleet duty admits. The plugin reads no liaison key. The liaison sends as a named persona on the worker ground and is reached as one, and `bin/fleet.example.json` carries no liaison entry.

Which class a fleet row takes, the order the five are tried in, and how the two words they share with a row's own `action` field behave are stated once, in the `fleet_status` tool description, the `registerTool("fleet_status"` call in `hooks/index.ts`. The `[FLEET]` prompt frame and `README.md` point there rather than restating it, because a session calling the tool holds that description and holds no file in this repository.

That description states the rules a caller acts on and leaves the reasons here, because the engine refuses a tool description over 4,096 characters. `session.start` registers each tool through one guard, so a refused registration costs the session that tool alone and leaves one `tool_register_refused` decision, while the persona claim, the store load and the heartbeat still run. `.kit/tool-description-length-test.mjs` holds every registered description to 4,000, so the guard is a backstop rather than the bound.

### Why a row's keeper standing reads as it does

`keeper.json` is written after a supervisor exit and never at a launch. Three of the description's rules follow from that one fact.

- A live claim under no hold or park marker reads `running` whatever the file records, because the file describes the exit before this session and not the session itself. A `running` row therefore carries no keeper standing in its `action`, and `nextDelaySeconds` and `note` are where one reads from.
- A signalled exit and a live claim together are settled on the clock. A claim last seen before that exit is the session that took the signal, so the row reads `stopped`. A claim last seen after it is a session that started since, so the row reads `running`. Where the exit carries no timestamp that can be read, the claim decides, the row reads `running`, and its note says the exit could not be placed against the claim.
- The file records the next rung of the keeper's delay ladder and no timer. `nextDelaySeconds` is therefore the delay the keeper applies after the persona's next crash, and how long a persona waiting to relaunch has left cannot be read from the row.

### Two vocabularies over one row

A row's `action` and its health class are two vocabularies. `action` is the keeper standing alone. The five health classes are a second vocabulary, derived from the row's fields, naming a whole row in one reading, and they are what a `[FLEET]` prompt's lines carry.

`stale` has three grounds. The first is tried second in the order: the action reads `stopped` and a live session holds the claim. The other two come out of what is left once the first four classes have been tried: a commons entry still standing for a persona the roster disables and nothing live holds, and a live claim whose row carries any note but an unwritten `keeper.json`.

`backing off` is read before `no live claim while the roster enables it` and before that remainder, so a row with no live claim whose delay has climbed reads `backing off` rather than either of them.

`held` means the same in both vocabularies, a hold marker or a park marker being what sets it either way. A hold marker stops the next start, and a park marker is cleared by it so the persona launches. `holdReasonSource` names the marker file the reason came from, and `holdReason` carries the keeper's own reason, which names a park. Where the marker's first line is blank, both fall back to `keeper.json` for either marker. `backing off` does not. Once a claim is live the action reads `running` for every keeper standing but `held`, and but a stop the clock settles against the claim, while the health class still reads `nextDelaySeconds` against the base. So a row whose action reads `running` carries the `backing off` class wherever that delay has climbed.

## Stopping and parking a persona

A persona's own tool takes it down in one of two ways, and they differ in whether it comes back by itself. A stop keeps it down until someone releases it by hand. A park keeps it down only until the keeper's next start, so an update window closes with the fleet it opened with. Both begin at `supervisor_shutdown` and differ in one fact the child writes, which every layer above carries as its own distinct value.

| Step | What does a stop produce? | What does a park produce? |
|---|---|---|
| The call | `supervisor_shutdown` | `supervisor_shutdown` with `park: true` |
| The decision in the persona store | `shutdown_requested` | `park_requested` |
| The decide unit's action | `stop_complete` | `stop_park` |
| The supervisor's exit code | 0 | 6 |
| The keeper's action | `hold` | `park` |
| The marker in the run directory | `keeper.hold` | `keeper.park` |
| The next keeper start | logs `HOLD` and launches nothing | removes the marker, logs `UNPARK <path>` and launches |
| The fleet reading's `action` | `held` | `held` |

**The tool.** The handler (`hooks/index.ts:9926-9952`) reads `park` as true where the argument is the boolean `true` or the string `"true"`, because arguments can arrive stringified. Any other value is a stop. It pushes one decision with the reason as its detail, defaulting to `operator requested park` or `operator requested shutdown`, and writes the store through `persist`. A session that does not own the persona is refused and writes nothing. A persist that fails answers with the same refusal text, and the decision stays in session memory, which `docs/backlog.md` files under "A refused persist leaves the shutdown or park decision in memory". The tool's own description is where a persona learns when to park. No instruction text `bin/supervise-holder.sh` writes at priming names the park.

**The supervisor.** The poll reads the newest `park_requested` beside `shutdown_requested` (`readStoreFacts` in `bin/supervise-poll.mjs`). The decide unit returns `stop_park` for one newer than the child's start. It sits below `stop_complete`, so a shutdown and a park both in force end in exit 0. It sits above the restart request, so a park outranks a restart. The decide path stops the child as `stop_complete` does and exits 6 at the poll loop's `stop_park)` case. The natural-exit path reads the park directly after the shutdown, sweeps under the label `park`, and exits 6 at its own park check. On either path a process left alive, or a tree that could not be read, ends the run at exit 5, which the keeper relaunches after its delay. The shutdown's natural-exit branch differs there: it exits 0 whatever its sweep found.

**The keeper.** `Get-KeeperDecision` returns `park` for exit 6, with no delay, the ladder unchanged and the exit-1 count reset (`bin/keeper-functions.ps1:75-80`). The wrapper writes `keeper.park` with the reason as its only line, writes the same reason into `keeper.json`'s `holdReason`, and exits 0 (`bin/Start-Persona.ps1:774-787`). At start it checks `keeper.hold` first, so a hold always wins and both files stay in place (`:638-650`). A park marker alone is removed and the start goes on (`:652-662`). That removal runs before the env file is read and before the supervisor's arguments are built. So a start that then fails on a fault of the wrapper's own has already cleared the park, and the persona launches at whichever later start gets past that fault. `-Release` removes the hold marker and then the park marker (`:620-636`).

**The fleet reading.** `readKeeperHalf` checks `keeper.park` only where the hold check found no marker (`hooks/index.ts:2015-2034`). A hold marker already decides the row, and a hold check that threw already decides it as `unknown`. Either marker makes the standing `held`, even beside a live claim. The reason comes from the marker in force, and falls back to `keeper.json`'s `holdReason` where that marker's first line is blank.

A supervisor started by hand rather than by a keeper still exits 6 on a park. Nothing relaunches it, as nothing relaunches its exit 0.

## Interrupting a persona's turn

The coordinator persona can end another persona's running turn without stopping its child, so that persona keeps its conversation. The request crosses three processes, and each one checks it before passing it on. No layer sends an interrupt on its own initiative.

| Step | Who acts? | What does it read? | What does it write? |
|---|---|---|---|
| The call | the coordinator's plugin, `fleet_interrupt` | the roster entry for the target persona | `<rundir>/interrupt.request`, `{ at, by, reason }`, in one write |
| The relay decision | the target's supervisor, on every poll of a running child | that file, `child-N/interrupt.served` and the child's own `heartbeat.json` | `child-N/interrupt.request`, `{ id, at, by, reason }`, by write and rename, then `interrupt.served` and one `supervisor.log` line |
| The control line | the holder, on every holder poll | `child-N/interrupt.request`, taken by renaming it to `interrupt.request.taken` | one stream-json `control_request` of subtype `interrupt` on the child's stdin, carrying only the id |
| The turn's end | the `claude` child | its stdin | a `result` of subtype `error_during_execution`, with the conversation kept |

**The tool.** The `fleet_interrupt` handler in `hooks/index.ts` checks `fleet_restart`'s gates in the same order: the coordinator ground, a readable roster, an enabled entry, a persona other than the caller's own, and an existing run directory. Each refusal writes nothing. It has no fifteen-minute refusal, because the supervisor's served record already makes one request send one interrupt. The reason is trimmed and cut at 200 characters, the bound `FLEET_RESTART_REASON_MAX` sets for both tools. Nothing removes the file once it is served.

**The supervisor.** `relay_interrupt_request` in `bin/supervise.sh` runs on every poll of a running child, launched or adopted, right after `run_child_poll`. It reads the request through `bin/supervise-interrupt-request.mjs`, which applies the restart reader's rules for what counts as no request. It acts only on a request newer than the child's start and newer than `interrupt.served`, and only once the child's session id is recorded. It then reads `turnStartedAt` through `readChildHeartbeat` in `bin/supervise-heartbeat.mjs`, the same reader the liveness verdict imports. A turn that started at or before the request's `at` is the one the coordinator meant, so the request is relayed under the id `<supervisor start ms>-int-<n>` and logged `INTERRUPT:`. No running turn, or a turn that started later, records the request served and logs `INTERRUPT_SKIPPED:`. A heartbeat read that fails outright leaves the request standing for the next poll.

**The holder.** `bin/supervise-holder.sh` takes the child-directory file as its sixth argument. On each poll it checks that file before the pending goal write and before the ask file. It renames the file, reads at most 4,097 bytes and refuses anything over 4,096. A valid file holds exactly the keys `id`, `at`, `by` and `reason`, with an id matching `^[A-Za-z0-9-]{1,64}$`. The holder builds the control line itself, so nothing from the file but the checked id reaches the child. It logs the relay or the refusal to `supervisor.err` and removes the taken file either way.

**Timing and boundaries.** The relay lands up to one supervisor poll plus one holder poll after the call, about 12 seconds at the default 10-second and 2-second polls. The child writes its heartbeat once per `heartbeatMs`, 30 seconds by default, so the turn reading lags by up to one interval at both ends. A request made in about the first interval of a turn is skipped, and one made just after a turn ends can still land on the turn after it. A served-marker write that fails is retried alone from the supervisor's in-memory record. A successor supervisor that adopts the child before that marker lands can act on the request once more. A holder launched by a supervisor that predates this path takes five arguments and watches no interrupt file, so its child is not interrupted until its next launch. Because the run-directory file stays in place, every later poll spawns `node` to read it, which `docs/backlog.md` files under the supervisor interrupt finishing pass.

The coordinator's role instruction, `COORDINATOR_ROLE_INSTRUCTION` in `bin/supervise-holder.sh`, names when to use the tool. The trigger is a `fleet_status` row with `turnState` `in turn` and a `turnRunningMs` far past what the turn's work needs, or a persona the operator names. To break in with something critical, the coordinator calls `fleet_interrupt` and then sends the record with `agentic_say`, which arrives as that persona's next prompt. `README.md` under Poll Loop and under `fleet_interrupt` is the operator-facing reference.

## The own-record self-review

Before the plugin asks the model for a self-review lesson, it reads the persona's own record for a repeated weakness. `reviewOwnRecord` in `hooks/self-review.ts` counts four signals from data the plugin already keeps. The self-review block of the controller tick in `hooks/index.ts` acts on what it returns. The pass runs on the self-review's own trigger, a reactive error streak or the periodic cadence, and only a pass that yields no finding goes on to the model lesson.

| Signal | What counts as one event? | What does a finding do? |
|---|---|---|
| `asks_unresolved` | an `ask_timeout` or `ask_reraised` decision | sends a `[FINDING]` record to the coordinator persona |
| `memory_quality` | a `memory_lesson_refused` decision, or a self-review lesson whose first six normalized words match another lesson's | sends a `[FINDING]` record to the coordinator persona |
| `message_wait` | an inbox record delivered `KAIZEN_MESSAGE_WAIT_MS` (10 minutes) or more after it was sent | sends a `[FINDING]` record to the coordinator persona |
| `long_turns` | a `turn_over_hour` decision, which `turn.complete` records for a turn of `KAIZEN_LONG_TURN_MS` (60 minutes) or longer | halves `selfReviewEveryTurns` and sends the change as a `[FINDING]` record |

A signal yields a finding when it holds at least `KAIZEN_REPEAT_MIN` (2) events newer than that signal's last send, read from the finder's own ledger, `monitor.selfReview.sent`. Where the signal has never been sent, every event counts. A signal that was sent stays quiet for `FINDING_COOLOFF_MS`, seven days, counted from the send.

The three signals other than `long_turns` each become a `[FINDING]` record to the coordinator persona, opening with `[FINDING] <persona> <signal> x<count>` and carrying the finding's objective, whose last sentence is a `Proof:` line. `sendPluginRecord` in `hooks/operator.ts` writes it, and the tick logs `finding_sent`. Where no coordinator persona can be reached, the finder announces the finding on its own thread instead, through a `[KAIZEN]` line, and logs `finding_unroutable`.

`long_turns` also carries a configuration change. The new cadence is `max(selfReviewDebounceTurns, floor(selfReviewEveryTurns / 2))`, and the finding is built only where that value is below the current cadence. The tick sets the cadence and logs `kaizen_config_adjusted` with the old and new values. Once the cadence sits at the floor, the signal yields no finding and the review falls through to the model lesson. A second halving needs two fresh `turn_over_hour` events, counted only from after the signal's last send, and the seven-day cool-off has to pass since that send. All of that has to happen inside one process's lifetime, because the halved cadence lives in process memory and a relaunch returns it to the configured default.

Any finding spends the review. The tick sends each finding to the coordinator persona as described above, then logs a `self-review` decision reading `own record -> <n> finding(s), no lesson`. No model lesson is written on that pass.

### Boundaries of the self-review

- A signal's cool-off runs from its last send, read from the finder's own ledger, `monitor.selfReview.sent`, for `FINDING_COOLOFF_MS`, seven days. Only `turn_over_hour` decisions timestamped after that send count toward the next `long_turns` finding. The halved cadence lives in process memory. A relaunch returns it to the configured `selfReviewEveryTurns`. The ledger survives the relaunch, so the next halving, from that value, still waits out the cool-off since the last send and needs two `turn_over_hour` events after it.
- A store can hold an open node whose `kaizenSignal` field names a signal an earlier self-review wrote a goal node for, `tree_lag` and `long_turns` among them. The field is typed as a string, so the store loads any such value. A routing step ahead of every review reads any open node carrying a `kaizenSignal` string, whatever the value, and sets it abandoned. It then sends the node as a finding, to the coordinator persona where one can be reached, or announces it on the persona's own thread otherwise, either way logging `kaizen_node_routed`. That send starts the seven-day cool-off on the node's signal, the same as an ordinary finding, which is what keeps the signal quiet once the node is routed.
- A review that throws counts as an attempt. Once the eligibility check admits a review, and before the review's first await, the block stamps the attempt on `monitor.selfReview`. It adds one to `count`, sets `windowStart` where it is zero, sets `lastAt` to now, and resets `turnsSince` to 0 and `pendingPeriodic` to false. So `selfReviewDebounceTurns` and `selfReviewMaxPerHour` bound a review that keeps failing exactly as they bound one that succeeds. The stamp comes first because the tick timer does not wait for a tick to finish. A tick that overlaps a slow review must read that review as spent. A failed attempt that was owed to a `goal_done` sets `pendingPeriodic` again, so it is retried once the debounce admits it rather than waiting for `selfReviewEveryTurns`. A failed attempt with only the reactive trigger sets nothing. Under the defaults a review that always fails makes at most two attempts in each hourly window.
- A failed attempt writes one `self-review` decision reading `<trigger>: error: <message>`. The message is the thrown error's message with square brackets turned to parentheses. Where that is empty, the error's name stands in, and where neither can be read the message is `unprintable error`. It is folded to one line on every line terminator and cut at 200 characters. The block catches the throw itself, so this decision is the only record of it and the tick's outer catch never logs it.

`selfReviewEveryTurns` (default 20), `selfReviewDebounceTurns` (default 5) and `selfReviewMaxPerHour` (default 2) arrive through the settings file's plugin options. `.kit/self-review-unit-test.mjs` pins the finder under its Test 12 cases. `.kit/controller-tick-test.mjs` pins the tick's handling under its `item8.4` cases, and its handling of a failed or overlapped review under its `caseCatchStampsAttempt_` cases.

## The goal tools' turn-origin gate

The gate's act list in `hooks/index.ts` names five acts. Three start a new effort: `goal_create`, `goal_add` where the resolved kind is `plan`, and `goal_longterm`, for both its `add` and its `drop`. One ends an effort: `goal_done` with the root's own `nodeId`, which completes a finished root. One settles a wait: `goal_resume` on an entry awaiting the operator's yes, or on a node under one. One helper, `turnMayStartEffort`, decides whether the turn now running may take one of the five. For these acts a priming turn is refused outright, except the plan add at the two wider autonomy levels below. A turn that matched an expected turn is admitted only where that entry is a delivery under the `COORDINATOR` ground whose record opens with none of `[FINDING]`, `[PROPOSAL]` and `[STARTED]`. Any other turn is admitted only where its prompt's origin kind is one of `composer`, `bridge`, `channel` or `sdk`. A `channel` prompt is admitted only where the envelope's opening tag names the sender class exactly `operator` or names none, as `channelSenderOf` in `hooks/index.ts` reads it. Any other class value, `participant` included, is refused like a turn with no operator origin. `turn.start` copies the class and the author from the prompt's origin reading onto the current turn, and a root `goal_create` builds in a channel turn records that author as `askedBy`, cut to `ASKED_BY_MAX_CHARS` (64). `README.md` under "Findings, proposals and long-term goals" states the class rule whole. The refusal text tells the caller to retry an act the operator or the coordinator persona directed in a turn one of them opens. Any other idea goes to the coordinator persona with `agentic_say`, the text opening with `[PROPOSAL]`.

The autonomy level reaches one act, `goal_add` of a plan. The level is the `autonomy` field in the persona's store, one of `propose`, `plan-and-ask` and `plan-and-start`, and a store without it reads `propose`. Only `goal_autonomy` sets it, and only in the operator's own turn. That tool's check has no coordinator branch. At `propose` the gate decides the plan add as it decides the other four acts. At `plan-and-ask` it admits the add in every turn. In a turn neither the operator nor the coordinator persona opened, the handler then creates the entry `paused`, with the reason `Awaiting the operator's yes` and the `awaitingYes` flag, and sends the coordinator persona one `[PROPOSAL]` record naming the entry through `sendPluginRecord`. At `plan-and-start` it also admits the add in every turn. In such a turn the entry is created `pending`, made `active` in the same turn where nothing else is active and no ask to the operator is open, and one `[STARTED]` record goes to the coordinator persona. Either record is sent only after the entry is saved. Before anything is written, such an add is refused where the session runs on the `default` persona or the reach rule refuses its write to the coordinator persona. A record the coordinator persona's inbox skips is sent again on a later quiet tick, while its entry still waits for the yes or is still open. It is sent again at most three times. Where the coordinator persona cannot be reached when a resend is due, or the record is skipped after its third resend, the record is announced on the persona's own thread instead, through a `[KAIZEN]` line. Where the record cannot be written, the add is refused and the entry is taken back out. Where that removal cannot be saved either, the refusal says the entry may remain in the store. In the operator's or the coordinator persona's own turn the add behaves the same at every level and sends no record.

The plugin performs that same add itself, through the same function and with no tool call, where a turn edited a plan document. That is route one under "The turn record" below. It runs at the persona's own turn end, at `plan-and-ask` and `plan-and-start` only, and it writes the paused-awaiting-yes shape and the `[PROPOSAL]` or `[STARTED]` record exactly as the handler does, because both call `addGoalEntry`. So the level's act list is one act reached two ways rather than one, and the gate's turn-origin steps stand in front of only the handler's. Route one announces at both live levels whatever the turn's origin, the operator's own turn included, because the add is the plugin's own act rather than a request the model made. A coordinator session that edits a plan document therefore writes the record into its own inbox.

Two refusals sit outside the act list. `goal_edit`'s `drop` of an entry awaiting the operator's yes, and `goal_done` by name on such an entry or on a node under one, are refused outside a turn the operator or the coordinator persona started. An allowed resume, drop or completion clears the wait. A `goal_resume` with no `nodeId` outside those turns picks only among paused entries that neither await the operator's yes nor sit under an entry that does, so an older paused entry stays resumable beside an awaiting one. Every other goal tool works inside what the persona already holds and is never gated.

## The task list

The task list is the lightest of a persona's four tracking tiers. It sits below the goal tree, and the long-term goals sit beside the tree. A task-list item is a note the persona keeps under the active goal. Unlike a goal tree's task-kind leaf, nothing activates, scores or schedules it.

It is the persona store's `tasks` field, an array of `TaskItem` records (`hooks/agent-state.ts`). Each record carries an id from `newTaskId`, the `goalId` it was added under, its text, `done` and `addedAt`. A done record also carries `doneAt`. A store at version 2 through 6 loads at version 7, seeded with an empty list where it held none. The step to version 6 seeds the turn record list beside it, and the step to version 7 seeds the list of memory records shown per goal. A malformed entry is dropped whole at load.

The list is per goal. The three verbs `task_add`, `task_done` and `task_clear` in `hooks/index.ts` act only on the entries whose `goalId` is the active goal, and each refuses when no goal is active. A reader session does not register them. None of them passes through `turnMayStartEffort`, because the list is the persona's own.

A plan entry keeps its own tracker. Where the active goal or an ancestor carries a `planPath`, the plan document's Chapters are the task list. `task_add` refuses there, and the block is not injected, both by the same `planHolderOf` test.

A goal's completion reaps its tasks. `reapCompletedGoalTasks` drops every entry whose goal is complete, abandoned or absent from the tree. `persist` calls it before each write, and `enforceInvariants` calls it on each load. So every path that closes a goal clears that goal's list without the path knowing the list exists. The authority does not run the other way: all tasks done produces a suggestion to call `goal_done` and never a completion.

`taskListBlock` in `hooks/index.ts` is the one producer of the `[TASK LIST]` block. The `prompt.submit` hook pushes it into `contextBlocks` right after `[GOAL TREE]`, inside the same active-node branch. It does so only when `planHolderOf` finds no plan entry and the active goal holds at least one entry. `taskListBlock` shows up to `TASK_LIST_MAX_LINES` item lines and counts the rest. It has no length budget against the `[GOAL TREE]` block. The plugin's own `$.prompt.submit` calls bypass that hook, so a nudge or delivery turn carries no block. The reader guard returns before `contextBlocks` exists, so a reader session never builds it.

Every id and text is sliced to `TASK_ID_MAX_CHARS` or `TASK_TEXT_MAX_CHARS`, folded to one line, then passed through `bracketSafeText`. That is the guard the `[PROPOSE]` frame applies to a long-term goal's text. The injection ledger sizes the block as `TASK_LIST_BLOCK`, reading every literal in `taskListBlock`'s body.

## The turn record

A turn record is how the plugin holds an external message before the model reads it. It is the fourth tracking tier, and the one the plugin opens for itself on every message: the goal tree holds the operator's work, the task list holds the persona's own notes under the active goal, the long-term goals sit beside the tree, and a record is one message the persona has not answered yet. The plugin writes into the goal tree without a tool call too, on route one below, but only where a turn edited a plan document. Nothing activates, scores, schedules or nudges a record, because nothing that reads `goals` can see it. That is what lets a one-turn request be tracked without leaving an entry the controller nudges after the answer was given.

It is the persona store's `turnRecords` field, an array of `TurnRecord` values (`hooks/agent-state.ts`). Each record carries an id, its text, `openedAt`, and a `status` from the closed set `TURN_RECORD_STATUSES`: `open`, `delivered`, `superseded`, `expired` and `promoted`. It optionally carries the `turnId` its turn's start stamped, the `goalId` it was attached to, a `planPath`, a `taskId`, `closedAt`, and the journal stamps each of its two questions is still waiting on, one list per question. A malformed record is dropped whole at load.

The stored text is already safe to print. `clampTurnRecordText` cuts it to `TURN_RECORD_TEXT_MAX` (80 characters), folds it to one line and rewrites its square brackets. Every producer of the field calls that one clamp, and so does the load, so no reader owes the guard a second time. The prints fold each field they splice all the same, because the goal-tree fields beside a record carry titles the model wrote.

At most one record is open at a time. `openTurnRecord` returns that one or null, and `enforceInvariants` keeps the newest where a store carries two. `reapTurnRecords` expires an open record on any of three readings of its `openedAt`, which share one reason: none yields an age the timeout can act on. The age has reached `TURN_RECORD_TIMEOUT_MS` (24 hours), the boundary sitting on the expiring side. The value is not a finite number. Or it sits ahead of the clock, which yields a negative age no timeout ever passes. The reap also drops closed records past `TURN_RECORDS_MAX` (20) in ascending `openedAt` order; it never drops an open one. `persist` calls it before each write and `enforceInvariants` on each load, and the record step calls it again before reading the open slot, since reading first would carry over a record that the same step's own write then expires. `goal_status` prints an open record as one `Turn record: <status> <text>` line above the tree, and prints no such line where none is open.

### What opens a record

The real `prompt.submit` hook opens records, and it fires only for a genuine external turn. The plugin's own submits, its nudges, its record deliveries and the daily proposal turn bypass that hook, so the step sees only the messages that arrive as a turn of their own: the operator's, from the keyboard or the thread, a peer session's, which the harness delivers through that same hook, and the harness's own. A coordinator persona's message arrives through the inbox drain, which is one of those plugin submits, so no record is held for it. It runs on the owner session alone.

Fixed rules run first and each decides without the classifier. A reader-armed session opens nothing, and neither does a session that does not hold the persona claim. A priming turn and a `[SUPERVISOR-ASK` status check open nothing. A turn whose prompt closed an open ask is the answer to that ask: it opens one record attached to the asked entry, supersedes any open record, and asks no question. The handler closes the ask on that same prompt only where the prompt carries one of the operator's origin kinds and a sender class other than `participant`, so a participant's message while an ask is open goes to the question below like any other.

What the rules leave goes to the `turn-open` question through `liveAsk`, over the arriving message's first 1,200 characters, the active entry's objective and the open record's text. Live, a `new-goal` verdict supersedes the open record and opens one whose text Haiku words in a line; a `step` verdict opens one attached to the active entry; a `continuation` verdict keeps the open record, whose text stands because a follow-up adds to the same request. Not live, and on every failure, the fallback is continue, then attach, then open bare: where a record is open it continues, else a record attached to the active entry where one is active, else a bare record carrying the message's own excerpt. The fallback never opens a goal. Each act logs one decision, `turn_record_opened`, `turn_record_attached`, `turn_record_continued` or `turn_record_superseded`.

### What closes a record

The `turn.complete` hook closes records, under the same true-boundary guard the compaction bank uses: the completing id is the one `turn.start` carried, no subagent id rides the completion, no turn is open once this completion's own entry is gone, this session holds the persona, and the turn was not skipped. A record is never deleted here. It changes status and gains `closedAt`, and the cap is the reap's alone.

Fixed rules run first here too, and each leaves the record open and in flight, logging one `turn_record_in_flight` decision that names itself. A closing text whose first line is a `BLOCKED:` or `WAITING:` lead is one. An ask open at the turn's end is another. A background agent the main loop started and still running, read from `$.agent.list()` as any agent that is running and carries no parent id, is the third. The agent list is read only once the first two have declined, since those two are facts already in hand and the list is a host call with a suspension of its own.

What the rules leave is the delivered-versus-mid-work residue, and it goes to the `turn-disposition` question through `liveAsk` over four fields: the active entry's objective, what the turn was asked, the persona's own closing message, and the turn's tool activity. The objective is the entry active at the turn's start, the one the turn served, because the scorer above this step can have completed that entry and activated the next. Live, the record reads `delivered` with a `closedAt` where the answer's probability for `delivered` is at least `TURN_DELIVERED_THRESHOLD` (one half), the equal case included, and stays open below it. Not live, and on every failure, the fallback is not delivered, which keeps the record open and costs nothing, since a record is never nudged. So with the live list empty `delivered` is unreachable, and the closes a record does reach are `superseded`, `promoted` and the reap's `expired`.

The turn's tool activity is the plugin's own view rather than the model's account of it. `tool.call` keeps a ring of the last eight tool names, seven flags and a work-tool count, all reset at `turn.start`. The flags are a plan document read, a plan document edited, a commit, a push, an agent dispatched, `goal_done` called and the reply tool called; the count is the work tools the turn used. A commit or a push is read from a `Bash` call whose command text carries `git commit` or `git push`, which is a read of the argument and never a run of it.

### Promotion into the goal tree

Three routes turn a record into real work, and the plugin drives one of them. No route opens a goal tree from a message; only the operator or the coordinator persona opens a tree.

Route one promotes on plan activity. At the true turn boundary, above the close so that a plan-touching record is promoted rather than closed, where the open record carries no `goalId` and this turn wrote or edited a file whose path matches `PLAN_PATH_PATTERN` once made relative to the session's working directory, the record takes that path. A read of a plan document does not count, and the architect persona the settings name never takes this route, because it authors plan documents for other workers by charter. Then the autonomy level decides. At `propose` nothing else happens, the standing block already telling a persona how to propose. Where no goal tree exists the record keeps its path and no entry is added. Where a plan entry of the tree already carries that path, no second entry is added either; that reading is the tree's rather than the record log's, because a paused entry outlives the twenty closed records the log keeps. Each of those three leaves the record open with its path and logs one `turn_record_plan_noted` naming which reading held. At `plan-and-ask` and `plan-and-start` the entry is added through `addGoalEntry`, the same function the `goal_add` handler calls, and the record reads `promoted` with the entry's id. A refused add logs one `turn_record_promotion_refused` naming the cause and leaves the record open with its path, so the next boundary tries again.

Route two is the model's own tool call. A `goal_create` or `goal_add` made in a turn holding an open record marks that record `promoted` with the new node's id, and a `task_add` does the same with the task's id where the record is attached to the active entry.

Route three turns a task into a goal. `goal_add` takes an optional `taskId`, copies that task's text as the title where none is given, and drops the task from the list as part of the add's own write. An unknown id is refused.

### Records and compaction

An open record does not withhold the compaction bank. The durable-boundary predicate reads the turn's own signals: a skipped turn, a `BLOCKED:` or `WAITING:` lead, an ask open at the turn's end, a plan section left half-done, and a live background agent each make the turn not durable. An open record with no lead, no open ask and no live agent is idle, and idle is durable, so the plugin banks a boundary there. The three in-flight rules the close reads are the same three this predicate reads, and the two consult one reading of the agent list. `README.md` under Limitations states the bank's own mechanics.

### Going live

Both questions ship in shadow and are read by nothing until the operator names one. The live list is `jevLive`, a comma-separated string of question-set ids that is empty by default, and only the three ids in `PROMOTABLE_SET_IDS` may be named, which are `turn-open`, `turn-disposition` and `memory-kind`. `README.md` under "Memory gate" states what naming `memory-kind` does. A question the list does not name is journaled in shadow and its answer reaches no branch. What earns a question its place is the promotion bar under the plan's own Operator Verification: a labelling pass over the shadow journal, measured against the outcome the plugin observed for itself.

`turn-disposition` as worded does not meet a bar of that kind, and the measurement exists. Replayed against the operator's own dialog with three personas, on a gold set of 136 turns labelled from the operator's words alone with the reply withheld, 70 of them closed and 66 still open, it scores 0.582 balanced accuracy against 0.500 for a coin. Moving the threshold does not help, and the best composite tried afterwards reaches 0.598. The cause is the question's subject rather than its answer shape: answering the request and waiting on the operator are independent facts, so no single question about the reply can decide closure, and a turn that answered every part of what was asked can still be open because it handed a decision back. Do not promote `turn-disposition` as it stands. Replacing it means asking both facts rather than rewording one, and the replacement needs a fresh held-out pass, since the gold set behind this reading has been read.

## The memory step

The memory step decides at a turn's end whether the exchange holds a durable fact worth storing. It runs in the `turn.complete` handler of `hooks/index.ts`, after the plan-health shadow question, at every completion the handler receives, a subagent's included. `README.md` under "Memory (M1, M2)" and "Memory gate" is the operator-facing reference.

### Turns that make no memory call

Four readings stop the step before any call. The third logs one decision, and the other three log nothing.

- **A skipped turn.** A completion that is aborted, errored or refused, or that carries no answer, makes no call.
- **A turn the goal nudge opened.** `turn.start` sets a per-turn flag where the turn's text matched a queued nudge entry. Every completion that arrives while that turn is open reads the flag and makes no call, a subagent's completion inside the turn included. The turn's own completion clears the flag before the handler's first await, so a completion arriving after the nudged turn ended is read as not nudged. This holds with `memory-kind` live or not. A nudge whose text matches no queued entry is never flagged, and `docs/backlog.md` files that under "A goal nudge that matches no expected-turn entry still reaches the memory step".
- **A turn opened by a task notification.** Where the text `turn.start` recorded for the turn starts with the harness's `<task-notification>` block, leading whitespace aside, the step makes no seam call, no classify and no distill, whatever `jevLive` and `jevMode` say. It logs one `memory_skipped_task_notification` decision. The test reads the turn's own opening text, so a plugin delivery or a continuation that follows a notification turn is classified, and so is a prompt carrying the block anywhere but its start.
- **The goal-close check turn.** The `[MEMORY CHECK]` turn a goal's close queues asks for record names rather than work, so its own completion makes no call. Neither does the first completion to arrive while that turn is the current one, a subagent's included.

### Haiku, or Jev first

Every other completion is classified. Where `jevMode` is `shadow` and `jevLive` names `memory-kind`, the step first awaits `liveAsk` on the state it would give Haiku, bounded at `LIVE_TIMEOUT_MS` for the request. A `discard` probability that rounds to at least the floor on a `dev` stamp skips both Haiku calls and logs `memory_gate_skipped`. Any other answer, a holdout stamp's whatever its probability included, runs Haiku, logs `memory_gate_passed` and writes Haiku's label as a `haiku_kind` outcome against the live stamp. A failed live call runs Haiku and logs `memory_gate_fallback` with the reason. Neither the passed path nor the fallback makes a shadow call. Everywhere else the step classifies with Haiku, shadows Jev with Haiku's label, and never calls `liveAsk`.

A label other than `discard` goes on to Haiku's distill call. Where the session owns the persona and the answer is not empty or `NONE`, it is written to the kit's shared memory store as one record through `memq put`. A reader session's distilled fact is dropped unwritten. `README.md` under "Memory (M1, M2)" states the record's name, its tags, the decisions each write logs, and the read that later judges it. A throw anywhere in the step is caught and ends the step silently.

The floor is `memoryGateDiscardPercent`, read once at registration. An absent value, or one that is not a number, reads as 90 with no decision, and so does `NaN`. A number is rounded, and one that rounds outside 50 to 100 reads as 90 with one `setting_clamped` decision at `session.start`. The supervisor refuses a roster value outside that range at startup, so a clamp means the value reached the settings file by another path.

The state both classifiers read quotes `currentPrompt` as "User asked:". That is the last prompt the prompt hook saw, or the last nudge text the plugin sent, rather than the turn's own opening text. On a delivery, proposal or plugin turn it pairs an earlier prompt with this turn's answer, and `docs/backlog.md` files that under "The memory step's "User asked:" line is the last external prompt, not the turn's own".

## Injected text and its guard

Four files write text into a child session that nobody typed: `bin/supervise-holder.sh` at priming, `bin/supervise.sh` for the final ask it relays through the holder and the shutdown ask it writes to the mailbox instead (`writeShutdownAskIfDue` in `bin/supervise-poll.mjs`, delivered by the plugin's own controller tick rather than by the holder), `hooks/index.ts` on every recurring prompt and at every tool registration, and `bin/restart-recap.mjs`, whose digest rides the `[RESTART RECAP]` block at a launch's priming turn. Each string the first three write carries the meaning of the label at its head, the one thing to do with that prompt, and a pointer to the surface that owns the rest. The owners are `CLAUDE.md` for writing and channel conduct, the kit's skills for a seat's duties, and a tool's own description for that tool's contract. A sentence with an owner does not ride a second copy in a prompt, and the guard below is what keeps it that way rather than an eye.

### What is injected, and how large

`.kit/injection-ledger.json` is the committed size baseline, 74 entries totalling 56,276 characters. Twelve entries come from `bin/supervise-holder.sh` and total 29,686, two come from `bin/supervise.sh` and total 292, and sixty come from `hooks/index.ts` and total 26,298, of which the twenty-one registered tool descriptions are 18,832.

| What a launch reads | Characters |
|---|---|
| A worker with a channel: skill-load, coordinator steer, reply-tool | 4,769 |
| The coordinator: those three plus the coordinator role instruction | 14,548 |
| The architect: reply-tool plus its charter, the other two cleared | 12,951 |
| The liaison: reply-tool plus its charter, the other two cleared | 2,315 |
| The twenty-one tool descriptions an owner-tier session registers | 18,832 |

The worker and coordinator rows are upper bounds. They sum each instruction variable whole, while a launch takes only the clauses its persona's guards admit: the coordinator's launch reads none of the steer instruction's worker-only clauses, and a worker reads the architect sentences only where its own settings file names an architect, and the coordinator reads its liaison clause only where its own settings file names a liaison. The liaison row is a launch with a channel attached. No row counts what a launch splices in, because the ledger strips interpolation. The persona names are one such value. None of the five rows counts `SUPERVISOR_MAILBOX_INSTRUCTION` (459 characters), which every launch's priming turn carries regardless of persona or `--no-channel`.

`fleet_status` alone is 3,934 of that last row, because the five health-class definitions live in it and every other surface points there. It registers into every session whatever the persona, including a worker that cannot call it.

The startup message is assembled at one `node -e` call in `bin/supervise-holder.sh`, the one that writes the `[SUPERVISOR-PRIMING]` line, from `SKILL_LOAD_INSTRUCTION`, `COORDINATOR_STEER_INSTRUCTION`, `COORDINATOR_ROLE_INSTRUCTION`, `ARCHITECT_ROLE_INSTRUCTION`, `LIAISON_ROLE_INSTRUCTION`, `SUPERVISOR_MAILBOX_INSTRUCTION`, `CHANNEL_REPLY_INSTRUCTION` and the priming body. Each is empty for the launch shapes it does not apply to. The reply-tool instruction is built only with a channel attached, and it states the operator-writing rules inline rather than by pointer alone: four of the five persona launch directories hold no `CLAUDE.md`, so a pointer at that file reaches one persona of five. Its closing sentence points there for the rules the kit doctrine carries, where the child's own working directory holds the file.

On the plugin side there is no shared prefix. Each recurring frame (`[FLEET]`, `[RECONCILE]`, `[KAIZEN]`, `[PROPOSE]`, `[STILL WAITING]`, the reply backstop, the idle nudges, the goal-tree blocks, `[TASK LIST]`, the no-goal reminder, `[STANDING]`, `[RESTART RECAP]` and `[MEMORY CHECK]`) carries its own label, its own instruction, and names the reply tool in its own words where its text is for the operator. The `goal_done` clause sits once, in that tool's description, and the prompts that deliver a reading point at it.

The no-goal reminder ships as two literals rather than one, `NO_GOAL_BLOCK` and `NO_GOAL_RECORD_SENTENCE`, and the ledger sizes each as its own entry. The first carries the goal rule: open a goal only for an effort that outlasts this turn, or one the operator asks the persona to track, and otherwise answer the message and say what was done. The second is appended only where the record step above actually ran, and says the plugin is already holding this message as the turn's record. The split is what keeps the block from claiming a record on a turn that opened none, which is a priming turn, a `[SUPERVISOR-ASK` status check, and an owner-armed session that does not hold the persona claim. The ledger's rule for the block anchors both literals and the line that selects between them, so a third arm or an interpolated operand throws rather than going unsized.

The `[STANDING]` block rides every external prompt of a session that is not reader-armed, after the goal blocks and any `[TASK LIST]` block, and before `[ENV]`. Its first line is the idle order: finish the active entry, then the next queued entry in the goal tree, then the backlog. Its second names the goal tree as the queue. Its third states the persona's autonomy level and what that level allows, scoped to work the persona finds on its own, outside the operator's request. At `plan-and-ask` and `plan-and-start` that line closes by saying a persona with no goal tree sends a `[PROPOSAL]` instead. Only the operator or the coordinator opens a tree. Where open entries remain and none of them can start by itself, a fourth line says the persona is idle for these duties. The plugin's own submits, a nudge or a delivery among them, bypass the `prompt.submit` hook and carry no block. The daily `[PROPOSE]` frame therefore carries its own sentence for the level.

The `[RESTART RECAP]` block rides only the supervisor's `[SUPERVISOR-PRIMING]` turn, in a session that holds its persona's claim and whose `restartRecap` setting is not `skill`. It sits right after `[STANDING]` and before `[ENV]`. The hook runs `bin/restart-recap.mjs` from the plugin's own directory with a five-second timeout (`RECAP_TIMEOUT_MS`). It injects the block only where the header's `lastRecordAt` is within 24 hours (`RECAP_RECENT_MS`) and either `activeGoal` is true or `lastOperatorAt` is within 6 hours (`RECAP_OPERATOR_MS`). Each channel line in the digest carries its author where the envelope names one, as `<kind> <hh:mm>: <author>: <words>`, the author cut to `RECAP_AUTHOR_CHARS` (64). The script reads the tag by the rule `channelSenderOf` in the hook applies, and a tag is whole only where its closing `>` ends its line. A whole tag whose class is exactly `operator`, or absent, prints under the `operator` kind. Any other class, or a tag that is not whole, prints under `participant`, the broken tag with no author. A participant's line moves neither `lastOperatorAt` nor the count line's operator messages, while `lastRecordAt` still moves, since the message is a record in the transcript. Where the header's lineage is not `recorded`, the frame adds a sentence saying the digest may be another persona's. The digest passes through `bracketSafeText` at the hook, so no line of it opens a block header. A failed run, a bad header, an empty digest, a stale session and a quiet one each inject nothing and write one `restart_recap_skipped` decision, and the prompt goes through unchanged.

### The ledger and the duplicate test

`.kit/injection-ledger.mjs` extracts every one of those strings from the two source files and prints `{ basis, entries: [{ name, file, chars, words }] }` on stdout. It normalizes CRLF to LF, decodes standard backslash escapes, and strips `${...}` interpolation, so a count does not depend on the checkout's line endings or on per-launch data. It resolves no identifiers: it reads text with patterns.

`.kit/injection-duplicate-test.mjs` runs the ledger and fails on four conditions: a sentence of eight or more words shared between an injected string and `CLAUDE.md` or between two injected strings; a string whose live size exceeds its baseline number; a name in the baseline with no live counterpart or a live string with no baseline entry; and any throw out of the ledger. It exits 0 when everything passes, 1 when a real check fires, and 2 when one of its own controls or a ledger guard broke, which is the reading that says the run says nothing about duplicates.

The ledger fails closed rather than recording a short value. Each rule asserts it consumed the whole source construct and throws with a tag naming the entry: `[instruction-count]` when a variable's assignment count moves, `[instruction-reassign]` when a bare reassignment carries text a growth-only size check could not see, `[priming-shape]` when a clause is appended to a priming body, `[fleet-note-prose]` when a fleet note's authored half changes shape, and `[delivery-exclusion]` when a record-delivery call site gains literal text. Four structural checks read a family's shape off the source rather than off the file's own list, so a string nobody added to the table fails the build instead of going unsized.

### What the guard does not reach

Four bounds are declared rather than closed: three in the ledger's header and in `README.md`, and one in the ledger's rule for the `[RESTART RECAP]` block. Each is a place where new text can reach a child unsized.

- A name. The extraction resolves no identifier, so prose hoisted out of a literal into a constant looks exactly like a variable carrying data. Closing it needs a parser rather than a further pattern. The fleet-note prose rule and the still-waiting re-raise rule do refuse that shape at their own sites, each under a control of its own.
- Prose a fleet note splices into its own line through an interpolation whose value is not itself a literal: a named constant, a helper's return, or a value read off another note. A literal inside an interpolation is sized, both arms of a ternary included.
- The three record-delivery prompts, whose whole text `hooks/operator.ts` builds. Two are named exclusions; the third delivers as tool-result context and is reached by no name, so the class is bounded by a count the ledger asserts over every `deliveryText` call site, with each site required to pass only data.
- The restart recap's digest. `bin/restart-recap.mjs` builds it at each launch from transcript text and a few lines of its own: the session line, the `last words:` line, the count line and the dropped-lines note. The ledger sizes the frame `hooks/index.ts` puts above the digest and reads the digest itself as per-launch data. What bounds it is the script's own caps, 400 characters a message, 64 an author and 6,000 for the whole.

### Operating it

Run `node .kit/injection-ledger.mjs` to read the live sizes and `node .kit/injection-duplicate-test.mjs` to gate. Both are offline, so they run beside a live fleet, and both take seconds. When an edit changes an injected string, refresh `.kit/injection-ledger.json` from the ledger's own output in the same commit: a rise is declared there rather than discovered later. A ledger throw is the tool refusing a source shape no rule names, and the fix is to re-anchor the rule beside the edit that moved it, never to delete the rule. A failure at exit 2 is the instrument, not the subject, and is read before anything is concluded from the run.

## The supervisor's self-heal paths the keeper depends on

The keeper's policy assumes the supervisor's exit code means what the exit table says. Three supervisor behaviors make that hold across a relaunch.

**No orphan at a natural-exit relaunch.** The supervisor walks the child's Windows process tree and keeps a snapshot of each process's pid and creation time (`CHILD_TREE_SNAPSHOT`). `refresh_child_tree` walks the MSYS closure of the launch pid every poll, launched or adopted alike, and for an adopted child checks only the root's resolved Windows pid against the one the handle recorded, reading the child gone on a mismatch rather than trusting a reused pid. `build_stop_snapshot` is the one that walks straight from the recorded Windows pid, and only for an adopted child at the stop itself, since that child's MSYS pid is never resolved or walked there. The walk accepts a process as a descendant only where its creation time is not earlier than its parent's, because Windows reuses a dead parent's pid and a walk on parent ids alone adopts unrelated processes. Before every natural-exit relaunch, `sweep_child_tree` kills each snapshot process still matching pid and creation time and confirms it dead. A stop the poll loop orders goes through `stop_child`, whose force-kill phase does the same against its own snapshot; `README.md` under Stop Phases states the phases. On the natural-exit path the shutdown branch exits 0 whatever the sweep found, recording a survivor as a `NOTE:` line. The park branch exits 6 on a clean sweep. It and every other branch exit 5 rather than relaunch beside a process they could not confirm dead. The sweep reaches only what the snapshot names; a process the child started after the last walk is outside it (`docs/backlog.md`).

**Limits enforced on the decide path.** The poll loop's `restart)` case updates the crash counter and the hourly restart count, then checks `SUPERVISOR_MAX_RESTARTS_PER_HOUR` (exit 4) and `SUPERVISOR_CRASH_LIMIT` (exit 3) before it relaunches, on the same counts and codes the natural-exit path uses. Without this a limit stopped the run one launch late, after the next child had claimed the persona and attached the channel.

**A rate-limited child is logged as parked, not read as frozen or gone.** The poll loop reads the newest record of the child's `stdout.jsonl` (`readRateLimitReset` in `bin/supervise-poll.mjs`). While that record is an `api_retry` with `error_status` 429 and a positive `retry_delay_ms`, the supervisor logs `RATE_LIMITED until <ISO>` in place of `WAITING`. The state ends by itself when the child writes any newer record. The reading suppresses nothing and sends no notification. The liveness verdict never reads a parked child `frozen` or `gone` on its own. The guard is the usage-limit rule in `bin/supervise-liveness.mjs`, which the verdict checks first: while the newest stream record is that retry and the process walk finds a live process, the verdict is `alive` with reason `usage_limit`. The second reason is the heartbeat, which a parked child keeps stamping.

The supervisor reads no account identity and takes no action when the child's account changes. An account swap is transparent to a running `claude`.

The liveness verdict (`bin/supervise-liveness.mjs`) reads a child as `frozen` or `gone` only where four signals are silent at once: the newest turn record across the child's own transcript and its subagent transcripts, the age of its output stream on the supervisor's own clock, its own heartbeat file, and an unacknowledged mailbox probe. The process-tree walk then decides which of the two: a live process is `frozen`, none is `gone`. Any signal that is not silent, and every fail-closed case (an unreadable transcript, a walk that did not complete), reads `alive`. `frozen` writes one final ask to the child's own input before it restarts; `gone` sweeps the recorded tree and relaunches. `README.md` under Poll Loop states the full priority order.

## External integrations

- **Windows Task Scheduler**: one `AgentPersona-<name>` task per enabled roster entry, the Password logon type at boot. Its restart-on-failure setting (999 at one minute) is the backstop for the wrapper crashing, not the policy for the supervisor.
- **Git for Windows bash**: `KEEPER_BASH_EXE` names it. The wrapper runs `bash <script>` with no `-l`, so the supervisor's children resolve on the delivered `PATH`, not on a login profile's rewrite.
- **`claude` CLI**: the supervisor's child, launched with stream-json on both ends. `KEEPER_PATH_PREPEND` is what makes it and `node` resolvable under a task with no user `PATH`.
- **Discord relay** (`D:/discord-channels`): the child attaches to a thread named `supervisor-<persona>`, or the roster's `channelName`, unless `args` carries `--no-channel`.
- **The commons store**: machine-global, one per installed plugin; the supervisor's pre-launch gate reads it for a live claim on the persona, and the plugin's inbox path runs through it.
- **The kit plugin's install record**: Claude Code's `installed_plugins.json`, under `.claude/plugins` in the home the session resolves, `USERPROFILE` or else `HOME`. `kitInstallPathOf` in `hooks/index.ts` reads the `grimoire@applefeld` key. A usable record has a non-blank string `installPath` and a `lastUpdated` that parses as a date, and the newest such record wins. The kit's memq CLI and its compaction checkpoint command both run from that record's path. Where the key holds no usable record, `compaction_boundary_skipped` and `memq_spawn_failed` carry a detail naming why. The supervisor's holder reads no install record: it names the kit's skills in the priming turn as `grimoire:` literally.
- **The kit's shared memory store**: the plugin runs `node` on the kit plugin's `scripts/memq.js`, found through the install record above, in the launch directory the first `session.start` captured and holds in `$.state`. `memq put` writes each distilled fact and each `memory_add`, `memq judged` reads the persona's judged records at each prompt, and `memq touch --applied` stamps each shown record the goal-close check names. Every spawn is bounded at 5 seconds, and a read that times out or that memq reports it could not run stands reads down for one minute. memq reaches the kit's embedding server, database host and Jev endpoint itself. `README.md` under "Memory (M1, M2)" states the plugin's side, and under "What leaves the machine" what the read sends.
- **TypeSafe** (`https://api.typesafe.ai/v1/systemone`): the plugin's one direct HTTP call. The decision seam puts each of the four closed questions the plugin asks Haiku to Jev, TypeSafe's classifier, in shadow unless `jevLive` names it. It also asks one plan-health question, `block-owner`, about a plan entry's closing text at that entry's turn end, and the two turn record questions one at a time at the prompt and at the turn's end; those three have no Haiku counterpart. Every answer is journaled. A question the `jevLive` setting names by id, one of the two turn record questions or `memory-kind`, is asked live and its answer read by the branch that asked it, which is the seam's one exception to reading nothing. A live call sends the same state its shadow call would; every other question, and every failure on a live call, falls to the question's stated default. Authenticated with `TYPESAFE_API_KEY` from the child's own environment, which no file in this repository sets. `jevMode` `off` makes no call at all. `README.md` under Decision seam states what each call sends.
