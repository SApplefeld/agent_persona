## A goal nudge that matches no expected-turn entry still reaches the memory step (found 2026-09-27)

## Supervisor-peer hardening left after Section 5 (found 2026-09-24)

Twenty-four items. Most would change a kill, a spawn, a claim, an adoption decision, a race window or accounting, or add a guard, which would owe a review round; item 4 is accepted and recorded only. Every citation is a function in `bin/supervise.sh` unless another file is named.

5. `ensure_child_ticks` retries a persistent miss every 64 polls for the run, through `ticks_retry_due`'s doubling gap. Remedy: stop after N misses and log the child unadoptable once.
6. `child_exit_code`'s adopted-marker wait is up to 50 `sleep 0.1` spawns per adopted exit. Remedy: five 1 s steps.
7. Nothing re-reads the claim after the gate's second read-back, so a claim overwritten later goes unseen; a lock to close this race was declined. Remedy: re-check `claim_is_ours` every N polls and detach on a foreign claim.
8. ## The adopted stop's grace loops count iterations, not time (found 2026-09-24)

`stop_child`'s two grace loops for an adopted child (`bin/supervise.sh`, both shaped `while stop_present && [ $n -lt $grace ]`) count a fixed number of iterations, `$grace`, 60 by default (`supervisorStopGraceMs` / 1000), rather than elapsed time. Each iteration calls `stop_present`, which for an adopted child runs `refresh_child_tree` every time. That is a `ps | awk | sort | tr` process-table read and one `/proc/<pid>/winpid` read per closure member on every iteration. It adds a bounded PowerShell walk, capped at `supervisorPsBoundS`, 30 seconds by default, whenever the child's Windows pid set differs from the standing tree record, and a walk that did not complete leaves the record behind the set, so the next iteration walks again. So the grace stretches with process-table and PowerShell cost on the uncooperative case, since a cooperative exit's marker ends the loop before the walk. A busy or unverifiable child stretches each iteration from about 1 second toward about 31 seconds. Two loops of 60 such iterations, at up to 31 seconds each, come to a worst case of about 62 minutes (2 × 60 × 31s = 3720s); an adopted stop sends no TERM, so there is no separate TERM wait to add. Whether a per-rung time bound belongs in the plan's own acceptance is open for the operator: no Goal sentence commits to one, and leaving it unbounded costs a stop that can run close to the full 62-minute worst case above before the supervisor moves past it. Remedy: time the loops on the clock, as the patient wait already does under `restart_passive`, and refresh the tree at most once per poll interval rather than once per iteration. The operator may instead choose to add a per-rung time bound to the plan's own acceptance.

## Design direction: let the outer loops recover a session that stopped, rather than only preventing the stop (operator dialog, 2026-09-13)

Not a defect and not yet a plan. Recorded from a design conversation with the operator so it survives the session that had it.

The problem it addresses, in the operator's own account: sessions are often found parked mid-effort, having declared a next action and then stopped, losing hours of wall-clock progress. The kit's stop hooks were built to prevent exactly that. The proposal is that the supervisor shell, which already launched the session and holds both ends of its pipe, could also recover one after the fact, the way a person at the keyboard types "continue".

What makes it viable: `bin/supervise-holder.sh`, an ordinary pipeline stage `bin/supervise.sh` launches ahead of the child, not a detached process, holds the write end of the child's stdin pipe for the child's whole run. The supervisor itself never touches that pipe; it reaches the child by writing `ask.request`, which the holder relays as one `[SUPERVISOR-ASK id=...]` turn on any poll with no gate on the priming turn's result line, and by writing `<rundir>/child-<n>.prompt`, which the holder sends only once that result line appears. A recovery nudge, a "continue" pushed into a stalled session, would need a relay kind of its own in the holder, since the ask relay's own shape carries a status question rather than an instruction. The child emits exactly one result line per turn it completes, and the holder gates only the prompt-file send on that line, because a prompt written earlier is absorbed into the open turn instead of starting its own; the ask relay carries no such gate, since a stalled child may never produce a result line at all.

The discriminator is the hard part, because one keystroke helps in one state and harms in another. Idle but alive: typing is right, and is what the operator does by hand. Process gone: typing does nothing and the existing restart is the answer. Mid-turn: typing is actively harmful, because the prompt queues and joins the next turn, which is the nudge pile-up Section 11 exists to stop.

The signal to build the discriminator on should be the shell's own, not the plugin's. The plugin's open-turn reading depends on `turn.start` events that are delivered for a minority of turns, per the entry above. The shell knows when it wrote a prompt and when the result line came back, and observes both halves itself.

Keep the stop hooks beside this rather than replacing them. They cover different failures. A hook prevents a bad stop at no cost when it works, but cannot fire in a session that has died, since whatever killed the process took the hook with it. A loop repairs after the fact and always pays a detection delay plus a resume that re-reads the plan and re-derives what the stopped session already held.

Design against one failure from the start: a loop that types "continue" on every quiet stretch will eventually type it into a session that correctly finished, which is the failure the operator described on a sibling project, many review rounds building features nobody asked for. The loop needs a predicate for whether work should still be happening, not only whether work is happening. The armed kit goal is the natural source, since it already records what the session was meant to finish.

Two limits worth knowing before anyone builds this. There is no working-on-it event in the stream, because the spinner is drawn by the interactive display, so silence during a long tool call is indistinguishable from death on the pipe alone and growth is the honest liveness evidence. And prompts the plugin submits to itself are not echoed into that stream, so a shell-side monitor sees the turn a self-nudge causes but never the nudge.

`docs/archive/agent_persona_supervisor-peer_v1.md` builds this proposal's liveness half: the verdict in `bin/supervise-liveness.mjs`, four silence signals plus a process-tree walk, that judges a child frozen or gone, and the one final ask written to the child's own pipe before a frozen child is restarted. Its recovery-nudge half, a message that pushes a stalled session back to work rather than only judging whether it is alive, stays open here.

## A session that could not load its persona holds no watcher until a tool call reloads it (found 2026-09-22)

A session whose store file does not parse at start-up comes up on the built-in default state. Its writes cannot publish that empty tree over the persona's real one, because `persist` reads the store before it writes and gives the persona up to whatever session the stored entry names. On the first heartbeat tick whose read parses, it yields the persona rather than publishing a claim built from a state it never loaded.

What the yield costs is the watcher. The session stops owning the persona, so the owner-gated fleet and reconciliation work stops running for the life of that process. Recovery is the `agentic_identity` tool, which loads the persona's entry from a store that parses and clears the not-loaded field.

Nothing recovers it on its own. The supervisor's liveness verdict (`bin/supervise-liveness.mjs`, read by the decide unit's own `frozen`/`gone` verdict branch in `bin/supervise-decide.mjs`) reads a child `frozen` or `gone` only where its transcript, its output stream, its own heartbeat file and an unacknowledged mailbox probe are all silent together and the process-tree walk decides between the two. A yielded session that is still answering turns keeps writing turn records to its own transcript, which keeps that signal from ever reading silent, so the verdict stays `alive` and nothing restarts it. So the session sits alive and watcher-less until a worker calls the tool.

The goal tools do tell the worker the state was never loaded, and name the cause. They do not name the remedy, so a worker has to know that `agentic_identity` is what clears it.

Remedy: one of three, and which is right is a design question rather than a known fix. Name the remedy in the not-loaded sentence the goal tools return, which is the cheapest and leaves the recovery manual. Or give the heartbeat a branch that holds the seat by sidecar and commons while publishing nothing and yielding to nothing, until a tool call loads the state, which keeps the watcher and is a new mechanism needing its own design stop. Or have the supervisor read the not-loaded state as its own restart trigger, which crosses into the restart rules the curation plan's `## Intent` refuses to change. The second keeps the sidecar live, which blocks the very relaunch that would otherwise recover the session, so its cost is not obviously smaller than the one it removes.

Raised while executing section 1 of `docs/archive/agent_persona_goal-tree-curation_v1.md`, where a consultant priced the yield as recoverable through a supervisor relaunch. That pricing is wrong, and the restart rule cited above is why: the transcript signal is what stops the relaunch for a session that is alive. The yield is still the right behavior for that section, because the alternative writes the built-in default over the persona's stored tree.

## The journal's state text is not the message the persona received (found 2026-09-26)

## The disposition stamp list on one turn record is unbounded, and its flush is one whole-file journal write per stamp (found 2026-09-26)

A turn record holds one unsettled journal stamp per turn-disposition call asked over it, and nothing caps that list. Each own turn end that reaches the classifier adds one. The list is drained at the next external message, or as `none` once the record expires, and the drain writes one outcome line per stamp. Each of those lines is a whole-file read and rewrite of that day's journal, serialized on a per-path chain.

Its recommendation, quoted as the reason this entry exists: the finding leans toward applying, because the Intent's own constraint sentence admits the deployment condition the growth needs, and because the journal is a stated deliverable rather than something incidental, so its cost under the stated deployment is a property of a thing the plan asked for. So what is owed is the operator's call on whether an autonomous persona nudged by an idle controller carries an implied bound on per-event journal work. If it does, the fix is in scope for a section. If it does not, this entry is the record of why not.

Remedy, in preference order. Append the outcome lines for one record as a single joined write, which removes the burst without bounding anything and needs no decision about what to discard. ## A goal entry with no plan path re-plans a finished plan as fresh batches (found 2026-10-01)

A root goal that names a plan in its words but carries no `planPath` is broken down by the planner, not by the plan document. It then re-plans the same sections as new entries each time the previous batch runs out of rounds. Nothing reads the plan document's `Status:`, so the tree cannot close when the plan finishes. It stops only at the planning cap.

DEV-DISCORD's store (`D:\discord-channels\.agentic-personas.json`, read 2026-10-01) shows the pattern. Root `root-muonm4w9`, "Finish the Session Activity Signals plan", has `planningRounds` 4 and no `planPath`. It holds four batches of plan entries, created 2026-09-30 22:07Z and 2026-10-01 01:37Z, 02:31Z and 03:34Z, with `planningRound` 0 to 3. The batches shrank from four entries to two as sections finished, and each re-listed every section still open under the same title. No entry carries a `planPath`. ASSISTANT reported, via the coordinator, that 11 entries sat blocked "Max rounds reached" and the root blocked "Planning cap reached" after the plan had finished and been archived in its own repository. DEV-DISCORD's `goal_done` on the root has since closed them all, so those blocked states are reported, not read.

The code confirms each step. Planning fires only when the root has no pending, active or paused descendant (`hooks/index.ts:8342`). Its prompt lists blocked items as history and allows one retry "with a different approach" (`:8415`). Every planner entry is pushed as a new node, and none is reused (`:8508-8531`). A node with no `planPath` on itself or an ancestor is not a plan entry (`isPlanEntry`, `hooks/index.ts:4710`, through `planHolderOf`, `hooks/agent-state.ts:1711`). So it keeps a round budget and is blocked "Max rounds reached" at `hooks/index.ts:10251`, and the load-time recovery at `hooks/agent-state.ts:855` skips it for the same reason. The cap blocks the root at 5 planning rounds or at 2 consecutive all-blocked rounds (`hooks/agent-state.ts:1888-1892`).

How the root came to lack a `planPath` is not confirmed. The likely path is a goal created from a sentence naming the plan rather than from the plan file. Two remedies are open. One makes the goal-creating tools set `planPath` whenever the text names a file under `docs/plans/` or `docs/archive/`. The other makes the planner decline to break down a root whose objective names a plan document and ask for the path instead. Either needs a tick-suite case driving a root with a plan named in its words and no path, and showing it never re-plans.

## The upgrade check's probe run drops three login keys but not a cloud-provider login (found 2026-10-02)

Step 2 of `bin/upgrade-check.mjs` runs the new build on a probe plugin under an empty config folder, so the run makes no model call. It drops `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` from the probe's environment, which is the list the types probe plan's ruling fixed. Remedy: decide whether the probe should also drop the cloud-provider switches, and if so add them to `PROBE_LOGIN_KEYS` with a unit case beside the existing one.
