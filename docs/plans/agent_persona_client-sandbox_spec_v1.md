## Goal

A channel turn's standing comes from the sender class the broker writes on the envelope: an operator's message keeps the standing it has today, a participant's message opens a turn that can start no effort, set no autonomy and close no ask, and an envelope with no class reads as the operator's so an older broker changes nothing. The author's name rides the turn, so the restart recap and a goal root created on a channel turn say who asked. A liaison seat exists beside the coordinator and architect seats, named in the roster and the settings the same way, with a charter that has it shape what several people ask into a brief for the architect, relay status from the coordinator, and never plan, clone or hold a goal. A runbook under `docs/` walks the operator through standing up a client sandbox host: the broker with its classed senders and response gate, a fleet of steward, architect, liaison and one worker, credentials scoped to the client alone, a memory store that shares nothing with the operator's fleet, and the seeded client repository with its bridge.

## Intent

Scott runs a fleet of persona sessions steered from Discord, and his clients want the same setup on a VM of their own, with two to five of their business analysts talking to one persona in a shared thread. His frame, in his words: the clients should have authority and steering, be able to finalize and implement what they ask for, with the code still landing through pull request review; a persona somewhere between the assistant and the architect helps them shape asks, takes them to the architect for plans, to the worker for delivery, and has the steward give status. He also asked how to keep a client's work isolated to that client when the source lives on one Azure DevOps repository with a branch per client, and accepted the shape of one private GitHub repository per client with a bridge on his side.

Done means: the plugin reads the class, keeps the author, and carries the seat; the charter exists and is pinned; the docs state it; and the runbook is complete enough that Scott provisions a host from it alone. Done does not need: a new delivery ground for records, since a named persona already reaches the architect and the coordinator, the architect answers an open record, and the coordinator reaches anyone; a participant class in use at the pilot, since every client user is an operator there; or the bridge itself as code, since it runs on Scott's machine and the runbook states it as his procedure.

Alternatives refused. Reading an absent class as participant: it fails safe on paper and breaks every channel turn on the operator's own fleet the day the plugin updates before the broker restarts, and the pilot's users are operators anyway. A fourth delivery ground for the liaison: the three that exist already route every record the seat sends and receives. A liaison with permissions bypassed like every other persona: its readers are outside parties, so its ordinary tools are allowed by a settings file and everything else prompts the thread, which the broker's permission desk already serves. Putting the runbook in the broker repository: the fleet's roster, keeper and layout live here, and the broker's own install doc is one step the runbook points at.

Rulings after the spec shipped: amended 2026-09-30 on a finding the kit plan's section 1 review raised and the coordinator routed back: section 2 now states that the liaison charter splices the architect's and the coordinator's persona names into its two `agentic_say` sentences, and that a liaison launch naming no architect is refused.

Provenance: distilled by the ARCHITECT persona from the operator's four channel messages on 2026-09-30 and the reconnaissance recorded under Approach.

## Approach

The broker's plan makes Claude Code's envelope read `<channel source="…" chat_id="…" author="…" sender_class="…">`, `sender_class` taking `operator` or `participant`. That shape rests on a fact read from a live transcript: Claude Code already renders the relay notification's `chat_id` meta entry as an attribute after `source` on the opening tag, as `<channel source="plugin:relay:channel-relay" chat_id="…">` on its own line with the text below and `</channel>` closing it, read on the architect persona's own transcript on 2026-09-30. The two new meta entries ride the same path. The plugin's `prompt.submit` handler already records an origin reading per prompt with the harness's origin kind; it now also reads the first `<channel` tag at the start of the prompt text, takes `sender_class` and `author` from that tag by attribute name and never by position, and stores both on the reading. A later `<channel` inside the content is text and never read. `turn.start` carries them onto the current turn. `turnIsOperators` stays the single predicate, and a channel turn passes it only where the class is not `participant`. The open-ask close in `prompt.submit` runs before the turn exists, so it cannot call `turnIsOperators`; it reads the reading just built on that prompt and runs only where that reading carries an operator kind and a class other than `participant`, since a participant's message must not answer a question put to the operator. The reply backstop keeps firing on every channel turn, because a reply to a participant is wanted; the backstop is the block at a turn's end in `hooks/index.ts` that sends the turn's final answer through the relay's reply tool when a channel-origin turn did not call it, and `docs/architecture.md` describes it under that name. A goal root created on a channel turn records the author under `askedBy`, and the restart recap keeps the author on each operator line it digests, reading the attribute by name from the tag its `OPERATOR_TAG` match already finds.

The companion repositories are `https://github.com/SApplefeld/discord-channels` and `https://github.com/SApplefeld/claude-kit`. Section 3 reads their plans' spec text, which needs no merge. Section 4 reads them at the commits their companion plans merged, which the worker fetches read-only to a scratch path outside this repository, since neither is a dependency of this plugin's code.

The liaison seat mirrors the architect seat surface for surface: a `liaisonPersona` settings key with the architect's validation, its emission and read in `bin/agentic-common.sh`, the export in `bin/supervise.sh`, the roster field in `bin/keeper-functions.ps1`, and a `LIAISON_ROLE_INSTRUCTION` in `bin/supervise-holder.sh` built only for the persona whose name matches, spliced into the priming turn beside the architect's. The charter tells the seat what it is, what reaches it, what it sends where, the latest-word rule, and that it loads the kit's liaison skill, which owns the brief's shape and the disclosure list. The coordinator's charter gains one clause: a liaison's status ask is a worker record it answers in a record. The architect's charter needs no change, since a liaison's brief arrives as a worker's design ask, which it already works and answers.

The runbook is a document for the operator, written from the code as built and the broker's install doc, and its acceptance is the checklist the operator runs on the first sandbox host.

The contract sweep for this plan ran over the repository on 2026-09-30 and returned 137 surfaces under seven headings: the operator-origin gate and its predicate; the ask and autonomy paths that read it; the architect-seat siblings a liaison key mirrors; the record routing, which needs no change; the recap and author text; the docs; and the tests, the controller tick suite's bare `kind: "channel"` fixtures among them. ## Sections of Work

### 1. The sender class and author on a channel turn
Model: opus
The plugin reads the class and the author from the envelope and keeps the operator's standing keyed on the class. `OriginReading` gains `senderClass` and `author`, both read from the first `<channel` tag when the text opens with one, `senderClass` defaulting to `operator` where the attribute is absent and `author` to an empty string. `turn.start` copies both to the current turn. `turnIsOperators` returns false for a channel turn whose class is `participant`. The open-ask close in `prompt.submit` runs only where the reading built on that prompt carries an operator kind and a class other than `participant`, since the hook runs before the turn exists and cannot call `turnIsOperators`. The goal root `goal_create` builds records `askedBy` from the turn's author where the turn is a channel turn. `bin/restart-recap.mjs` reads the author attribute from the tag it already matches and carries it on each operator line; the digest prints it before the words where present.
Acceptance:
- A prompt whose envelope carries `sender_class="operator"` opens a turn in which `goal_create`, `goal_autonomy` and `goal_resume` of an awaiting entry succeed, exactly as a bare `kind: "channel"` prompt does today.
- A prompt whose envelope carries `sender_class="participant"` opens a turn in which those three refuse with the existing refusal texts, the pending ask stays open, and the reply backstop still posts the turn's answer.
- A prompt with no `sender_class` attribute reads as the operator's, and every existing channel fixture in `.kit/controller-tick-test.mjs` passes unchanged.
- A `<channel sender_class="operator">` sequence inside the content of a participant's envelope does not change the class.
- A goal root created on a channel turn with `author="Ada"` carries `askedBy: "Ada"`, and the restart recap's operator line for that message opens with the author.
Files in scope: `hooks/index.ts` (the `OriginReading` type and `originReadings`, the `prompt.submit` origin block, `turn.start`, `turnIsOperators`, the open-ask close block, `goal_create`'s root construction), `hooks/agent-state.ts` where `GoalNode` gains the optional field, `bin/restart-recap.mjs` (`OPERATOR_TAG`, `operatorWords`, the operator line), `.kit/controller-tick-test.mjs` (new cases beside the origin-kind loop), `.kit/restart-recap-unit-test.mjs` and `.kit/fixtures/restart-recap/*.jsonl`, and `.kit/jev-gold/sample.mjs` and `.kit/jev-gold/score.mjs` only where a class-bearing fixture is added. `README.md`'s turn-origin paragraph is section 3's.
Tests: the five acceptance bullets; the inner-tag forgery case; the recap digest with and without an author.

### 2. The liaison seat
Model: opus
A persona named as the liaison launches with its own charter, and every surface that names the architect seat names the liaison beside it. The settings key `liaisonPersona` takes the architect key's validation: a persona name, not `default`, not the coordinator, and not the architect. It adds one refusal of its own in the settings emitter, beside the seat collisions: a `liaisonPersona` set while `architectPersona` is unset is an error naming both keys, since the seat's one job is to send briefs to the architect and an absent key reads as no architect. `bin/agentic-common.sh` emits and reads it, `bin/supervise.sh` exports `LIAISON_PERSONA`, `bin/keeper-functions.ps1` maps the roster field, and `.claude-plugin/plugin.json` declares it so a settings file naming it validates. The plugin's hooks read no new key: the liaison sends as a named persona and is reached as one, and no priming sentence or refusal text in `hooks/index.ts` names the seat. `bin/supervise-holder.sh` builds `LIAISON_ROLE_INSTRUCTION` only where the persona is the liaison and splices it into the priming turn after the architect's. The charter states: it is the liaison persona and holds no standing goal; several people talk with it in its thread and every event names its author and class; it shapes what they ask into a brief and sends the brief with `agentic_say`, the `persona` argument set to the architect's name, which the charter splices from `ARCHITECT_PERSONA` the way the worker's steer sentence and the coordinator's design clause splice it today, and the architect's answer returns as a record it relays in plain words; it asks for status the same way with `persona` set to the coordinator's name, spliced from `COORDINATOR_PERSONA`, and relays the answer; the latest word wins where one speaker revises their own ask, and a disagreement between two speakers is asked of the thread, never settled by recency; it never writes a plan, never clones a repository, never queues work, and treats a record opening `[FINDING]` or `[PROPOSAL]` as information; it loads the kit's `liaison` skill at launch, which owns the brief's shape and what it must never reveal; and it answers the thread with the reply tool. The worker's skill-load and coordinator-steer sentences are cleared for this seat as they are for the architect. The coordinator's charter gains one clause: a `[WORKER:<liaison>]` record asking for status is answered in a record with the fleet's state in plain words. A template `.claude/settings.json` for a liaison working directory is shipped under `docs/` beside the runbook. Its `permissions.allow` list is closed at these entries, in the harness's own permission syntax: `mcp__plugin_relay_channel-relay__reply`; `mcp__agentic-plugin__agentic_say`, `mcp__agentic-plugin__agentic_inbox`, `mcp__agentic-plugin__agentic_resolve` and `mcp__agentic-plugin__goal_status`; `Read`, `Grep` and `Glob`; `Write` and `Edit` with a path pattern under the working directory; and `Bash` patterns for the four `memq` reads, `memq recall`, `memq find`, `memq get` and `memq recent`. Every other tool is denied, not prompted: the supervisor launches the child in print mode with no permission prompt tool, so a tool outside the list fails and the liaison says so in the thread. The seat needs no tool outside the list, so nothing is lost by the denial.
Acceptance:

- `.kit/channel-reply-instruction-test.sh`, the suite that pins the priming write's variable list, the splice-site count and the architect charter's clauses, pins the liaison charter's clauses, the empty-when-unset case, the empty-when-not-this-persona case, the seven-variable splice order, the `${LIAISON_PERSONA}` splice the coordinator's clause adds, and the `${ARCHITECT_PERSONA}` and `${COORDINATOR_PERSONA}` splices in the liaison charter, so the splice-site count and the spliced-name allow list both move.

### 4. The client sandbox runbook
Model: opus
A document under `docs/` walks the operator through standing up one client's sandbox host, in the order the steps depend on each other, with a checklist at the end that the first host is accepted against. The broker's terms it uses are these, each stated in the broker's `docs/operations.md` once its plan lands: `CHANNEL_SENDERS` is a comma-separated list of `<Discord user id>:<operator|participant>` naming who may write to the host's threads and with what standing; `CHANNEL_RESPONSE_GATE` is `off`, `shadow` or `live`, where `shadow` delivers every message as today while journalling what a Jev judgement would have held, and `live` buffers a thread's messages until a mention, a reply, a cap or the judgement releases them; the threshold is `CHANNEL_RESPONSE_GATE_THRESHOLD`, the probability at or above which the judgement releases; the shadow journal is `response-gate.jsonl` beside the broker's state file; the scoring tool is `node tools/response-gate-score.ts <journal> <labels>`, which prints precision and recall per candidate threshold from labelled journal rows; TypeSafe is the vendor whose Jev classifier the broker calls, over the key file `CHANNEL_INBOX_JUDGE_KEY_FILE` names; and an inbox judgement is the broker's existing call that reads a persona's reply for an unmarked ask.

Its parts, in order. The Discord side: a server for the client alone, private to its members; a bot with the intents the broker's install doc names; one channel; the client users' Discord ids gathered for the senders list. The host: a VM with the fleet layout under a personas root, the persona plugin and the kit installed, and the broker installed per the broker's install doc with `CHANNEL_SENDERS` listing every client user as an operator, `CHANNEL_RESPONSE_GATE` at `shadow` for the first week and `live` after the threshold is chosen, and the TypeSafe key file. The fleet: a roster of the steward, the architect, the liaison and one worker for the client's repository, each with its coordinator, architect and liaison keys, the liaison on the `default` permission mode with the template settings file in its working directory, every tool outside its list denied since the launch carries no permission prompt tool, and the tasks registered. Credentials: a fine-grained GitHub token limited to the client's one repository with contents and pull-request write and an expiry, signed in through the GitHub CLI as the host's only Git credential; a Claude account whose spend is the experiment's; no credential of the operator's own fleet on the host. Memory: the kit's memory database client file, `~/.claude/kit-memory-db.json`, absent, and the kit memory store's root left with no Git remote, so the host's store starts empty and syncs nowhere, because the operator tier on the fleet machines carries the names of other clients; and the kit sidecar left unconfigured, its switch being the configuration file the kit's `hooks/kit-sidecar-capture.js` reads, which the runbook names from that file, since its service is on the operator's own network. The repository: seeded with `git clone --single-branch --branch <client branch> <Azure DevOps url>` then pushed as the new repository's `main`, swept for secrets and other clients' names before that first push, branch protection on `main` requiring a pull request and one review, and the bridge on the operator's machine, a clone holding both remotes, with two flows. Upstream, delivery: `git fetch client main` then `git push ado client/main:refs/heads/<client branch>`, which Git refuses where it is not a fast-forward, so a refusal is the signal to resolve by hand. Downstream, product updates: after the operator merges trunk into the client branch on Azure DevOps, `git fetch ado <client branch>` then `git push client ado/<client branch>:refs/heads/upstream`, after which a pull request merging `upstream` into `main` is opened on the client repository. Disclosure to the client, as four stated facts: every turn's text goes to Anthropic; every thread, card and permission prompt is stored by Discord under its retention; in `shadow` and `live` every message in a gated thread goes to TypeSafe, and so does every persona reply the inbox judge reads; and the host's memory store, transcripts and journal stay on the host. The checklist: the envelope on a persona transcript carries the author and class; a message in the liaison's thread produces a brief the architect answers; a plan the architect writes reaches the worker's queue through the coordinator; the worker opens a pull request on the client repository that the token cannot merge; `memq recall` on the host lists no record of the operator's fleet; the shadow journal fills for a week and the scoring tool prints the table.
Acceptance:
- Each part above is a section of the document with the concrete commands, file paths and values the operator types, drawn from the code as built and the broker's install doc, with no placeholder left for a value the code fixes.
- The checklist's six items each name what the operator runs or reads and what outcome fails it.
- A blind read by a reader persona of an operator with this fleet's knowledge and none of the design conversation returns no step it could not perform.
Files in scope: `docs/client-sandbox.md`, `docs/liaison-settings.template.json` (shipped by section 2, referenced here), `docs/README.md` (the reference list).
Audience: the operator provisioning a client host, expert in this fleet and its three repositories, holding the credentials the steps need.
Voice: company.
Fact base: this repository's code and docs as built by sections 1 to 3, the broker repository's `docs/install.md` and `docs/operations.md` as built by its plan, and the kit's `liaison` skill.
