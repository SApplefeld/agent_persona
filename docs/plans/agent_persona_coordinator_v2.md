## Goal

Today, a "worker" is a `bin/supervise.sh` launch: one Sonnet-tier `claude -p` child, one repo, one persona, one Discord thread. The operator drives each one directly. v2 adds one Fable-tier "coordinator" persona that reads status across N workers in N repos, batches steers to them without blocking on their multi-minute turns, receives their findings and escalations, reports to the operator on its own thread, and - per the Decisions section's FORK B ruling - dispatches bounded work to a worker without a human round trip per message, within a checkable bound and a judgment call the operator has explicitly delegated. The mechanism is an extension of the existing commons-store inbox path (`agentic_say`/`agentic_inbox`), not a new transport. Discord stays the operator's channel; the coordinator does not read or post into a worker's thread.

## Approach

**Grounding.** This design was pressure-tested by a two-lens Fable-tier design council (Round 1, 2026-09-12) before being written down: an operability/reliability lens and an authority/safety lens, converged by a facilitator. Every claim about the plugin's own code below was independently confirmed against `hooks/index.ts`, `hooks/operator.ts`, `hooks/commons.ts`, and `bin/supervise.sh`, both by the council and, for the load-bearing ones, spot-checked again by this session before this line was written. The full council transcript is retained at `.kit/runs/v2-council-round1/` (copied out of the workflow's own transcript dir before archiving, per the memory note `a-run-dir-is-merge-evidence-until-the-merge-lands`).

**The rejected mechanisms, and why.** Two other transports exist on this machine and both were considered and rejected as the coordinator-to-worker channel:
- The harness's own peer tools (`ListAgents`/`SendMessage`): this plugin actively consumes `session.receive` events of kind `peer`/`peer-send-message` before the model ever sees them (`hooks/index.ts:694-712`), specifically so a peer message carries no steering authority. Using it as a coordinator channel means reversing that design decision and rebuilding deferred-status, urgent break-in, reply capture, and the reader-claim trust gate on a transport this plugin does not own. Its address is a live session id, which a `supervise.sh` relaunch mints fresh every time (Chapter 8.3's own proof: child-1, then child-2), while `persona:<name>` is the thing that actually stays stable across a restart.
- Each worker's own Discord thread: inbound authority there is the operator's own Discord account against a one-account allowlist; the relay's own instructions tell a worker to treat channel text as keyboard-equivalent operator steering. A coordinator posting there either launders its own text into operator authority with no way for the worker to tell the difference, or has no channel to post through at all, since the relay never tells one process which session serves another process's thread. Read access is closed the same way. Discord stays the operator's channel, full stop; the coordinator reports to the operator on its own thread, same as any worker does today.
- `DISCUSSION.md` (the append-only file the worker and Reviewer personas use today for handoffs): turn-serial, invisible to the plugin's own trust gate, and polled by hand. It works between two co-equal live sessions watching one repo; it does not scale to a coordinator directing N workers in N repos, none of which read it. v2 retires it as a steering path; the plan doc and the coordinator's own thread are the record going forward.

**The chosen mechanism: the commons-store inbox path, extended in four small places.** `agentic_say`/`agentic_inbox` already has everything this needs except cross-repo reach: a machine-checked writer gate (only a live reader-claim holder's record reaches the model, `hooks/index.ts:3736-3740`), a deferred-status view that doesn't block on a busy worker (`:3784-3808`), an urgent break-in that reaches a worker mid-turn through the `tool.call` hook's own `context` return (`:3830-3868`), reply capture, and a decision-log trail. Item 8.3 built these for the operator-to-worker direction; the coordinator reuses them rather than inventing a second version.

Four extensions, in order of what blocks the next:
1. **Cross-repo deferred status.** `heartbeatPath` is the literal string `".agentic-heartbeat.json"`, read relative to the process's own cwd (`hooks/index.ts:408, 425, 581`). A coordinator running in one repo can never see a worker in another repo as busy; it would read its own empty or irrelevant heartbeat file. Fix: publish `turnStartedAt` and `workdir` into the session's commons entry (`hooks/commons.ts:24-28`, keyed `commons:<sessionId>`, one entry per live session, already a machine-global store). Finding the right entry for a named persona is `commonsWinner(readAllClaims(...), "persona:<target>")` (`hooks/commons.ts`), the same lookup `shouldYieldCommons` already uses for arbitration - not a lookup this design invents.
2. **Addressing N workers.** `agentic_say`/`agentic_inbox` operate on `sess.persona` only. Reaching a specific worker today means an `agentic_identity` switch, which also swaps the coordinator's own in-memory state to that persona's store, losing its own. Fix: an optional `persona` argument on both tools, so the coordinator addresses a worker by name without switching identity.
3. **Coordinator-to-worker and worker-to-coordinator addressing, both authorized without a reader claim - because a reader claim cannot cover this shape at all.** (Correction, Reviewer Round 111 R25: worker-to-coordinator addressing needs the caller to own *some* persona, per Section 3's own text - a reader-only session with no owned persona, this Reviewer's own shape, is refused when addressing the coordinator. "No special claim at all" below means no claim *beyond ordinary ownership*, not no requirement whatsoever.) `claimReaderRole` (`hooks/index.ts:1036, 1138, 3170`, also reached at session start on lost commons arbitration) is only ever reached through `agentic_identity` switching `sess.persona`, which also releases `persona:<previous>` (`hooks/index.ts:3112`) - so a session that owns `persona:coordinator` cannot also hold `reader:<worker>` for N workers without giving up its own persona each time it addresses one. (A *reader-only* coordinator, with no persona of its own, is the live counterexample - the Reviewer session holds `reader:dev`, `reader:reviewer`, and `reader:aios` simultaneously today, and this is a real, working alternative shape. It is rejected here because the coordinator needs its own supervisor lifecycle - restarts, a goal tree, a Discord thread of its own - which only an owned persona gets; a reader has none of that. So the choice is "the coordinator owns a persona, like a worker does" plus a new authorization rule for reaching *other* personas from that position, not an appeal to impossibility.) The new rule: the caller must hold `persona:<coordinatorPersona>` (the one configured coordinator name, `cfg.coordinatorPersona`, read beside `controllerTickMs` at `hooks/index.ts:648`) to address any *other* persona, **or** the target persona must equal `<coordinatorPersona>` (so any worker can push to the coordinator without holding any special claim at all - the coordinator's own name is the address, known config rather than a credential the worker must acquire). Both `agentic_say`'s owner-only denial (`hooks/index.ts:3731-3733`) and `agentic_inbox`'s matching owner-only denial (`:3768-3771`) are relaxed by exactly this rule: refused only when the target equals the caller's own persona (self-messaging stays blocked, for everyone, no exception); allowed for any other target when either side of the "or" holds. No new reader-claim path, no new tool.

   This alone is not sufficient for a record to actually reach a worker's model: `hasLiveReaderClaim` (`hooks/operator.ts:407-417`) matches only a `reader:<persona>` resource and has no notion of a coordinator or owner claim at all, so it gates the send (`hooks/index.ts:3736-3740`), the matching `agentic_inbox` check (`:3773-3777`), the delivery-tick filter (`:1336`, marks `"skipped"` at `:1345`), the urgent path (`:3846`), and the ask-answer delivery (`:1266`) - five places, not the three the first cut of this design named, that would silently swallow a coordinator's own record or a worker's push to the coordinator. Section 3 composes a new check at all five rather than assuming the existing gate already covers this shape. Without this, Section 4's labels are computed for records that never arrive.
4. **Provenance label.** Every delivered record today is submitted to the model as a flat `[OPERATOR] <text>` or `[OPERATOR, urgent] <text>` (`hooks/index.ts:1372, 3860`), with no distinction between the real operator (who no longer even uses this path since Discord attaches directly) and any reader session, coordinator included. Fix: label a record `[COORDINATOR] <text>` when the writer's session holds `persona:<coordinatorPersona>` in commons, computed at delivery time from the writer's live claims (not stored on the record at send, so a claim that changed hands between send and delivery is read as it stands at delivery - the same freshness `hasLiveReaderClaim` already uses elsewhere), and reserve `[OPERATOR]` for records that actually originate from the operator's own Discord channel path (untouched by this section - it never goes through this delivery code). A non-coordinator reader (the Reviewer, the relay) gets a distinct `[READER:<persona>]` label rather than either. This is a prerequisite for the FORK B decision below, not optional plumbing: without it, a worker cannot apply any coordinator-specific rule to coordinator text, because it cannot tell coordinator text from anyone else's. Round 106 is the live argument for why this matters now rather than later: the item 8.3 urgent break-in delivered a Reviewer steer into a *subagent's* tool-call result labelled `[OPERATOR, urgent]`, the subagent (correctly, per doctrine) refused to act on unverifiable injected text, and the worker reported to the operator that something on the machine could inject fake authoritative-looking messages - which was true, and is exactly the provenance gap this label closes. Section 4 below adds the further fix Round 106 asks for: the urgent break-in must never fire inside a dispatched subagent's own tool call, only the top-level session's.

**Machine-budget contention.** Confirmed live via `Get-Process` at council time: 4+ `claude` processes at 345-597 MB each, plus their node children. A coordinator adds one more process pair; each worker adds one more. The mechanism choice does not change this count. Two contention findings, both grounded in the live store rather than guessed: `listInboxRecords` and `hasLiveReaderClaim` each poll the one shared JSON file every tick per owner plus on a 5-second throttle per tool call, so K workers plus one coordinator is K+1 pollers on one file; and the store shows two separate clusters of multiple full-file `.bak` rewrites within a third of a second of each other, consistent with concurrent processes each writing a full snapshot in quick succession (confirmed as contention; not confirmed as corruption - all copies parsed as valid JSON with matching key counts). Mitigations, detailed in Section 5: the coordinator's own launch sets its tick cadence well above the worker default (a launch-time setting, no new knob); the existing closed-record roll to the append-only log stays in place; and `.kit/live-all.sh` gains a new refuse-at-start check - the whole gate does not run at all while any real fleet is live, not merely waits for it, per Section 5.

**Operating rule that falls out of the turn-serial constraint.** A worker's own turn runs 2-5 minutes; a message delivered mid-turn queues until it ends (confirmed live in this plan's own Rounds 100-103: a message sent to this worker mid-turn queued exactly this way). So: steers to one worker batch into one record per cycle rather than trickling in one at a time; `urgent` is reserved for a real stop-or-redirect, never for "what is your status"; and status is never asked of a worker in-band - the coordinator reads `agentic_inbox`, the worker's own `.agentic-personas.json` in its repo, and the commons entry, all of which are file reads with no turn cost to the worker.

## Sections of Work

### 1. Commons entry carries turn state and workdir
Model: opus
`hooks/commons.ts`'s per-session commons entry gains `turnStartedAt: number | null` and `workdir: string`. **Correction (Reviewer Round 111 R24 - this line was reported fixed in Round 110 and was not):** the commons entry is not written at turn start or turn complete today, only at `claimResource`/`releaseResource` call sites (`hooks/index.ts:1072, 1128, 3131`) - `turn.start` (`:2592-2600`) and `turn.complete` (`:2674-2676`) write the *heartbeat file* only. This section adds a commons-entry write at both of those two hooks, beside the existing `writeOwnerHeartbeat` calls there, so the new fields track a turn's lifecycle the same way the heartbeat file's own `turnStartedAt` already does. No existing reader of the commons entry breaks: these are additive fields.
Files in scope: `hooks/commons.ts`, `hooks/index.ts` (every commons-entry write site).
Tests: a harness case that a commons entry written mid-turn (at the `turn.start` handler) carries a non-null `turnStartedAt` and the entry's own `workdir`, and a control that `turn.complete` (`hooks/index.ts:2674-2676`, the same site that already clears the heartbeat's own turn stamp) clears the commons entry's copy back to null too.

### 2. Deferred status reads the commons entry, not the local heartbeat file
Model: opus
`agentic_inbox`'s deferred-status check (`hooks/index.ts:3784-3808`) reads the target persona's commons entry (Section 1's new fields) instead of the cwd-relative `.agentic-heartbeat.json`, so a coordinator in one repo correctly reads a worker in another repo as busy or free.
Files in scope: `hooks/index.ts`, `README.md:285` (describes today's heartbeat-file deferred read; Reviewer Round 111 R30 - updated to describe the commons-entry read instead).
Tests: a harness case with two simulated working directories/personas proving the deferred check reads the addressed persona's own commons state, not the caller's local heartbeat file; a control proving the same-repo case (today's only working case) still passes.

### 3. `persona` argument on `agentic_say` / `agentic_inbox`, authorized without a reader claim
Model: fable
Both tools take an optional `persona` argument; when given, the write/read targets that persona's inbox rather than `sess.persona`, with no identity switch.

**The self-message guard (Reviewer Round 109 F2 correction).** The naive reading - "denied when the target equals the caller's own persona" - breaks today's only working path: a reader's `sess.persona` *is* the persona it reads (`hooks/index.ts:1033-1036` joins as reader under `sess.persona`; `:3722` and `:3765` default the target to `sess.persona`), so that reading would deny the Reviewer's own `reader:dev` session from ever messaging `dev`. The real guard is narrower: denied only when the caller **owns** the target persona (`sess.isOwner` true and target equals `sess.persona`) - an owner talking to itself, which is pointless. A reader addressing the persona it holds a reader claim on is unaffected, exactly as today. An owner addressing a *different* persona than its own is not self-messaging and reaches the next check below.

**Reaching a persona the caller doesn't own or hold a reader claim on (the actual coordinator mechanism).** Neither `agentic_say`'s owner-only denial (`hooks/index.ts:3731-3733`) nor `agentic_inbox`'s matching one (`:3768-3771`) is the whole story once a `persona` argument can name a target the caller neither owns nor reads: allowed when either the caller holds `persona:<coordinatorPersona>` (coordinator addressing any worker), **or** the target equals `<coordinatorPersona>` and the caller owns some persona of its own (any worker escalating to the coordinator, no special claim beyond being a legitimate live persona owner - the coordinator's own name is the address). `cfg.coordinatorPersona` is read beside `controllerTickMs` (`hooks/index.ts:648`).

**The delivery-side gates (Reviewer Round 109 R8/F1, F4 - the critical gap the first revision only asserted, never actually composed).** Being allowed to *send* is not being allowed to *arrive*: `hasLiveReaderClaim` (`hooks/operator.ts:407-417`) matches only a `reader:<persona>` resource, full stop - it has no notion of a coordinator claim at all, so a worker's record addressed to the coordinator (`from` = the worker's own session, holding `persona:<worker>`, never `reader:coordinator`) is refused at the send gate, or, if it somehow got past that, marked `"skipped"` at the tick's delivery filter. Five call sites read this gate today and all five need a second, coordinator-aware check added beside the existing `hasLiveReaderClaim` call, not instead of it: `agentic_say`'s send gate (`:3736-3740`), `agentic_inbox`'s matching gate (`:3773-3777`), the tick's delivery filter (`:1336`, marks `"skipped"` at `:1345`), the urgent break-in (`:3846`), and the ask-answer delivery path (`:1266`, drops a coordinator's answer to a worker's open ask with `operator_skipped_no_claim` today - the fifth gate the first revision missed entirely). A new exported helper beside `hasLiveReaderClaim`, `hasLiveOwnerClaim(store, sessionId, persona?, opts?: { excludePersona?: string })` (checks `readAllClaims` for a live `persona:<persona>` claim held by `sessionId`; when `persona` is omitted, any live `persona:*` claim at all held by that session, except one matching `opts.excludePersona` when given), composes at each of the five sites as: `hasLiveReaderClaim(store, persona, rec.from) || hasLiveOwnerClaim(store, rec.from, coordinatorPersona) || (persona === coordinatorPersona && hasLiveOwnerClaim(store, rec.from, { excludePersona: "default" }))` - the first disjunct is today's existing reader path (untouched), the second is the coordinator addressing any worker, the third is any worker pushing to the coordinator, deliberately excluding a bare `persona:default` claim from satisfying it. **The `!== "default"` exclusion in the third disjunct (Reviewer Round 113 R44) is load-bearing until Section 6 lands:** every plugin-loaded interactive session claims `persona:default` today (Section 5's own ordering note says as much), so without this exclusion any plain chat session on this machine could push text into the coordinator's model the moment it exists, on no stronger a credential than having the plugin loaded at all. Excluding `persona:default` specifically means only a session holding a *named*, non-default persona claim - a real worker launched the way this spec's own launch recipe describes - can use this path; a plain chat session cannot, arming default or not.

Files in scope: `hooks/index.ts` (tool registrations and handlers for both tools, all five delivery-side gates named above, and `cfg.coordinatorPersona`'s read site beside `controllerTickMs`), `hooks/operator.ts` (the write/read helpers both tools call, and the new `hasLiveOwnerClaim` helper beside `hasLiveReaderClaim`), `README.md` (the Operator channel section, which today states both tools are reader-only and refused to the owner, and states the trust boundary as "a record whose writer holds a reader claim on the same persona" - `README.md:277-287, 318` - both need updating to state the coordinator exception).
Tests: both directions of the corrected self-message guard (an owner cannot message its own persona; a reader still can address the persona it reads, unaffected - this is the control that catches the F2 regression before it ships); both directions of the coordinator-claim requirement for reaching an unrelated third persona (refused without the claim, succeeds with it); a **delivery** test, not merely a send test, for the worker-to-coordinator direction: a worker's record addressed to the coordinator is actually submitted to the coordinator's model on the next tick (not marked `"skipped"`), and the same for the ask-answer path - a send-only test is exactly what let this gap ship once already; and, per R44, a control that a session holding only `persona:default` is refused on the worker-to-coordinator path even though it holds a live owner claim, since that claim alone is not proof of being a real worker.

### 4. Provenance labels: `[COORDINATOR]`, `[READER:<persona>]`, `[OPERATOR]` reserved; the urgent break-in stops crossing into subagents
Model: opus
At both delivery sites (`hooks/index.ts:1372`, `:3860`) and the ask-answer delivery (`:1323`), the label is computed at delivery time (not stored on the record at send) from the writer's live commons claims: `[COORDINATOR]` when the writer holds `persona:<coordinatorPersona>` (the config key Section 3 defines); `[READER:<persona>]` for any other reader, where `<persona>` is the persona the writer holds a live *reader claim* on (not necessarily the record's target - relevant once Section 3's coordinator exception lets a caller address a persona it neither owns nor reads); when the writer holds several reader claims at once (the Approach notes the Reviewer holds three today), the label names the record's target persona if it is among them, else the first one alphabetically (Reviewer Round 111 R26); `[WORKER:<persona>]` for a writer whose only live claim is an owned, non-coordinator persona - Section 3's third disjunct (a worker pushing to the coordinator) produces exactly this shape, holding `persona:<worker>` and no reader claim, and without this label it would fall through to the untouched `[OPERATOR]` literal, laundering a worker's own escalation as operator authority - the exact provenance gap this section exists to close (Reviewer Round 113 R33); `[OPERATOR]` reserved for the operator's own Discord-originated channel path, which does not go through this delivery code today and is untouched by this section. Uses `readAllClaims` (`hooks/commons.ts:154`), already used elsewhere for commons arbitration.

A stop needs no delegated authority to act on - surfacing it is enough. Only non-urgent, tick-delivered `[COORDINATOR]` records - which arrive as an ordinary `$.prompt.submit` turn, not tool-result context - carry Option 2's authority.

## Decisions

### FORK B: coordinator steer authority - decided 2026-09-12, Option 2, autonomy with judgment

**The question.** Once Section 4 ships, a worker can tell a coordinator's record apart from anyone else's. What still needed settling was the rule for what that label is allowed to do: when a worker receives a `[COORDINATOR]` steer that would change files inside its own approved plan, does it act on it directly, or hold for the operator's confirmation first? Two positions were on record from two live sessions working this exact repo (the worker's Round 101, the Reviewer's Round 103), and the design council's authority lens (Round 1) took a position between them rather than picking one outright.

**The ruling, the operator's own words in substance (Round 107):** agree wholeheartedly with the coordinator having the ability to steer the worker. The premise is autonomy, abstracting as many decisions away from the operator as possible. It is a fine line, easy to land on the wrong side of - a sibling project (`ai-os`) did, running 30-plus review-round loops building features nobody wanted - but largely the coordinator determines what stays aligned with the goals and product vision and directs that on its own, and what is divergent or problematic and needs a conversation to realign or decide. It will not get this right every time, and that is acceptable; the closer it gets, the better the output.

**What this settles, concretely:**
1. **Option 2 is the rule.** A `[COORDINATOR]` steer inside a worker's approved plan is acted on without an operator round trip. Option 1 ("unverified until the operator confirms") is retired for coordinator records specifically; it still holds for any record that is not machine-labelled `[COORDINATOR]` (a plain reader, the Reviewer's own steers), which is exactly why Section 4's label and Round 106's subagent fix are prerequisites, not plumbing - Option 2 is only ever as safe as the label that triggers it.
2. **The bound is judgment plus a closed exclusion list, not a per-message confirmation.** The checkable parts stay from the original Option 2 proposal: the worker ties the steer to a goal node in its own tree under an approved plan, the resulting act stays within that node's scope and the plan's own recorded commit model, and the act is none of a closed exclusion list - no push beyond the plan's commit model, no deploy, no settings/CLAUDE.md edits, no write outside the plan's own scope, no onward dispatch purely on message content, no shared-tier memory-lesson promotion, no instruction to skip the machine's heavy-process claim protocol. **This list is this spec's own enumeration inside the operator's ruling (Reviewer Round 109 F12, marking completed per Round 111 R23): the Reviewer proposed it in Round 103 and the operator read it as part of the FORK B ask before ruling, so it is accepted in substance, not invented after the fact - but it is marked here, and under Open Questions below, as a proposed exclusion list, operator to confirm or strike an item; Section 7 (the worker-side bound checks) does not start until that confirmation lands.** Beyond those mechanical checks, the operator's own line - aligned-with-goals versus divergent-and-needs-conversation - is the coordinator's judgment call to make, not a further checklist item. A wrong call lands on a branch and waits at merge: `agent_persona`'s branch protection (ruleset `protect-main`, id `22911862`) is confirmed active with `pull_request` required and `autoMergeAllowed: true` (Reviewer, Round 105, `gh` GraphQL read at 16:52Z) - a confirmed fact this Decision rests on, not a reported claim any longer, and no Open Question remains about it below.
3. **The escalation criterion belongs in the coordinator's own instructions, not the worker's, with a stated number rather than a deferred one (Reviewer Round 109 R12).** "Divergent and problematic enough to need a conversation" is the coordinator's own call to raise with the operator, not a rule the worker enforces on incoming steers. The guard against the named failure mode (the `ai-os` loop of many rounds building unwanted features) is a round cap of **two rounds per steer** - matching the cap the operator has already set on the `aios` worker today, rather than a number invented for this spec - plus a scope check against the plan's own Goal, both already in this kit's vocabulary (goal-tree round caps; the scope-adjudicator seat), rather than a human gate on every message. The coordinator's own operating instructions (Section 8, not Section 7 - Section 7 is the worker-side half, Reviewer Round 111 R19) state this plainly: *"If a steer would take more than two rounds to land, or the worker's own reading of it drifts from the plan's stated Goal, stop and raise it with the operator instead of pushing a third round."* Section 8 is where this actually gets built, not deferred further.
4. **The rollout order (Reviewer Round 109 R13, corrected per Round 111 R31): `ai-os` first, `Neuro-Evolution-Operations` not onboarded until the operator calls the `ai-os` run a success.** `NEO` is not a persona in this repository - it names `D:\Neuro-Evolution-Operations`, the operator's critical product repository and the coordinator's intended second worker repo. v2's coordinator mechanism is proven live against the `ai-os` repo's workers as a chronological experiment before the `Neuro-Evolution-Operations` repo gets a worker of its own under the coordinator; a future session executing this plan does not onboard it early on the strength of `ai-os` alone still being in flight.
5. **What stays open.** The kit's standing-grant rail rewrite (in flight as of this spec's authoring) is no longer a precondition for building Option 2 - the operator's ruling is the authority, not the rail - but it stays an alignment check: once the rewrite lands, re-read `skills/role/SKILL.md` and confirm the delegation chain it defines is still compatible with what this Decision states, and reconcile if not.

This Decision is recorded as the operator's ruling on the Reviewer's own thread (Round 107), overruling the worker's Round 101 position for coordinator-labelled records specifically. The worker's position stood as one live view weighed, not dismissed; it is recorded as considered and overruled by the operator, not by the Reviewer.
