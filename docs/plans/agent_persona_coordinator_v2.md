## Goal

Today, a "worker" is a `bin/supervise.sh` launch: one Sonnet-tier `claude -p` child, one repo, one persona, one Discord thread. The operator drives each one directly. v2 adds one Fable-tier "coordinator" persona that reads status across N workers in N repos, batches steers to them without blocking on their multi-minute turns, receives their findings and escalations, reports to the operator on its own thread, and - pending the operator's ruling on FORK B below - may dispatch bounded work to a worker without a human round trip per message. The mechanism is an extension of the existing commons-store inbox path (`agentic_say`/`agentic_inbox`), not a new transport. Discord stays the operator's channel; the coordinator does not read or post into a worker's thread.

## Approach

**Grounding.** This design was pressure-tested by a two-lens Fable-tier design council (Round 1, 2026-09-12) before being written down: an operability/reliability lens and an authority/safety lens, converged by a facilitator. Every claim about the plugin's own code below was independently confirmed against `hooks/index.ts`, `hooks/operator.ts`, `hooks/commons.ts`, and `bin/supervise.sh`, both by the council and, for the load-bearing ones, spot-checked again by this session before this line was written. The full council transcript is retained at `.kit/runs/v2-council-round1/` (copied out of the workflow's own transcript dir before archiving, per the memory note `a-run-dir-is-merge-evidence-until-the-merge-lands`).

**The rejected mechanisms, and why.** Two other transports exist on this machine and both were considered and rejected as the coordinator-to-worker channel:
- The harness's own peer tools (`ListAgents`/`SendMessage`): this plugin actively consumes `session.receive` events of kind `peer`/`peer-send-message` before the model ever sees them (`hooks/index.ts:694-712`), specifically so a peer message carries no steering authority. Using it as a coordinator channel means reversing that design decision and rebuilding deferred-status, urgent break-in, reply capture, and the reader-claim trust gate on a transport this plugin does not own. Its address is a live session id, which a `supervise.sh` relaunch mints fresh every time (Chapter 8.3's own proof: child-1, then child-2), while `persona:<name>` is the thing that actually stays stable across a restart.
- Each worker's own Discord thread: inbound authority there is the operator's own Discord account against a one-account allowlist; the relay's own instructions tell a worker to treat channel text as keyboard-equivalent operator steering. A coordinator posting there either launders its own text into operator authority with no way for the worker to tell the difference, or has no channel to post through at all, since the relay never tells one process which session serves another process's thread. Read access is closed the same way. Discord stays the operator's channel, full stop; the coordinator reports to the operator on its own thread, same as any worker does today.
- `DISCUSSION.md` (the append-only file the worker and Reviewer personas use today for handoffs): turn-serial, invisible to the plugin's own trust gate, and polled by hand. It works between two co-equal live sessions watching one repo; it does not scale to a coordinator directing N workers in N repos, none of which read it. v2 retires it as a steering path; the plan doc and the coordinator's own thread are the record going forward.

**The chosen mechanism: the commons-store inbox path, extended in four small places.** `agentic_say`/`agentic_inbox` already has everything this needs except cross-repo reach: a machine-checked writer gate (only a live reader-claim holder's record reaches the model, `hooks/index.ts:3736-3740`), a deferred-status view that doesn't block on a busy worker (`:3784-3808`), an urgent break-in that reaches a worker mid-turn through the `tool.call` hook's own `context` return (`:3830-3868`), reply capture, and a decision-log trail. Item 8.3 built these for the operator-to-worker direction; the coordinator reuses them rather than inventing a second version.

Four extensions, in order of what blocks the next:
1. **Cross-repo deferred status.** `heartbeatPath` is the literal string `".agentic-heartbeat.json"`, read relative to the process's own cwd (`hooks/index.ts:408, 425, 581`). A coordinator running in one repo can never see a worker in another repo as busy; it would read its own empty or irrelevant heartbeat file. Fix: publish `turnStartedAt` and `workdir` into the session's commons entry (`hooks/commons.ts:24-28`, keyed `commons:<sessionId>`, one entry per live session, already a machine-global store). Finding the right entry for a named persona is `commonsWinner(readAllClaims(...), "persona:<target>")` (`hooks/commons.ts`), the same lookup `shouldYieldCommons` already uses for arbitration - not a lookup this design invents.
2. **Addressing N workers.** `agentic_say`/`agentic_inbox` operate on `sess.persona` only. Reaching a specific worker today means an `agentic_identity` switch, which also swaps the coordinator's own in-memory state to that persona's store, losing its own. Fix: an optional `persona` argument on both tools, so the coordinator addresses a worker by name without switching identity.
3. **Worker-to-coordinator push, and coordinator-to-worker addressing, both authorized by the coordinator's own persona claim, not a reader claim.** `claimReaderRole` (`hooks/index.ts:1036, 1138, 3170`) is only ever reached through `agentic_identity` switching `sess.persona`, which also releases `persona:<previous>` (`hooks/index.ts:3112`) - so a session that owns `persona:coordinator` structurally cannot also hold `reader:<worker>` for N workers without giving up its own persona each time. Cross-persona addressing is therefore authorized a different way: the caller must hold `persona:<coordinatorPersona>` (the one configured coordinator name, `cfg.coordinatorPersona`, read beside `controllerTickMs` at `hooks/index.ts:648`) at call time, checked the same way `readAllClaims`/`commonsWinner` already checks any other claim. An owner is denied `agentic_say` **and** `agentic_inbox` today when the target is its own persona (`hooks/index.ts:3731-3733` and the matching `agentic_inbox` denial at `:3768-3771`); both denials are relaxed identically: refused only when target equals caller's own persona (self-messaging stays blocked for everyone), and additionally allowed, for a *different* target persona, when the caller holds `persona:<coordinatorPersona>`. No new reader-claim path, no new tool - the coordinator's existing ownership of its one persona is the credential.
4. **Provenance label.** Every delivered record today is submitted to the model as a flat `[OPERATOR] <text>` or `[OPERATOR, urgent] <text>` (`hooks/index.ts:1372, 3860`), with no distinction between the real operator (who no longer even uses this path since Discord attaches directly) and any reader session, coordinator included. Fix: label a record `[COORDINATOR] <text>` when the writer's session holds `persona:<coordinatorPersona>` in commons, computed at delivery time from the writer's live claims (not stored on the record at send, so a claim that changed hands between send and delivery is read as it stands at delivery - the same freshness `hasLiveReaderClaim` already uses elsewhere), and reserve `[OPERATOR]` for records that actually originate from the operator's own Discord channel path (untouched by this section - it never goes through this delivery code). A non-coordinator reader (the Reviewer, the relay) gets a distinct `[READER:<persona>]` label rather than either. This is a prerequisite for FORK B below, not optional plumbing: without it, a worker cannot apply any coordinator-specific rule to coordinator text, because it cannot tell coordinator text from anyone else's.

**Machine-budget contention.** Confirmed live via `Get-Process` at council time: 4+ `claude` processes at 345-597 MB each, plus their node children. A coordinator adds one more process pair; each worker adds one more. The mechanism choice does not change this count. Two contention findings, both grounded in the live store rather than guessed: `listInboxRecords` and `hasLiveReaderClaim` each poll the one shared JSON file every 10-second tick per owner plus on a 5-second throttle per tool call, so K workers plus one coordinator is K+1 pollers on one file; and the store shows two separate clusters of multiple full-file `.bak` rewrites within a third of a second of each other, consistent with concurrent processes each writing a full snapshot in quick succession (confirmed as contention; not confirmed as corruption - all copies parsed as valid JSON with matching key counts). Mitigations: the coordinator's own tick cadence stays well above the worker default; the existing closed-record roll to the append-only log stays in place; and `.kit/live-all.sh`'s own running-lock is extended to refuse a whole-gate run while more than one live `persona:` claim exists in the shared store, so a live coordinator/worker fleet and a whole-gate run never overlap by accident.

**Operating rule that falls out of the turn-serial constraint.** A worker's own turn runs 2-5 minutes; a message delivered mid-turn queues until it ends (confirmed live in this plan's own Rounds 100-103: a message sent to this worker mid-turn queued exactly this way). So: steers to one worker batch into one record per cycle rather than trickling in one at a time; `urgent` is reserved for a real stop-or-redirect, never for "what is your status"; and status is never asked of a worker in-band - the coordinator reads `agentic_inbox`, the worker's own `.agentic-personas.json` in its repo, and the commons entry, all of which are file reads with no turn cost to the worker.

## Sections of Work

### 1. Commons entry carries turn state and workdir
Model: opus
`hooks/commons.ts`'s per-session commons entry gains `turnStartedAt: number | null` and `workdir: string`, written wherever the entry is written today (session start, turn start, turn complete, heartbeat tick) using the existing `writeOwnerHeartbeat`-style call sites as the pattern to mirror. No existing reader of the commons entry breaks: these are additive fields.
Files in scope: `hooks/commons.ts`, `hooks/index.ts` (every commons-entry write site).
Tests: a harness case that a commons entry written mid-turn (at the `turn.start` handler) carries a non-null `turnStartedAt` and the entry's own `workdir`, and a control that `turn.complete` (`hooks/index.ts:2674-2676`, the same site that already clears the heartbeat's own turn stamp) clears the commons entry's copy back to null too.

### 2. Deferred status reads the commons entry, not the local heartbeat file
Model: opus
`agentic_inbox`'s deferred-status check (`hooks/index.ts:3784-3808`) reads the target persona's commons entry (Section 1's new fields) instead of the cwd-relative `.agentic-heartbeat.json`, so a coordinator in one repo correctly reads a worker in another repo as busy or free.
Files in scope: `hooks/index.ts`.
Tests: a harness case with two simulated working directories/personas proving the deferred check reads the addressed persona's own commons state, not the caller's local heartbeat file; a control proving the same-repo case (today's only working case) still passes.

### 3. `persona` argument on `agentic_say` / `agentic_inbox`, authorized by the coordinator's own claim
Model: fable
Both tools take an optional `persona` argument; when given, the write/read targets that persona's inbox rather than `sess.persona`, with no identity switch. The owner-only denial on `agentic_say` (`hooks/index.ts:3731-3733`) and the matching owner-only denial on `agentic_inbox` (`hooks/index.ts:3768-3771`) are both relaxed by the same rule: denied when the target persona equals the caller's own persona (self-messaging stays blocked, for everyone, no exception); allowed for any other target persona only when the caller holds `persona:<coordinatorPersona>` (Section 6 names the config key) at call time, checked live via `readAllClaims`/`commonsWinner` (`hooks/commons.ts`) the same way the plugin already checks any other claim. A plain worker's owner-only denial for its *own* persona is unchanged in every other respect. This is the section carrying the real judgment call (composing the existing owner/reader gates with a third, coordinator-specific one without opening self-messaging or letting any owner spam an unrelated persona's inbox) and is why it is fable-tier, not sonnet.
Files in scope: `hooks/index.ts` (tool registrations and handlers for both tools, and `cfg.coordinatorPersona`'s read site beside `controllerTickMs`), `hooks/operator.ts` (the write/read helpers both tools call), `README.md` (the Operator channel section, which today states both tools are reader-only and refused to the owner - `README.md:277-287, 318` - and needs its own update to state the coordinator exception).
Tests: at minimum, both directions of the self-message guard (a persona cannot message itself even via the new argument, coordinator claim or not), and both directions of the coordinator-claim requirement (an owner with no `persona:<coordinatorPersona>` claim is refused a cross-persona call; the coordinator succeeds) - a silent bypass of either is the expensive failure here.

### 4. Provenance labels: `[COORDINATOR]`, `[READER:<persona>]`, `[OPERATOR]` reserved
Model: opus
At both delivery sites (`hooks/index.ts:1372`, `:3860`) and the ask-answer delivery (`:1323`), the label is computed at delivery time (not stored on the record at send) from the writer's live commons claims: `[COORDINATOR]` when the writer holds `persona:<coordinatorPersona>` (the config key Section 3 defines); `[READER:<persona>]` for any other reader; `[OPERATOR]` reserved for the operator's own Discord-originated channel path, which does not go through this delivery code today and is untouched by this section. Uses `readAllClaims` (`hooks/commons.ts:154`), already used elsewhere for commons arbitration.
Files in scope: `hooks/index.ts`; `.kit/controller-tick-test.mjs` (the existing assertion at `:672-673` that the general drain produces exactly one `[OPERATOR]`-prefixed prompt is updated to expect `[READER:<persona>]` for a plain reader); `.kit/live-restartrequest-test.sh` (its standing instruction at `:77-81` is keyed on the literal `[OPERATOR]` prefix and is updated to match whichever label that suite's own reader now carries, or the suite's reader is given the coordinator claim, whichever keeps its restart proof honest); `README.md:312, 314` (documents the `[OPERATOR]` marker; updated to describe all three labels).
Tests: one case per label (coordinator claim present -> `[COORDINATOR]`; a plain reader claim, no coordinator -> `[READER:<persona>]`), and a control that the operator's own Discord-origin path still carries no prefix at all (that path only sets a flag, `hooks/index.ts:3882`; it was never prefixed, and this section leaves it that way).

### 5. Contention guards
Model: sonnet
A `coordinatorTickMs` knob (code default, `hooks/index.ts`, matching the convention of `askReraiseWindowMs` and its siblings - no `plugin.json` entry), set to 60000 (double the 30000 default `controllerTickMs` falls back to at `hooks/index.ts:648`, and six times `bin/supervise.sh`'s own 10000 default at `:119` - either reading of "well above" is satisfied by this one value). `.kit/live-all.sh`'s running-lock extended to also refuse start while any live `persona:` claim other than the caller's own exists in the shared commons store (not "more than one": a single live worker or coordinator already means the box is not quiet), read with `wait_persona_free`'s existing node one-liner (`bin/agentic-common.sh:147-169`), widened from its current `persona:default`-only check (`:164`) to any `persona:` resource.
Files in scope: `hooks/index.ts` (the `coordinatorTickMs` knob), `bin/agentic-common.sh` (`wait_persona_free`), `.kit/live-all.sh`.
Tests: a case that the extended lock refuses to start with one foreign live persona claim present (not two - one is already the threshold), and a control that it starts clean with zero.

### 6. Coordinator launch shape, config key, and persona/thread naming
Model: sonnet
The coordinator's persona name is read as `cfg.coordinatorPersona` beside `controllerTickMs` (`hooks/index.ts:648`'s config-reading site), default `coordinator`, settable the same way `cfg.persona` already is. The coordinator is launched exactly like a worker - `bin/supervise.sh <repo> <persona> <permission-mode> --rundir <path>` per the memory record `a-second-worker-launches-in-its-own-repo-with-a-unique-persona-name` - with `MODEL` set to the Fable model id, `<persona>` set to the same name as `coordinatorPersona` (or `coordinatorPersona` overridden to match, whichever the operator finds clearer), and its own `--channel-name` (its own Discord thread, distinct from every worker's). No new script. The launch recipe omits `--dev`: Section 0 item 3 retires the `--plugin-dir` runtime for the installed marketplace plugin as a v2 prerequisite, and every worker and the coordinator load the same installed copy, per that section. This section also checks `bin/supervise.sh` for any assumption that a worker never messages other personas, and lifts it if found (checked against the actual script, not assumed).
Files in scope: `bin/supervise.sh` (the config emission, and read for any such assumption), `hooks/index.ts` (`cfg.coordinatorPersona`'s read site), `README.md` (the quickstart gains the coordinator launch shape as a documented pattern, per item 6 of v1).
Tests: none; acceptance is proved live: the launched process holds `persona:<coordinatorPersona>` in the commons store, its own Discord thread opens, and one `agentic_inbox` call with `persona: <a live worker's name>` returns that worker's own records.

## FORK B sits outside "Sections of Work" numbering above by design

### Decision ask: coordinator steer authority (FORK B)

**Situation.** Once Section 4 ships, a worker can tell a coordinator's record apart from anyone else's. What it still needs is a rule for what that label is allowed to do. Two positions are already on record from two live sessions working this exact repo, and the design council's authority lens took a position between them rather than picking one outright.

**The decision.** When a worker receives a `[COORDINATOR]` steer that would change files inside its own approved plan, does it act on it directly, or does it hold for the operator's confirmation first?

**What it blocks.** Every worker turn costs 2-5 minutes; a human confirmation costs an unbounded amount of time. With N workers, "hold everything file-changing for the operator" makes the coordinator a relay with better prose rather than something that actually coordinates. Shipping v2 with the mechanism but no answer here means the coordinator can observe and report but never usefully dispatch.

**Option 1 - unverified until the operator confirms (the worker persona's standing position).** A coordinator steer is treated exactly like today's Reviewer steers: informative, actionable in spirit, but any file change waits for the operator's explicit word. Cost: throughput is bounded by the operator's own response time, which is the thing a coordinator exists to remove.

**Option 2 - a bound the worker can check on its own surface (the Reviewer's position, refined by the authority lens).** A `[COORDINATOR]` steer is in-grant, and the worker acts without a human round trip, only when all of: the worker can tie the steer to a goal node in its own tree under an approved plan; the resulting act stays within that node's scope and the plan's own recorded commit model; and the act is none of a closed exclusion list (no push beyond the plan's commit model, no deploy, no settings/CLAUDE.md edits, no write outside the plan's own scope, no onward dispatch purely on message content, no shared-tier memory-lesson promotion, no instruction to skip the machine's heavy-process claim protocol). Anything arguable against that list routes to the operator, same as today. Cost: trust extends to whatever local process currently holds `persona:<coordinator>` in the shared commons store, since that claim - like any commons claim - goes stale at 90 seconds and can be inherited by a different process the same way the Reviewer once inherited `dev` (memory: `killing-the-owner-child-hands-the-persona-to-the-reviewer.md`).

**What the operator should know before ruling.** Two facts this spec leans on are reported, not run: branch protection with auto-merge-on-approval is active on `agent_persona` (reported by the Reviewer in `DISCUSSION.md`, not independently confirmed by the council or this session with `gh api`) - if true, it's the argument for Option 2, since a wrong dispatch under grant still lands on a branch and waits at merge, moving the human gate from every dispatch to every merge rather than removing it. The kit's own standing-grant rail (`skills/role/SKILL.md`, read at a pre-rewrite mtime) already defines a Coordinator-to-Expert-to-Worker chain shaped like Option 2 - the warrant is a record on the worker's own surface, never the message - but that rail is being rewritten, timing unknown, and may not keep this shape.

**Recommendation.** Option 2 in its checkable form (the goal-node tie plus the closed exclusion list), contingent on: (a) confirming branch protection/auto-merge really is active on this repo, and (b) the rail rewrite landing with the same or a compatible chain. Until both are confirmed, ship Section 4's label with workers defaulting to Option 1 behavior - which is today's actual state regardless of what this decision ask says - and revisit once the two open facts resolve.

**If this goes unanswered**, v2 ships the mechanism and the label with Option 1 as the default worker behavior, since that is what today's code already does with no change.

## Out of Scope

- Cross-machine coordination (the commons store is one machine-global file; a second machine is a different problem).
- A UI or dashboard for the coordinator's view of N workers; `agentic_inbox`/`goal_status`/the commons store are the interface for now.
- Automatic lesson promotion to a shared kit memory tier; the council named this as needing at least the same external-anchor bar item 8.2 already enforces plus a review gate, and it is deliberately left to a future section once the coordinator itself has run for a while and has real cross-repo lessons to promote.
- Retiring `DISCUSSION.md` as a physical file (only as a steering path going forward); its history stays as the record of v1's own build.
- Any change to the Discord relay, the broker, or `discord-channels` - the coordinator does not touch that surface at all in this design.
