## Goal

When this ships, every message a persona receives is held by the plugin as a turn record, in code, before the model reads it. A message with no active goal opens a record. A message that steps an active goal attaches the record to it. A message that carries on an open record continues it. At the turn's end the plugin decides whether the turn delivered what the record asked, from fixed rules first and from Jev, TypeSafe's classifier, only on what the rules leave open, and closes the record when it did. A closed record drops out of view, so the goal tree never becomes a chat log and an answered question is never nudged. An open record that ended on a `BLOCKED:` or `WAITING:` lead, an open ask or a live background agent is in flight; any other open record is a durable boundary, so Plan A's turn-end banking compacts at it. Both Jev questions ship in shadow, journaled with the state the operator's labelers need and an outcome each, and each goes live only when the operator names it in a settings list, one question at a time. A record that touched a plan document is promoted into the goal tree through the autonomy dial, and a record the operator turned into a goal or a task by the model's own tool call is marked promoted, so no record dangles beside the entry it became.

## Intent

The frame, in the operator's words on 2026-09-24: every message has a purpose, so every turn should set, follow or complete a goal, even one that lasts a single turn. The constraint: a turn-scoped goal must close automatically when the turn ends, or the idle controller nudges an answered question. "Answer delivered" must count as "goal complete", recorded deterministically rather than by the model remembering to call `goal_done`.

What done needs to do: hold every external message as a record in the store, decide at turn end whether it was delivered, keep records out of the goal tree and out of the nudge, make an idle open record a compaction boundary, ship the two Jev questions in shadow with the state and outcomes a labeling pass needs, give the operator one settings switch per question to go live, and mark a record promoted when it becomes a goal or a task.

What done does not need to do: no Haiku decision on either question, because the operator ruled that Jev makes the quick calls and Haiku only words a new goal. No automatic goal from a message, because the ruling is that a message with no active goal opens a turn record and never a real goal. No nudge on a record, because a record is not a goal entry. No automatic close of a goal entry from a delivered record, because the task-list plan's ruling keeps goal completion with the goal. No retirement of the `untracked_work` line, because the supervisor reads it on a clean exit. No labeling pass inside the plugin, because the promotion bar is judged offline from the journal.

Alternatives refused:
- Haiku decides both questions with Jev in shadow, as the four existing sites do. Refused: the operator ruled Jev makes these calls, and a Haiku decision here would add a second judge to retire later.
- A turn record is a goal-tree leaf. Refused: the operator ruled records stay out of the tree as small leaves that close and drop out of view, and a tree leaf is scored, budgeted and activated one at a time.
- The turn record is a task in the task-list tier. Refused in that plan: a task belongs to an active goal and never exists without one, while a record is an intention with no goal yet or ahead of one.
- A record that was not delivered is dropped at the next message. Refused: the operator agreed an undelivered record carries over across turns with a time-out backstop, so a follow-up lands on the intention it continues.
- Promotion sends a `[PROPOSAL]` at the propose level whenever a record touches a plan document. Refused: the architect persona authors plan documents for other workers every turn, so that branch would propose the architect's own specs to itself. Plan activity stores the plan path and sends nothing at propose; the standing block already tells a persona how to propose.
- The plugin decides compaction from the record itself. Refused: the kit gate stays the sole decider, and Plan A's banking step is the one place the persona side speaks to it; this plan only adds a rule to Plan A's predicate.

## Approach

**The turn record is a field beside the goals array, not a node in the tree.** `AgentState` gains `turnRecords: TurnRecord[]`, seeded empty by a version migration, capped, and reaped on load. A record carries `id`, `text`, `openedAt`, `status`, and optionally `turnId`, `goalId`, `planPath`, `taskId` and `closedAt`. Its `status` is a closed set of five: `open`, `delivered`, `superseded`, `expired`, `promoted`. At most one record is `open` at a time; a message Jev reads as a new goal or a step supersedes the open one, whether that one is bare or attached. `turnId` is absent at the open, since `prompt.submit` runs before the turn id exists, and `turn.start` stamps it on the open record for every route, from the origin reading whose text the turn opens with. `goal_status` prints the open record on one line above the tree, so the operator can see it without reading the store. A record is never a goal entry, so nothing that reads `goals`, the tick's idle branch and the nudge among them, sees it. The task-list plan's `tasks` field is the exact sibling for the schema, the migration, the cap and the load-time reap.

**Opening runs in the real `prompt.submit` hook, which fires only for a genuine external turn.** The plugin's own submits, nudges, deliveries and the idle proposal, bypass that hook, so the seam sees exactly the messages the operator, the coordinator, a peer or the harness sent. Fixed rules run first, in order, on the owner session only; a reader-armed session opens nothing. A priming or supervisor-ask turn opens nothing. A turn arriving while an ask is open is the answer to that ask: it opens one record attached to the asked entry, superseding any open record, and asks Jev nothing, since the handler already closes the ask on that same turn. Then the turn-open question, `turn-open`, a `choice` over `new-goal`, `step` and `continuation`, is put to Jev over the state `active_goal`, `open_record` and `message`. Live, `new-goal` opens a record worded by Haiku, `step` opens a record attached to the active entry, and `continuation` keeps the open record and moves its `turnId` to this turn. Not live, or on any failure, the fallback is continue-or-attach-or-bare-record: where a record is open it continues, else a record attached to the active entry where one is active, else a bare record whose text is the message's first 80 characters, and never a goal. So under fallback an open record carries over until it expires, which is the agreed carry-over. Haiku words a new goal only on a live `new-goal` verdict, through the same `$.model.complete` call shape the controller's reason call uses, bounded to one line, with the excerpt as its fallback.

**Closing runs at the persona's own turn boundary in `turn.complete`.** The step sits under the same true-boundary guard the backstop-turn-guard plan and Plan A use: the completing id equals `currentGateTurnId` and, after this completion's own `openTurns` delete, `turnIsOpen()` is false, so a background subagent's completion closes nothing. Fixed rules run first, in order, and each decides without Jev. A skipped turn, one aborted, errored, refused or with no answer, leaves the record as it was. A closing text whose first line is a `BLOCKED:` or `WAITING:` lead, read with `readStatusLine(e.answer)`, leaves the record open and in flight. A turn that opened an ask, or ends with one open, leaves the record open and in flight. A turn with a live background agent, read from `$.agent.list()` as any agent whose `status` is `running` and whose `parentId` is absent, leaves the record open and in flight. What the rules leave is the delivered-versus-mid-work residue. There the turn-disposition question, `turn-disposition`, a `choice` over `delivered`, `mid_work` and `blocked_or_waiting` with the ASSISTANT experiment's clarified descriptions verbatim, is put to Jev over the state `active_goal`, `this_turn_was_asked` (up to 1,200 characters), `agent_final_message` (up to 3,000 characters) and `turn_tool_activity`. Live, the record is delivered when the answer's `probabilities.delivered`, which every `ChoiceAnswer` carries per option, is at least `TURN_DELIVERED_THRESHOLD` (0.5), else it stays open. The rule "a turn that opened an ask" reads `sess.state.pendingAskId` after the handler's own `ASK:` marker step, which is what sets it. Not live, or on any failure, the fallback is not delivered, which keeps the record open and costs at most one nudge on a goal entry, and nothing on a record. The experiment measured this question at 95% agreement on 110 rule-free turns with one false delivered at the threshold, and its promotion bar is recorded under Operator Verification.

**`turn_tool_activity` is built by the plugin from its own `tool.call` view.** The handler already counts work tools; this plan adds a per-turn ring of the last eight tool names and a set of flags reset at turn start: a plan document under `docs/plans/` read, a plan document edited, a commit, a push, an agent dispatched, `goal_done` called, the reply tool called, and the work-tool count. A commit or push is read from a `Bash` call whose command carries `git commit` or `git push`, which is a text read of the argument and not a run. That list is the specification of the state; the ASSISTANT's experiment scripts are background and nothing in this repository depends on them.

**Jev goes live one question at a time, by name, from the settings.** The plugin reads `jevLive` beside `jevMode`: an array of question set ids, empty by default, each of which must be one of the two ids this plan ships, held in `PROMOTABLE_SET_IDS`. A question named there is asked live; any other question the plugin asks stays in shadow. The seam's one request path gains the mode `live` beside `shadow`: both send, and `live` takes its own timeout, `LIVE_TIMEOUT_MS` (2,000 ms), because a live call is awaited on the turn-end path where a shadow call is not. A new wrapper, `liveAsk`, is the one entry point for the two questions. Where the question is not in `jevLive`, or `jevMode` is not `shadow`, it calls `shadowAsk` itself and returns null. Where it is live, it awaits the seam, journals the call and its answer with mode `live`, and returns the validated answer, or null on any of the closed failure reasons. So a caller sees one shape, an answer or null, and null always means the stated default for that question. `shadowAsk` is untouched. `jevLive` reaches the child the way `jevMode` does: a roster field the keeper maps to `JEV_LIVE`, which `emit_settings_json` writes under both plugin ids and `ensure_settings_jev_live` carries onto a provided file, refusing any id outside the promotable set with no file left behind. Under `jevMode` `off`, `jevLive` is read but nothing is sent, so the fallbacks decide; the kill switch stays a kill switch.

**Each question is journaled with an outcome the plugin can observe.** `turn-open`'s outcome is `record_delivered_within`: whether the record that call opened or continued reached `delivered` within `RECORD_OUTCOME_TURNS` (3) of the persona's own turns, written once as `true` or `false`. `turn-disposition`'s outcome is `next_prompt_kind`: the verdict the next external message took on `turn-open`, one of its three option ids, or `none` where the record expired first, written once against every disposition stamp still pending on that record, since a record open across several turn ends has several. Both join by the call's stamp id the way `next_score` and `chapter_within` do. The journal's closed set of outcome kinds gains both.

**An open record is a durable boundary unless it is in flight.** Plan A's banking predicate reads the lead line and the plan holder's Chapter advance. This plan adds one rule to that predicate: a live background agent, read as above, makes the turn not durable. An open record with no lead, no open ask and no live agent is idle, and idle is durable, so Plan A banks. Nothing else in the compaction path changes, and the kit gate is not touched.

**Promotion has three routes, and the plugin drives one of them.** Route one, a record into the tree on plan activity: at the true turn boundary, before the disposition close so a plan-touching record is promoted rather than closed, where the open record has no `goalId` and this turn wrote or edited a file whose path matches `PLAN_PATH_PATTERN` after the working-directory prefix, the record takes that `planPath`. A read alone does not count, and the architect persona the settings name never takes route one, because it authors plan documents for other workers by charter. Then the autonomy level decides, read from `AgentState.autonomy`. At `propose` nothing more happens; the standing block already tells the persona to propose. Where no goal tree exists the record keeps `planPath`, no entry is added, and one decision says so, since only the operator opens a tree. At `plan-and-ask` and `plan-and-start` the plugin adds a plan entry with that `planPath` through the same path the autonomy-dial plan gives `goal_add` at that level, so the entry is paused awaiting the operator's yes at the one and active at the other, and the record becomes `promoted` with the new entry's id. Route two, the operator's word: a `goal_create` or `goal_add` the model calls in a turn holding an open record marks that record `promoted` with the new node's id, and a `task_add` in a turn holding an open record attached to the active entry marks it `promoted` with the task's id. Route three, a task into a goal: `goal_add` takes an optional `taskId`, copies that task's text as the title where none is given, and reaps the task. No route auto-opens a goal from a message, which is the ruling.

**The `[NO GOAL]` block stops asking for a goal on every request.** Today it tells the model to call `goal_create` for any request, size aside. Under this plan the plugin holds the request as a record, so the block says so and tells the model to open a goal only for an effort that outlasts this turn or that the operator asks it to track. The text is one ledger entry, regenerated.
