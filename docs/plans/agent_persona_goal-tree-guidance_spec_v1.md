# A plan document handed to the goal tools becomes one plan entry, the round budget asks instead of blocking, and a skill tells every persona how to use its goal tree

Status: Ready
Commit Model: Branch-and-PR
Created: 2026-10-01

## Goal

When this ships, a goal created from a plan document is one plan entry that the document closes, and the automatic planner never breaks such a goal into batches. An entry that reaches its round budget is asked whether it is done, still going, too big or blocked, and is never blocked by the count alone. A queued plan entry closes when its document reads Complete or moves to the archive, whether or not it is the active entry. Every tool description says what its code does. A persona reads one skill, named in its priming, that states what a goal is, when to open one, when to close one, and how tasks sit under it.

## Intent

The operator's frame, on the ASSISTANT persona's relay thread on 2026-10-01, as the ASSISTANT recorded it: a goal is anything that opens medium- to long-term work, and sits above a task. It can be as small as one request answered in full or as big as "refactor this codebase". A plan document is one kind of goal, not the model for all of them. Tasks are the small steps under a goal, and each ties back to it. The operator listed what no written guidance covers: creating a goal, cleaning one up, using the goal tree as the working list, writing to it and removing things from it, and keeping tasks separate from goals with each tied back.

The trigger. On 2026-09-30 the DEV-DISCORD persona's root goal "Finish the Session Activity Signals plan" was created with the plan document's path passed as `roadmapPath`, which is the planner's input, and with no `planPath`. The planner broke the plan into four batches of entries over five hours, each batch re-listing the sections still open, and every entry carried a round budget and no document to close it. The persona closed all thirteen entries, the twelve and the root, by hand on 2026-10-01.

What done needs to do: make a plan document handed to `goal_create` produce one plan entry and no planner job; close a queued plan entry from its document without waiting for it to be active; replace the round-budget block with a check-in the persona answers; make the tool descriptions true; and give every persona one skill that answers the operator's five gaps.

What done does not need to do: no change to how the planner plans a root that names no document, since that route is for work with no plan, so a planner-made entry keeps its block and the planner's own caps; no new status vocabulary beyond `WORKING:`, `WAITING:` and `BLOCKED:`; no status-card change in the relay repository; no rewrite of `docs/architecture.md`, which stays the maintainer's reference; no hand edit of any persona store; no change to the kit's coordinator skill, because the coordinator's queueing rule already lives in its priming text.

Alternatives refused:
- Block an entry that shows no progress instead of one that spends its rounds. Refused by the operator on 2026-10-01: a stuck session is a failure a block cannot fix, and activity cannot stand in for progress, so the plugin asks rather than measures.
- Have the planner refuse a root whose objective names a plan document and ask for the path. Refused: the incident's root named the document in `roadmapPath`, not in its objective, so the tool's own argument is the place to read it, and a refusal on prose would miss the next phrasing.
- Put the doctrine in the tool descriptions alone. Refused: a description is read at the moment of one call and carries one rule; the reasoning across tools, which is what the operator's five gaps ask for, needs one document a persona reads before its first call.
- Put the doctrine in the kit's operating doctrine or coordinator skill. Refused: the goal tools are this plugin's, every persona runs this plugin, and the kit's corpus is under a size cap with its own lean pass in flight.
- Keep a fixed cap and raise the default. Refused: the DEV-DISCORD entries spent 5 to 14 rounds each on real work, so no number separates a long section from a loop.

Rulings after the spec shipped, each appended dated:
- 2026-10-01, by the operator on the ASSISTANT's thread, before this spec: the stall check is a check-in, not a block, and the ARCHITECT reviews the plan before anything is queued.

## Decisions

**Item 1. Where the doctrine lives.** Ruled by the ARCHITECT, 2026-10-01, as the ASSISTANT's draft left it to the architect: a plugin skill `skills/goal-tree/SKILL.md`, loaded by the priming's skill-load sentence before the first goal tool call, with the one-line rule of each tool in its own description. The kit's coordinator skill takes no paragraph: the coordinator's queueing rule lives in `bin/supervise-holder.sh:340` already, and the kit's corpus is under a size cap with its own lean pass in flight. Alternatives: the standing block, refused because it is three sentences sized by the injection ledger and rides every prompt; the kit doctrine, refused as above.

**Item 2. Whether the check-in extends the nudge-lead vocabulary.** Ruled by the ARCHITECT, 2026-10-01: no. Done is `goal_done`, a split is `goal_add`, and still going, waiting or blocked are the three leads sessions already write.
