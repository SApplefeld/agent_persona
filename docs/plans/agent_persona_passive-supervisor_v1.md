## Goal

The supervisor becomes something an operator starts once and talks to. Started with no goal, it waits quietly and holds its persona. A goal arrives as a sentence in a chat, not as a tool call. During a goal the operator can redirect, pause, add, or drop work by talking. When the goal completes the supervisor goes quiet again and waits for the next one. The chat is a Discord thread or a proxy agent, and only text from a holder of a reader claim ever steers the worker.

Every numbered item below is a goal with its acceptance, not a task list. The worker decides how.

## Roadmap

1. Passive start. `bin/supervise.sh` launched with no `--prompt` runs indefinitely: the child idles with its persona claimed and heartbeating, the supervisor logs that it is waiting, and neither idleness nor an empty goal tree is read as a crash, a restart trigger, or completion. Proof: a run with no prompt is still alive and logging after ten minutes, with zero restarts.
   - The pre-gate, the EOF stop path, and the exit codes keep their current meaning.
   - The supervisor also changes into the work directory itself, so launching it from elsewhere no longer splits the store from the poll.

2. A goal arrives by conversation. An operator message delivered through the reader channel, phrased as a request in plain words with no tool named, leads the worker to open a goal tree and begin planning, and the worker's reply states the goal it took in one line. Proof: the decision log shows the operator turn, then `goal_create`, then `planning_fired`, and the reader's inbox holds the one-line confirmation.
   - A one-step request opens a goal too (Reviewer, 2026-09-11). The plain prompt with no tool named, which is what this item asks for, does not reliably open a goal: the child reads a one-file task as too small for the goal tree and writes the file with no `goal_create`, so nothing records the request, the scorer has no leaf to close, and the supervisor's return to passive never sees a root complete. Chapter 2's own proof prompt named `goal_done`, which is why it passed. Required: every operator request opens a goal before the work starts, whatever its size, and the `[NO GOAL]` reminder says so in words a cost-conscious model does not argue with; how hard the reminder pushes, and whether the controller opens the goal itself when a turn ends with work done and no tree, are the worker's design call, recorded in the Chapter. Proof: a harness case for the reminder path with a control, and the `goalconvo` suite green on the item 7 stamp with the plain prompt, since item 7's whole gate cannot close around a red that is a roadmap gap.

3. Steering during a goal. While plans are active, operator messages can add a plan, drop one, change priority, pause, and resume, and the worker answers each with what it changed. Proof: a mid-run message produces a recorded decision naming the change and a matching change in the goal tree, for at least add, drop, and pause.
   - The roadmap file is already re-read at every planning event; a steer that edits the roadmap is one acceptable mechanism, and a steer that acts on the tree directly is another. Both are recorded.
   - An ask record carries the worker's full question. Today the stored `question` is cut near one hundred characters, so the reader sees a fragment; the reader must see what the worker asked.

4. Quiet between goals. When the root completes, the supervisor returns to the passive state of item 1 instead of exiting, and a second goal given by conversation in the same supervisor lifetime runs to completion. An explicit shutdown request from the operator stops the child by the EOF path and exits 0. Proof: two goals completed and one clean shutdown in one `supervisor.log`.

5. A chat channel. Text typed in a Discord thread reaches the worker as an operator turn, and the worker's replies and open asks appear in that thread. The shape is decided (operator, 2026-09-11): the channel is native, not a proxy session. The supervised child is itself the session bound to a Discord thread, the way every session started through `D:\discord-channels\wrapper\Enter-ClaudeSession.ps1` gets its own thread today: text in the thread arrives in the child as a channel event, the child answers with the relay's `reply` tool, and the broker's one-account allowlist is the authorization. No second model sits between the phone and the worker, nothing polls, and no message round-trips through the shared store. The proxy shape is rejected: in use the proxy session confused its own conversation with the relayed one, its polling loop was either slow to steer or noisy in the thread, and every message cost a store write and read. Proof: a message from a phone produces an `[OPERATOR]` turn in the decision log with no proxy session live, and the reply is visible in the thread.
   - The supervisor launches the child with the channel attached, so a supervised run has a thread from its first turn. Whether the relay attaches to a headless `claude -p` stream-json child is the first thing to establish; the wrapper's notes contemplate a `-p` launch, and if it does not hold, the fix goes to the relay side in `D:\discord-channels`, not to a proxy.
   - One thread per supervisor, for its whole lifetime. The broker binds a thread to a session ID and every child the supervisor launches is a new session, so a restart would open a new thread and the operator would follow a trail of short threads instead of one conversation. The supervisor's children must land in one persistent thread across restarts, with one line in the thread saying a restart happened. This is a broker-side change in `D:\discord-channels`, and the worker builds it (operator, 2026-09-11): under a plan document in that repository's `docs/plans/`, on a branch with a pull request, never a direct push to its trunk. Interactive sessions started through the wrapper keep one thread per session. This item's Chapter names that plan and its PR. The stale `docs/plans/sapplefeld-channels_dsh-bridge_spec_v1.md` in that repository, about the retired harness, is archived in the same PR. Mirroring is off for supervised children so the thread carries operator conversation, not every turn.
   - An open ask never silences the worker. Today an open ask suppresses the controller's nudges, the classifier can re-open the same question after it was answered, and only an inbox record carrying the ask id closes it; with a quiet channel the worker sits for hours logging "still open" and reads nothing, not even this file. Required: a reply typed in the thread while an ask is open answers that ask, a closed question is not re-asked for the same node, an ask open past a bounded window re-raises itself into the thread once, and the controller's own nudges resume on a plan whose ask has gone unanswered rather than waiting forever. Proof: a harness case for each of the four, and a live run where an ask is answered from the thread with no ask id typed.
   - A proof child is stopped when its proof ends, so its persona claim does not shape the next proof. A second proof child that finds the first still holding `default` comes up as a reader and proves less than it seems to.
   - `agentic_say` and `agentic_inbox` stay as the tool-to-tool path between sessions on one machine, which is what the live suites use. They are not the operator's channel.
   - Bounded store. The shared store keeps only open asks and a short window of recent inbox and reply records per persona; closed records roll to an append-only `.agentic-channel.jsonl` in the work directory. Today every message ever sent stays in the one JSON file, which grows without bound and is rewritten whole on each write. The persona file (`.agentic-personas.json`) is bounded the same way: the decision log is capped at the push, not only when the file is parsed at a session load, since a long-lived child never reloads (today the cap of 200 lives in `parseState` and the running worker's file holds over 500); entries that fall off the cap roll to the same append-only log; and memory has a cap, with the quality rule from item 8 deciding what enters. Proof: a harness case that sends more records than the window holds and finds the store at the window size and the log holding the rest, and one that pushes more decisions than the cap in a single session and finds the file at the cap with the overflow in the log.
