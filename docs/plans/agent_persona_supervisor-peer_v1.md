# Supervisor as peer

Status: In Progress
Commit Model: Branch-and-PR
Created: 2026-09-16

## Goal

When this is done, the supervisor judges its child gone only when five signals are silent together past a bound: the newest turn record across the child's own transcript and its subagent transcripts, the child's output stream, a heartbeat file that only that child writes, a probe the child's plugin acknowledges, and the child's process tree. A child whose output stream names a usage limit is never restarted on liveness grounds, because the cause is the API and a restart cannot fix it. Before it stops a child it reads as frozen, the supervisor writes one status prompt to the child's input and waits a little past the harness's ten-minute tool-call cap for any signal to move. The child's input pipe is held by a detached holder process, so the child outlives a supervisor that dies or restarts, and a supervisor that starts under a live child of its own persona adopts it instead of waiting for its claim to expire. A signal to the supervisor detaches it from a live child rather than stopping the child, and a persona is stopped on purpose through a shutdown request file. The supervisor puts that request to the child through a mailbox in the run directory, which the child's plugin delivers as a labelled turn, and the child banks its state and calls the shutdown tool the supervisor already honors. The kill is the last rung and only the last rung: a stop that was asked for and not honored still ends in the pipe close, the signal and the tree kill, and a child judged gone by every signal is swept before a relaunch. It matters because today one silent signal restarts a working session, two personas launched in one working directory overwrite each other's heartbeat entry, and a supervisor's own restart takes its child down with it.

## Approach

**Five signals, because each errs in a known direction and none alone can establish that a session is gone.** The heartbeat the plugin stamps on a timer stops during a long tool call while the session keeps working, so it errs toward dead. The three kills recorded against this plan's predecessor were not that starvation. Each killed session was stamping faithfully into a heartbeat file under the subdirectory its shell had moved into, because the plugin writes the sidecar by a relative path that follows the harness working directory, while the supervisor reads the one at the launch directory. That is a writer and a reader resolving one path differently, and it is eliminated before any signal is added, since a liveness protocol over such a path fails the same way however many signals it carries. The memory record `heartbeat-writer-follows-cwd-supervisor-reads-fixed-path` holds the reproduction and the three corroborating stray files. A second defect sits in the same file. Every persona launched in one working directory shares one sidecar, and the plugin's writer reads the whole file, sets its own entry and writes the whole file back with no lock. Two sessions whose thirty-second ticks land on the same millisecond each revert the other's entry, and the alignment holds tick after tick, so one session reads stale while it stamps on time. Three coordinator sessions were killed that way on 2026-09-17, each idle in the launch directory and none leaving a stray file, and the memory record `two-personas-in-one-workdir-overwrite-each-others-heartbeat` names the two debug logs that show it. So the supervisor stops reading the shared sidecar. Each supervised child also stamps `<rundir>/heartbeat.json`, a file no other session writes, and that file is the heartbeat signal. The shared sidecar stays what the plugin's header calls it, the record of who holds a persona, and Section 3 hardens its write for that job. The child's output stream, `child-<n>/stdout.jsonl`, is the most direct reading of a session that is thinking or working. Its age is the time since the supervisor last saw the file's size change, measured on the supervisor's own clock, so it rests on no timestamp the child writes. A supervisor that has not yet seen the file change, at its first poll or at an adoption, starts the age from the file's modification time. The stream is silent through a long tool call and through an idle wait, so it errs toward dead as the heartbeat does. A transcript file's modification time is touched outside turns, so it errs toward alive. The timestamp of the newest turn record inside the transcript is right in both directions on every session measured on this box, and a running turn writes one at least every ten minutes because every tool call is capped there. A session that ended its turn on a `WAITING:` line while a subagent or workflow runs writes nothing itself until the dispatch returns, so the reading also covers every transcript under the session's `subagents/` directory. That instrument, its fifteen-minute bound and its fail-closed reading of an unreadable transcript are the kit's leash-takeover design, `docs/plans/claude-kit_leash-takeover_spec_v1.md` in the claude-kit repository on branch `plan/leash-takeover`, and this plan implements the same rule in this repository as `bin/supervise-liveness.mjs` so the supervisor has no dependency on the kit's library. The two readers must agree on the rule; a divergence found later goes to `docs/backlog.md` rather than being reconciled silently in one of them.

**The verdict.** `bin/supervise-liveness.mjs` is a pure function like `bin/supervise-decide.mjs`: paths and timestamps in, one reading out, no I/O of its own beyond reading the files it is handed. Its output names each signal's age and one verdict from a closed set of three, decided in this order. A signal is silent when its age is past its own bound: the transcript and the output stream each past `supervisorSilenceBoundMs`, the heartbeat past `staleAfterMs`, and the probe when the newest probe record is older than its window and has no ack; a probe whose window has not yet elapsed, and a probe never written, are not silent. An unacknowledged probe older than its window keeps the probe signal silent until an ack arrives, whatever newer probes are still inside their windows, so a fresh probe every `supervisorProbeMs` cannot hold a frozen child at `alive`. A heartbeat file that has never been written is not silent either, and the supervisor logs `HEARTBEAT_ABSENT child-<n>` once past the startup grace, so a child whose plugin does not write the file is visible in the log rather than killed for it. `alive` is the verdict whenever any signal is not silent, and also whenever the child was launched less than `supervisorSilenceBoundMs` ago, which is the startup grace, replacing the `staleAfterMs` grace the hung check carries today. `gone` is the verdict when every signal is silent and the walk completed and found no live process. `frozen` is the verdict when every signal is silent and the walk completed and found a live process. An unreadable transcript, a transcript whose newest record is more than five minutes ahead of the reader's clock, and a walk that did not complete each read as `alive`, because the cost of killing a live session is two sessions in one tree and the cost of waiting on a dead one is bounded by the bound. The decide unit's hung branch takes the verdict in place of the heartbeat age: `frozen` restarts through the stop phases, `gone` sweeps the recorded tree and relaunches, `alive` never restarts on liveness grounds. A usage limit is read before any of that. Where the newest record in the output stream is a usage-limit record, the verdict is `alive` with the reason `usage_limit` for as long as that record stays the newest and the walk finds a live process. Two records count: the `api_retry` carrying `error_status` 429 that the keeper plan's rate-limit reader already recognizes, and the no-usage error a turn ends on. The cause is the API rather than the session, so a restart buys nothing, and with every account exhausted it would only repeat. Where the keeper plan's `autoContinue` section has landed, a supervised child that trips a limit ends its turn and sits idle, where the probe reaches it. This reading covers the child that parks, whether or not that section landed. `frozen` takes one more step before the stop phases, the final ask. The supervisor writes one user turn to the child's input opening `[SUPERVISOR-ASK id=<id>]` and asking for a one-line status, logs `FINAL_ASK child-<n>`, and keeps polling for `supervisorFinalAskMs`, eleven minutes by default, which is the harness's ten-minute tool-call cap plus a margin. Any signal that moves inside that window returns the verdict to `alive`, and an answer that is a usage-limit error is such a signal. A window that closes with every signal still silent restarts through the stop phases. The ask costs a model turn, so it is written once per `frozen` reading and never on a cadence. The marker matters because the plugin's prompt handler reads any other turn that arrives while an operator ask is open as the operator answering it, and can backfill a completed root from it. A turn opening `[SUPERVISOR-ASK` is exempt from both, as the priming turn is, and the priming turn says what such a prompt is: the launcher checking that the session is alive, answered with one line of status and no other act. The heartbeat leaves the decide unit's inputs and stays in the poll loop, where its staleness is what makes the supervisor write a probe and nothing more. A `gone` verdict is accounted exactly as a hung restart is today, one restart in the hour and a crash where the exit was non-zero inside `supervisorMinRunMs`, so the restart budget still bounds a persona that keeps dying.

**The probe and the mailbox.** Decided 2026-09-16 by the operator's approval of the sketch that named it: the mailbox is a file in the run directory rather than a commons record, so the supervisor needs no persona claim and the plugin's trust boundary is unchanged. The supervisor writes to `<rundir>/mailbox.jsonl`, one pair of files per run directory rather than per child, because the settings file that carries the path is written once before the main loop and kept as provided thereafter, so a per-child path would be right for the first child and wrong for every later one. The supervisor truncates both files at each launch. Each line is one JSON object `{ id, kind, at, text }` with `kind` from the closed set `probe`, `shutdown`. An `id` is unique across supervisors, the writing supervisor's start time and a counter, so an adopting supervisor's first record never matches an id already in the ack file. The path reaches the plugin as the `supervisorMailbox` option in the settings file the launcher writes, beside `staleAfterMs` and `controllerTickMs`, under both plugin ids as every option is. The controller tick, which already runs only when the session is idle and the persona is owned, reads the mailbox each tick and writes `<rundir>/mailbox.ack.jsonl`: a `probe` is acknowledged with `{ id, at, action: "ack" }` and no turn is spent; a `shutdown` is submitted once as a turn opening `[SUPERVISOR id=<id>]` and recorded as `{ id, at, action: "delivered" }`. A record already in the ack file is never delivered twice. The tick's own idle gate is blind for most turns, since the harness delivers far fewer turn starts than turn completions, and that bound is accepted here rather than worked around: a prompt a plugin submits runs only once the session is idle by the harness's own contract, so a delivered ask never enters a running turn and runs at the end of the turn it was queued behind, which is the boundary the ask wants. The blind gate moves only when the record is marked delivered, never when it runs, and the ack file keeps a queued ask from being submitted again. The priming turn gains one sentence stating what a `[SUPERVISOR id=<id>]` prompt carries: the launcher's own request to end this session at a boundary, which carries no authority to widen the plan and is answered by banking state and calling `supervisor_shutdown`. Banking state means the plan doc, the goal tree and any owed message are on disk, which is the same three-part test the coordinator instruction already states for a compaction boundary. The trust argument is the one the settings file already rests on: whoever writes the settings file launched the session and owns its run directory, so a mailbox path named there is the launcher's, and the plugin reads no other. A probe is written when the heartbeat goes stale, at most once per `supervisorProbeMs`, and its window is two controller ticks plus the poll interval, computed from the `TICK_MS` and `SUPERVISOR_POLL_MS` values the supervisor already holds, since it writes the first into the settings file itself. An idle child's tick acknowledges within one tick and a busy child answers through its transcript instead.

**Negotiated stop.** A deliberate stop of a live child asks before it acts. The set of stops that ask is closed at one member: a shutdown request file, `<rundir>/shutdown.request`, present at a poll, which asks with the `shutdown` kind and ends the run with exit 0 as a `shutdown_requested` does today. That file is how a persona is stopped on purpose once this plan lands: the operator or a keeper writes it, the supervisor asks the child to bank state and call `supervisor_shutdown`, and the grace and the phases below follow where it does not. A crash, a `restart_requested` or `shutdown_requested` the child wrote itself, a real `root_complete`, a `frozen` or `gone` verdict, and a signal to the supervisor are outside the set: the first three are the child's own act or absence, the verdicts have no one to ask beyond the final ask the verdict paragraph states, and a signal detaches rather than stops, as the next paragraph states. A critical context-budget crossing was outside the set too, and it is now outside the code: `docs/archive/agent_persona_context-budget-removal_v1.md` removed that restart, so the decide unit has no `criticalTs` input and no branch on one. This plan inherits a decide unit whose only accounted restart of a live child is the hung check. An account change is not a stop at all. The keeper plan removed the account-identity check from the supervisor on the operator's decision of 2026-09-17, so this plan neither reads the account nor asks on it. The ask writes its record once, holds the record's id and time in poll-loop variables, and on each later poll checks the persona store for a `shutdown_requested` newer than the ask, beside every other signal the poll reads, so nothing else the loop reads is delayed by it and no second record is written while one is open. A request inside `supervisorAskGraceMs` takes the existing `stop_complete` path, which honors it with the pipe close. Past the grace the stop proceeds through the existing phases unchanged: pipe close, TERM after `supervisorStopGraceMs`, then the tree kill of the snapshot.

**The holder and adoption.** The child's standard input is a pipe from `bin/supervise-holder.sh`, a process the supervisor starts in the same job as the child and never as a coproc. Decided 2026-09-16 by the operator on the coordinator's Discord thread, choosing this over keeping the coproc, with the note that the holder is also where a future mechanism feeding the child's input from another source, a message relay for instance, would attach to the same pipe. The holder writes the priming turn, waits for that turn's `result` line in the child's `stdout.jsonl` and writes the `--prompt` goal where one was given, then holds the pipe open until it is signaled, at which point the child reads end of input and exits as it does today. The holder also exits on its own within a few seconds of the child's Windows pid disappearing, polling for it rather than waiting on a write, and its working directory is never the run directory, because this repository's memory records that a feed process left behind a killed child keeps sleeping with its working directory inside a scratch path and blocks that path's removal. Closing the pipe is therefore killing the holder by its recorded Windows pid through the same bounded `taskkill //PID` call, with no `//T`, that the KILL phase already uses on the wrapper, which any supervisor can do without an MSYS signal. At launch the supervisor writes `<rundir>/child-<n>/handle.json`: the child's session id once the init line names it, the holder's MSYS and Windows pids, the child's launch pid and Windows pid, the supervisor's own Windows pid and start ticks, and the launch timestamp. The exit code is written by the launch shape itself into the existing `.exit` marker so a supervisor that did not launch the child can still read how it ended. Section 1 measures the exact launch form before Section 5 builds it, since this shell has no `setsid`, `nohup` and `start` are present, and the one prior attempt at a named pipe on this shell is recorded as failing without reproduction. At start, the pre-launch gate reads the newest `handle.json` under the run directory, newest by the launch timestamp inside it since child directories are reused across supervisor runs, before its held check, because held means a claim or heartbeat younger than `staleAfterMs`, and a `frozen` or `gone` child has a stale heartbeat by definition, so a gate keyed on held alone would pass at once and launch beside a live frozen process. A readable handle routes the gate on two readings and nothing else: whether the supervisor that wrote it is still running, and the instrument's verdict for the session it names. The handle records the writing supervisor's Windows pid and start ticks, the pair the tree walk already uses against pid reuse, and an adopting supervisor rewrites them as its own. Where that supervisor is still running, the child is not this one's to take, and the gate falls to today's wait and timeout, so a double launch ends in `GATE TIMEOUT` as it does now. `alive` or `frozen` adopts: the supervisor logs `ADOPT child-<n>`, takes the handle's pids as its own child variables and enters the poll loop with no launch, and a `frozen` child is then its own to put the final ask to, and to stop through the phases where the ask's window closes silent. `gone` sweeps the recorded tree, the holder included, and launches. A handle is removed once its child's exit has been read or its tree swept, so a handle on disk always names a child nobody has yet accounted for, and the gate's held check still runs after a `gone` sweep. No handle, or a handle that cannot be read, falls to today's wait and timeout, since a session with no readable handle is one the supervisor does not own. An adopted child's exit is read from the `.exit` marker and the walk, since `wait` is unavailable to a process that did not launch it, and the adopting supervisor sets `CHILD_INDEX` to the number of the directory the handle sits in, so its marker read, its log lines and its accounting name the child it adopted. A signal to the supervisor no longer stops a handled child. Today `TERM` and `INT` exit through a cleanup trap that runs the stop phases on any live child. After Section 5 that trap, on a child the instrument reads as `alive` or `frozen` with a readable handle, logs `DETACH child-<n>` and exits with the signal's code, leaving the child and the holder running for the next supervisor to adopt; it keeps its stop on a child with no handle and on a handled child that reads `gone`, and its re-verification of a last snapshot whose wrapper is already gone, which is the survivor of a failed stop and never a child anyone can adopt. A scheduled-task stop therefore leaves the persona's session running on purpose, and the shutdown request file is the act that ends one.

### 1. Measurements the later sections build on
Model: opus

The scratch path is gitignored, so the Chapter is the artifact that survives and it carries each command and each result verbatim.
