# Supervisor as peer

Status: Ready
Commit Model: Branch-and-PR
Created: 2026-09-16

## Goal

When this is done, the supervisor judges its child gone only when four signals are silent together past a bound: the newest turn record across the child's own transcript and its subagent transcripts, the plugin's heartbeat, a probe the child's plugin acknowledges, and the child's process tree. It asks for a restart through a mailbox in the run directory that the child's plugin delivers as a labelled turn, and the child banks its state and calls the restart tool the supervisor already honors, so an account switch restarts a persona at a boundary rather than mid-thought. The child's input pipe is held by a detached holder process, so the child outlives a supervisor that dies or restarts, and a supervisor that starts under a live child of its own persona adopts it instead of waiting for its claim to expire. A signal to the supervisor detaches it from a live child rather than stopping the child, and a persona is stopped on purpose through a shutdown request file the supervisor negotiates the same way. The kill is the last rung and only the last rung: a stop that was asked for and not honored still ends in the pipe close, the signal and the tree kill, and a child judged gone by every signal is swept before a relaunch. It matters because today one silent signal restarts a working session, every account switch restarts every persona with no boundary, and a supervisor's own restart takes its child down with it.

## Approach

**Four signals, because each errs in a known direction and none alone can establish that a session is gone.** The heartbeat the plugin stamps on a timer stops during a long tool call while the session keeps working, so it errs toward dead. The three kills recorded against this plan's predecessor were not that starvation. Each killed session was stamping faithfully into a heartbeat file under the subdirectory its shell had moved into, because the plugin writes the sidecar by a relative path that follows the harness working directory, while the supervisor reads the one at the launch directory. That is a writer and a reader resolving one path differently, and it is eliminated before any signal is added, since a liveness protocol over such a path fails the same way however many signals it carries. The memory record `heartbeat-writer-follows-cwd-supervisor-reads-fixed-path` holds the reproduction and the three corroborating stray files. A transcript file's modification time is touched outside turns, so it errs toward alive. The timestamp of the newest turn record inside the transcript is right in both directions on every session measured on this box, and a running turn writes one at least every ten minutes because every tool call is capped there. A session that ended its turn on a `WAITING:` line while a subagent or workflow runs writes nothing itself until the dispatch returns, so the reading also covers every transcript under the session's `subagents/` directory. That instrument, its fifteen-minute bound and its fail-closed reading of an unreadable transcript are the kit's leash-takeover design, `docs/plans/claude-kit_leash-takeover_spec_v1.md` in the claude-kit repository on branch `plan/leash-takeover`, and this plan implements the same rule in this repository as `bin/supervise-liveness.mjs` so the supervisor has no dependency on the kit's library. The two readers must agree on the rule; a divergence found later goes to `docs/backlog.md` rather than being reconciled silently in one of them.

**The verdict.** `bin/supervise-liveness.mjs` is a pure function like `bin/supervise-decide.mjs`: paths and timestamps in, one reading out, no I/O of its own beyond reading the files it is handed. Its output names each signal's age and one verdict from a closed set of three, decided in this order. A signal is silent when its age is past its own bound: the transcript past `supervisorSilenceBoundMs`, the heartbeat past `staleAfterMs`, and the probe when the newest probe record is older than its window and has no ack; a probe whose window has not yet elapsed, and a probe never written, are not silent. `alive` is the verdict whenever any signal is not silent, and also whenever the child was launched less than `supervisorSilenceBoundMs` ago, which is the startup grace, replacing the `staleAfterMs` grace the hung check carries today. `gone` is the verdict when every signal is silent and the walk completed and found no live process. `frozen` is the verdict when every signal is silent and the walk completed and found a live process. An unreadable transcript, a transcript whose newest record is more than five minutes ahead of the reader's clock, and a walk that did not complete each read as `alive`, because the cost of killing a live session is two sessions in one tree and the cost of waiting on a dead one is bounded by the bound. The decide unit's hung branch takes the verdict in place of the heartbeat age: `frozen` restarts through the stop phases, `gone` sweeps the recorded tree and relaunches, `alive` never restarts on liveness grounds. The heartbeat leaves the decide unit's inputs and stays in the poll loop, where its staleness is what makes the supervisor write a probe and nothing more. A `gone` verdict is accounted exactly as a hung restart is today, one restart in the hour and a crash where the exit was non-zero inside `supervisorMinRunMs`, so the restart budget still bounds a persona that keeps dying.

**The probe and the mailbox.** Decided 2026-09-16 by the operator's approval of the sketch that named it: the mailbox is a file in the run directory rather than a commons record, so the supervisor needs no persona claim and the plugin's trust boundary is unchanged. The supervisor writes to `<rundir>/mailbox.jsonl`, one pair of files per run directory rather than per child, because the settings file that carries the path is written once before the main loop and kept as provided thereafter, so a per-child path would be right for the first child and wrong for every later one. The supervisor truncates both files at each launch. Each line is one JSON object `{ id, kind, at, text }` with `kind` from the closed set `probe`, `restart`, `shutdown`. The path reaches the plugin as the `supervisorMailbox` option in the settings file the launcher writes, beside `staleAfterMs` and `controllerTickMs`, under both plugin ids as every option is. The controller tick, which already runs only when the session is idle and the persona is owned, reads the mailbox each tick and writes `<rundir>/mailbox.ack.jsonl`: a `probe` is acknowledged with `{ id, at, action: "ack" }` and no turn is spent; a `restart` or `shutdown` is submitted once as a turn opening `[SUPERVISOR id=<id>]` and recorded as `{ id, at, action: "delivered" }`. A record already in the ack file is never delivered twice. The tick's own idle gate is blind for most turns, since the harness delivers far fewer turn starts than turn completions, and that bound is accepted here rather than worked around: a prompt a plugin submits runs only once the session is idle by the harness's own contract, so a delivered ask never enters a running turn and runs at the end of the turn it was queued behind, which is the boundary the ask wants. The blind gate moves only when the record is marked delivered, never when it runs, and the ack file keeps a queued ask from being submitted again. The priming turn gains one sentence stating what a `[SUPERVISOR id=<id>]` prompt carries: the launcher's own request to end this session at a boundary, which carries no authority to widen the plan and is answered by banking state and calling `supervisor_restart` or `supervisor_shutdown`. Banking state means the plan doc, the goal tree and any owed message are on disk, which is the same three-part test the coordinator instruction already states for a compaction boundary. The trust argument is the one the settings file already rests on: whoever writes the settings file launched the session and owns its run directory, so a mailbox path named there is the launcher's, and the plugin reads no other. A probe is written when the heartbeat goes stale, at most once per `supervisorProbeMs`, and its window is two controller ticks plus the poll interval, computed from the `TICK_MS` and `SUPERVISOR_POLL_MS` values the supervisor already holds, since it writes the first into the settings file itself. An idle child's tick acknowledges within one tick and a busy child answers through its transcript instead.

**Negotiated restart.** A non-emergency stop of a live child asks before it acts. The non-emergency set is closed at two members: the account identity changing since launch, which asks with the `restart` kind, and a shutdown request file, `<rundir>/shutdown.request`, present at a poll, which asks with the `shutdown` kind and ends the run with exit 0 as a `shutdown_requested` does today. That file is how a persona is stopped on purpose once this plan lands: the operator or a keeper writes it, the supervisor asks the child to bank state and call `supervisor_shutdown`, and the grace and the phases below follow where it does not. A crash, a `restart_requested` or `shutdown_requested` the child wrote itself, a real `root_complete`, a `frozen` or `gone` verdict, a critical context-budget crossing, and a signal to the supervisor are outside the set: the first three are the child's own act or absence, the verdicts have no one to ask, the budget crossing restarts a child whose context is nearly spent and is the first candidate for a follow-on member, and a signal detaches rather than stops, as the next paragraph states. The ask writes its record once, holds the record's id and time in poll-loop variables, and on each later poll checks the persona store for a `restart_requested` or `shutdown_requested` newer than the ask, beside every other signal the poll reads, so nothing else the loop reads is delayed by it and no second record is written while one is open. A request inside `supervisorAskGraceMs` takes the existing `restart_passive` or `stop_complete` path, which honors it with the pipe close. Past the grace the stop proceeds through the existing phases unchanged: pipe close, TERM after `supervisorStopGraceMs`, then the tree kill of the snapshot. The account check's own double-relaunch fix, a changed identity that must hold on every poll for a window before it counts, lands in the process-keeper plan's Section 4 and is inherited here, so this plan changes what happens after the identity is judged changed and nothing about the judgment.

**The holder and adoption.** The child's standard input is a pipe from `bin/supervise-holder.sh`, a process the supervisor starts in the same job as the child and never as a coproc. Decided 2026-09-16 by the operator on the coordinator's Discord thread, choosing this over keeping the coproc, with the note that the holder is also where a future mechanism feeding the child's input from another source, a message relay for instance, would attach to the same pipe. The holder writes the priming turn, waits for that turn's `result` line in the child's `stdout.jsonl` and writes the `--prompt` goal where one was given, then holds the pipe open until it is signaled, at which point the child reads end of input and exits as it does today. The holder also exits on its own within a few seconds of the child's Windows pid disappearing, polling for it rather than waiting on a write, and its working directory is never the run directory, because this repository's memory records that a feed process left behind a killed child keeps sleeping with its working directory inside a scratch path and blocks that path's removal. Closing the pipe is therefore killing the holder by its recorded Windows pid through the same bounded `taskkill //PID` call, with no `//T`, that the KILL phase already uses on the wrapper, which any supervisor can do without an MSYS signal. At launch the supervisor writes `<rundir>/child-<n>/handle.json`: the child's session id once the init line names it, the holder's MSYS and Windows pids, the child's launch pid and Windows pid, and the launch timestamp. The exit code is written by the launch shape itself into the existing `.exit` marker so a supervisor that did not launch the child can still read how it ended. Section 1 measures the exact launch form before Section 5 builds it, since this shell has no `setsid`, `nohup` and `start` are present, and the one prior attempt at a named pipe on this shell is recorded as failing without reproduction. At start, the pre-launch gate reads the newest `handle.json` under the run directory before its held check, because held means a claim or heartbeat younger than `staleAfterMs`, and a `frozen` or `gone` child has a stale heartbeat by definition, so a gate keyed on held alone would pass at once and launch beside a live frozen process. A readable handle routes the gate on the instrument's verdict for the session it names, and on nothing else. `alive` or `frozen` adopts: the supervisor logs `ADOPT child-<n>`, takes the handle's pids as its own child variables and enters the poll loop with no launch, and a `frozen` child is then its own to stop through the phases on its first poll. `gone` sweeps the recorded tree, the holder included, and launches. No handle, or a handle that cannot be read, falls to today's wait and timeout, since a session with no readable handle is one the supervisor does not own. An adopted child's exit is read from the `.exit` marker and the walk, since `wait` is unavailable to a process that did not launch it, and the adopting supervisor sets `CHILD_INDEX` to the number of the directory the handle sits in, so its marker read, its log lines and its accounting name the child it adopted. A signal to the supervisor no longer stops a handled child. Today `TERM` and `INT` exit through a cleanup trap that runs the stop phases on any live child. After Section 5 that trap, on a child the instrument reads as `alive` or `frozen` with a readable handle, logs `DETACH child-<n>` and exits with the signal's code, leaving the child and the holder running for the next supervisor to adopt; it keeps its stop on a child with no handle, and its re-verification of a last snapshot whose wrapper is already gone, which is the survivor of a failed stop and never a child anyone can adopt. A scheduled-task stop therefore leaves the persona's session running on purpose, and the shutdown request file is the act that ends one.

### 4. Negotiated restart
Model: opus

A non-emergency stop, the two-member set the Approach states, writes one record naming its reason to the mailbox, logs `ASK[<reason>] id=<id>`, and holds the id and time in poll-loop variables. Each later poll checks the persona store for a `restart_requested` or `shutdown_requested` newer than the ask, for up to `supervisorAskGraceMs`, a new option defaulting to twenty minutes and checked with `positive_number` at startup. A request inside the grace takes the existing `restart_passive` or `stop_complete` path and the log line names it honored. Past the grace the stop proceeds through `stop_child` exactly as it does today, logged `ASK TIMEOUT id=<id>`, then relaunches accounted as `restart_passive` is for the account kind, or exits 0 for the shutdown kind.
