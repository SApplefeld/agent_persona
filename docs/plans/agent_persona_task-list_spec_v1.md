# Task List Tier

Status: In Progress
Commit Model: Branch-and-PR
Created: 2026-09-24

## Goal
The agent_persona plugin gains a structured task list: a lightweight working-item store that sits beside the goal tree, scoped to the goal a persona is on right now. A persona adds tasks, marks them done, and clears them, the same add / done / clear lifecycle the goals already have, one tier below. The list is injected into the persona's context scoped to the active goal, so the persona sees its own working items. The goal is the authority for completion: completing the goal clears its tasks, and completing all of a goal's tasks prompts the persona to close the goal rather than closing it automatically. The list is the short-term tier of a three-tier model: task list now, goals medium-term, long-term goals as the slow-moving direction. It does not touch the goal tree, and it stays out of the way of a plan run, where the plan document's chapters are already the crossed-off task list.

## Intent
Scott asked for a genuine task list, distinct from the goal tree. In his words: a persona working through a series of turns on a goal maintains a scratch pad of active working items, completes them, and is usually done with the goal when they are done. That scratch pad is short-term memory. The goals are medium-term. The long-term goals are the big overarching direction. He wants the task list structured, with tasks genuinely crossed off and then cleared, the way the goals are, rather than a freeform note.

What done needs to do: give the persona a per-goal working list with add, done, and clear, injected scoped to the active goal, and cleared automatically when that goal completes. The list must be lighter than a goal, because the goal tree already carries the medium-term structure. The injected list is bounded so it stays lighter than the goal block.

What done does not need to do: it does not decide when a task should become a goal. That is goal genesis, and it belongs with the turn-records and promotion design still being worked out, deferred whole to a later plan (Plan B). This store is also not the turn record: a task belongs to an active goal and never exists without one, while a turn record, a separate field a later ruling defines, is an intention with no goal yet or ahead of one. This spec builds the task field only.

Alternatives refused:
- Reuse the goal tree's existing task-kind leaf nodes as the task list. Refused because those leaves are heavyweight: scored, round-budgeted, and activated one at a time. Scott asked for a lighter tier beside the tree, not a rename of the tree's leaves.
- A literally separate file on disk, which Scott's "second file" framing evoked. The plugin keeps all persona state in one store file per working directory, so the list is a field in that file, beside the goals array. This honors the separate-structure intent without a second file.

Rulings after the spec ships:
- Ruling 2026-09-24: the goal is the authority for completion. Completing the goal clears its tasks. Completing all of a goal's tasks prompts the persona to close the goal, through the injected block, but never closes it automatically. Scott confirmed this direction over auto-completion, because a premature auto-close is annoying to undo and the persona adds tasks incrementally, so the system cannot know a task list is a goal's whole decomposition.

Provenance: distilled from the design conversation with Scott on 2026-09-24, on the ARCHITECT relay thread, with the task-versus-turn-record seam coordinated with the ASSISTANT persona.

## Approach
The task list is a new lightweight structure, not an extension of the goal tree. The goal system already has three-level goal nodes (root, plan, task) that are scored and activated one at a time. The task list sits below that granularity: it holds the fine-grained working items for whichever goal is active, and it never becomes a goal.

Storage is a new `tasks` array on `AgentState`, beside the existing `goals` array, each task carrying the id of the goal it belongs to. The store is versioned, so adding the field is a version bump from 4 to 5 with a migration that seeds an empty list on an older store. A task carries an id, its goal's id, its text, a done flag, and timestamps.

The list is scoped to the active goal by the goal id on each task. Because exactly one leaf is active at a time (the exactly-one-active-leaf invariant that `enforceInvariants` holds), the active goal and the active leaf are the same node; the spec uses "active goal" for it. The injection shows only the active goal's tasks.

Completion clears a goal's tasks through a reap helper, `reapCompletedGoalTasks(state)`, that drops any task whose goal has reached a terminal status or no longer exists. It is called on the persist path, so a completion mid-session reaps immediately, and again inside `enforceInvariants`, the load-time backstop for any path that writes state without persisting. This two-site placement is required because `enforceInvariants` today runs only inside `parseState` (agent-state.ts:764, 787, 893) and not on the runtime write path, so an `enforceInvariants`-only reap would not fire until the next load.

A persona drives the list with three new MCP verbs, `task_add`, `task_done`, and `task_clear`, registered beside the `goal_*` verbs and mutating the store through the same persist and yield-arbitration path. The list defers to a plan run: `task_add` refuses when the active goal is a plan-holder, and the injected block never appears there, so the plan document's chapters stay the sole tracker. Long-term goals, the third tier, are the existing `AgentState.longTermGoals` field (agent-state.ts:342) and are not changed.

The task-to-goal promotion seam is deferred whole to Plan B, which the ARCHITECT persona authors. It has three branches, not one: a turn record graduating into a task under the active goal, a turn record graduating into a new goal, and a task graduating into a goal. This spec builds none of them and names the seam so Plan B owns it.

## Standing Brief Amendments

- A goal's completion reaps its tasks on every path by which a goal completes, the root included. A goal reopened afterwards starts with an empty task list, since the plan's Out of Scope list keeps tasks from persisting across a goal's completion.
- A task id is unique across the store and never carries a goal node's or a long-term goal's prefix. Its clock encoding is not part of that contract.

## Sections of Work

### 1. Task store: schema, migration, and completion reap
Model: opus
Add a `TaskItem` type and a `tasks: TaskItem[]` field to `AgentState`, beside `goals`. A `TaskItem` carries `id: string`, `goalId: string`, `text: string`, `done: boolean`, `addedAt: number`, and `doneAt?: number`. Mint a `TaskItem` id the same way goal-node ids are minted (the existing id generator), so ids are unique across the store. Bump the store `version` from 4 to 5. Add a v4 to v5 migration step in `parseState` that seeds `tasks: []` on a store that lacks it. `serializeState` is `JSON.stringify(state)` and includes the new field with no change. Export two constants: `MAX_TASKS_PER_GOAL` (20) and `TASK_LIST_MAX_LINES` (12), used by sections 2 and 3.

Add the reap helper `reapCompletedGoalTasks(state)`, exported from `hooks/agent-state.ts`: it drops any task whose `goalId` maps to a goal in a terminal status, or to no goal at all. Terminal status is a closed set of exactly two values, `complete` and `abandoned`. A task whose goal is `pending`, `active`, `paused`, or `blocked` is kept. Call the helper in two places: inside `enforceInvariants` (the load-time backstop), and in `persist` (hooks/index.ts, before the store write near 2215) so a completion mid-session reaps immediately without waiting for the next load. The persist-path call is what makes the Goal's "when the goal completes, its tasks clear automatically" true within the session.

Also update the stale `docs/backlog.md` cost-ledger entry that names "version 4" to reflect that the terminal store version is now 5; leave its "`enforceInvariants` never touches cost" claim, which stays true.

Acceptance: a v4 fixture store parses to a v5 state with an empty `tasks` array; a goal completed by a persist-triggering mutation has its tasks gone in the same session (the reap ran on persist, not on the next load); a task whose goal is `complete` or `abandoned` is gone after `parseState` too (the load backstop); a task whose goal is `paused` survives both; a task with a `goalId` matching no goal is gone.
Files in scope: hooks/agent-state.ts, hooks/index.ts, .kit/cost-migration-test.mjs (or a new .kit/task-store-unit-test.mjs following the same fixture pattern), .kit/fixtures/ (a new v4 fixture), .kit/controller-tick-test.mjs, docs/backlog.md.
Tests: at minimum, lock the v4-to-v5 migration seeding an empty list, lock the reap firing on the persist path in the same session (not only on load), and lock the reap in both directions (a terminal goal's tasks dropped, a paused goal's tasks kept); a reap that fires only on load, leaving a completed goal's tasks injected for the rest of the session, is the expensive failure.

### 2. Task verbs: task_add, task_done, task_clear
Model: sonnet
Register three MCP verbs beside the `goal_*` registrations (hooks/index.ts near 2932 to 3118) and add their handlers following the `goal_*` handler pattern (intercept in the tool chain, mutate `sess.state`, `persist`, honor yield-arbitration). The active goal is the active leaf.

- `task_add(text)`: append a `TaskItem` to `sess.state.tasks` with `goalId` set to the active goal's id, `done: false`, `addedAt: now`. Refuse when there is no active goal. Refuse when the active goal is a plan-holder, that is when `planHolderOf(sess.state, activeLeaf)` returns a node carrying a `planPath`, whether that node is the active leaf itself or an ancestor; the refusal message points the persona to the plan document's chapters. Refuse when the active goal already holds `MAX_TASKS_PER_GOAL` tasks.
- `task_done(id)`: set `done: true` and `doneAt: now` on the task with that id under the active goal. An id whose task belongs to a goal other than the active one, or that matches no task, is refused as unknown.
- `task_clear()`: remove every task whose `goalId` is the active goal's id. Refuse when there is no active goal.

The plan-holder refusal is the gating rule: `task_add` accepts exactly when `planHolderOf(sess.state, activeLeaf)` returns no node carrying a `planPath`, and refuses otherwise (alongside the no-active-goal and cap refusals). There is no third admission case.

Acceptance: `task_add` under a non-plan active goal adds a task; `task_add` under a plan-holder active goal refuses with the chapters message, whether the active leaf is itself the plan-holder or sits under one; `task_add` with no active goal refuses; `task_add` at the cap refuses; `task_done` marks the named task done and refuses an id not under the active goal; `task_clear` empties the active goal's tasks and leaves other goals' tasks untouched; each verb persists through the normal store write.
Files in scope: hooks/index.ts, .kit/controller-tick-test.mjs, .kit/tick-harness.mjs.
Tests: at minimum, lock both directions of the plan-holder gate (a non-plan goal accepts, a plan goal refuses, including the leaf-is-itself-the-holder case) and lock that `task_done` refuses an id outside the active goal; a silent accept under a plan run, creating a second tracker beside the chapters, is the expensive failure.

## Out of Scope
- The turn record, a separate short-term field a later ruling defines for an intention with no goal yet or ahead of one. This spec builds the task field only, and names the distinction so the two beside-goals fields do not blur.
- Deciding when a task graduates into a goal (goal genesis and promotion), across all three branches. Deferred whole to Plan B; see Open Questions.
- Any change to the goal tree, its task-kind leaves, scoring, activation, the `goal_*` verbs, or the long-term goals field.
- Persisting tasks across a goal's completion, or any task history or archive. Tasks are reaped on goal completion by design.
- Editing or reordering a task's text after it is added (no `task_edit`); the lifecycle is add, done, clear only.
- Auto-completing a goal when its tasks are all done. The completion authority runs one way only: the goal closes tasks, and all-tasks-done prompts but never closes the goal.
- The kit plan document's chapters, which remain the task record for a plan run and are not touched.

## Assumptions
- assumed 2026-09-24 (default): the task list is a field in the single per-directory store file, not a separate file; reversal: a separate file would fight the plugin's one-store-per-directory design and is a larger change.
- assumed 2026-09-24 (default): the task list is per-goal and clears on goal completion rather than persisting; reversal: a persisting or historical task tier would need its own store field and an archive path, a larger change.
- assumed 2026-09-24 (default): tasks are injected scoped to the active goal only, not across all goals; reversal: an all-goals task view would enlarge the injected block and is the leanness cost the goal tree already guards against.
- assumed 2026-09-24 (default): `task_add` refuses under a plan-holder goal rather than allowing a silent, non-injected list; reversal: relaxing to allow-but-not-inject is a one-line change if Scott wants quick sub-notes under a plan goal.
- assumed 2026-09-24 (default): the task list does not replace or touch the plan-document chapters for a plan run; reversal: unifying the two trackers would be a separate, larger design.
- assumed 2026-09-24 (source: brainstorming scope check): this is one coherent subsystem (one store field, three verbs, one injected block, one lifecycle), specced as one plan rather than split.
